## 3. 关键决策

### 3.1 布局形态：可折叠侧边栏 + 顶栏

```
┌──────────────┬──────────────────────────────┐
│ 求职助手  ☰   │ 今日概览           [操作区]   │ ← 顶栏 56px
├──────────────┼──────────────────────────────┤
│ ▸ 今日概览    │                              │
│   投递管理    │                              │
│   JD 匹配分析 │                              │
│   模拟面试    │        页面内容区             │
│   八股陪练    │       <router-view />        │
│   错题本      │                              │
│   面经整理    │                              │
│   系统设置    │                              │
└──────────────┴──────────────────────────────┘
  侧边栏 210px，折叠后 64px
  顶部右侧 [操作区] = 页面级按钮插槽，本步留空
```

**理由**：后续页面需要页面级操作区（新增投递、生成总结、刷新模型列表等按钮），顶栏提供统一落点，避免每个页面各写一套标题栏。折叠态改善小屏可用性。

### 3.2 代码组织：App.vue 骨架 + 抽出侧边栏/顶栏子组件

| 文件 | 职责 | 预估行数 |
|---|---|---|
| `App.vue` | `el-container` 骨架、折叠状态、`<router-view />` | ~60 |
| `components/SideNav.vue` | 菜单配置渲染、`el-menu`、路由高亮 | ~60 |
| `components/AppHeader.vue` | 折叠按钮、当前页标题、右侧操作区插槽 | ~40 |

**理由**：项目结构文档规定「App.vue = 布局：侧边导航 + 内容区 + `<AgentFloatBall/>`」。全部内联会让 App.vue 膨胀到 ~200 行且职责混杂；抽子组件既保持 App.vue 的布局职责，又不新增文档外目录（`components/` 已在文档目录树中）。

**替代方案**（未采用）：路由嵌套 + `layouts/DefaultLayout.vue`。更灵活（未来做无布局页面容易），但本项目所有页面共用同一布局，用不上该灵活性，且引入文档外的顶层 `layouts/` 目录。

### 3.3 引入 `@element-plus/icons-vue`

项目结构文档第 5 节的 frontend 依赖清单未列此包，但**折叠侧边栏是本步的既定形态**：折叠后菜单只剩图标位，无图标则侧边栏变成一条空白窄条，完全不可用。因此图标包是折叠布局的前提条件，非装饰性新增。

按需引入使用到的图标（不做全局注册，避免打包全部 ~300 个图标）。

### 3.4 不建 `stores/` 目录

系统设计文档 4.2 规定 `useAppStore` 承担「设置项、全局提示（el-message 封装）」。但本步没有任何 store 的真实需求：

- 设置项 → 步骤 7
- 概览数据轮询 → 步骤 5
- 悬浮球对话状态 → 步骤 16

`main.js` 照常 `.use(createPinia())` 挂载 Pinia（为后续铺路）；`request.js` 的错误提示直接调用 `ElMessage`（3 行）。步骤 7 建 `app.js` 时如需收口提示逻辑，改 `request.js` 一行 import 即可。

**若倾向骨架一次到位**，可改为本步创建 `stores/app.js` 空壳——本设计默认不建（YAGNI）。

### 3.5 不建 `styles/` 目录

全局样式仅需 `html, body, #app { height: 100%; margin: 0 }` 等少量规则，写在 `App.vue` 的**非 scoped** `<style>` 块内。这样目录结构与项目结构文档第 3 节完全一致，不引入文档外目录。

### 3.6 `request.js` 拦截器返回业务数据

`baseURL = '/api/v1'`（对齐后端 `settings.api_prefix`）。

**关键依据**：后端异常处理器（`app/exceptions.py`）保证**所有错误出口均为「非 200 HTTP 状态码 + 统一响应体」**，从不出现「HTTP 200 + code≠0」：

| 场景 | HTTP | body.code |
|---|---|---|
| 成功 | 200 | 0 |
| 参数校验失败 | 400 | 10001 |
| 资源不存在 | 404 | 10002 |
| 资源冲突 | 409 | 10003 |
| 业务异常 | 由错误码映射（400/404/409/502…） | 对应业务码 |
| 未捕获异常 | 500 | 10000 |

因此拦截器的**主逻辑在 `error` 分支**，具体行为见 4.5。

### 3.7 概览页保留后端连接状态卡片

概览页占位中调用 `GET /health`，展示后端连通性与 AI 配置状态。

**理由**：
1. 步骤 1 验收标准含「/health 通」——需一条真实请求链路证据；
2. 这是验证 `request.js` 全链路（axios 实例 → baseURL → Vite 代理 → 拦截器 → 后端响应体）的唯一手段，代码走查看不出代理与拦截器问题；
3. 接口文档 3.1 明确 `llm_configured` 字段「供前端在概览提示未配置 AI」，概览页本就该用它；
4. 步骤 5 实现真正概览页时在此基础上扩展，非废弃代码。

### 4.2 工程配置

**依赖**（版本以安装时稳定版为准，由 `package-lock.json` 锁定）：

| 类型 | 包 |
|---|---|
| 运行时 | `vue`、`vue-router`、`pinia`、`element-plus`、`axios`、`@element-plus/icons-vue` |
| 开发 | `vite`、`@vitejs/plugin-vue` |

**`vite.config.js`**：

```js

  port: 5173,                        // 与后端 CORS 白名单一致
  proxy: {
    '/api': { target: 'http://localhost:8000', changeOrigin: true }
```

**`main.js`** 挂载顺序：Pinia → Router → Element Plus（全量引入 + `zh-cn` locale）→ mount。Element Plus 选全量引入，依据系统设计文档 4.3「项目规模下按需引入收益低，控制构建复杂度」。

### 4.3 路由与菜单

单一数据源：菜单项**从路由表派生**（`meta` 驱动），不做两份配置。

| 菜单/标题文案（`meta.title`） | path | 组件（懒加载） | `meta.icon` |
|---|---|---|---|
| 今日概览 | `/` | `Overview.vue` | `HomeFilled` |
| 投递管理 | `/applications` | `Applications.vue` | `Suitcase` |
| JD 匹配分析 | `/jd-analysis` | `JdAnalysis.vue` | `DataAnalysis` |
| 模拟面试 | `/interview` | `InterviewList.vue` | `ChatDotRound` |
| 八股陪练 | `/practice` | `Practice.vue` | `EditPen` |
| 错题本 | `/wrong-questions` | `WrongQuestions.vue` | `Collection` |
| 面经整理 | `/experiences` | `Experiences.vue` | `Reading` |
| 系统设置 | `/settings` | `Settings.vue` | `Setting` |
| —（不进菜单） | `/interview/:sessionId` | `InterviewChat.vue` | — |

菜单文案与顶栏标题**统一取 `meta.title`**（单一数据源，不做两份配置）。文案取自系统设计文档 4.1 页面列。图标名为 `@element-plus/icons-vue` 的组件名，在 `SideNav.vue` 内按需 import；若某图标名在该版本不存在，构建会报错，替换为语义相近的图标即可。

**`meta` 约定**：

| 字段 | 用途 |
|---|---|
| `title` | 顶栏标题 + 菜单文案 |
| `icon` | 菜单图标（组件引用，直接 `<component :is="...">`） |
| `hidden` | `true` 时不进菜单（`/interview/:sessionId` 用） |
| `activeMenu` | 高亮指向的菜单 path（`/interview/:sessionId` → `/interview`） |

路由懒加载（`() => import(...)`）——9 个页面均为占位，但为后续页面变大做准备。

### 4.5 请求层 `src/api/request.js`

```js
axios.create({ baseURL: '/api/v1', timeout: 30000 })
```

**响应拦截（成功分支）**：

1. `config.responseType === 'blob'` → 直通返回 `response.data`（为步骤 4 的模板下载预留）；
2. 否则返回 `response.data.data`（调用方直接拿到业务数据，无需解构 `code`/`message`）；
3. 防御性判断：若出现 `code !== 0`（当前后端不会发生，见 3.6），同样按错误处理。

**响应拦截（失败分支）**：按来源分类提示，并把业务错误码透传给调用方：

| 情况 | 提示文案 | 透传信息 |
|---|---|---|
| 超时（`ECONNABORTED`） | 请求超时，请稍后重试 | — |
| 有响应体（`error.response.data.message`） | 取后端 `message`（统一响应体的错误文案） | `bizError.code = body.code`、`bizError.httpStatus` |
| 无响应（网络不通 / 后端未启动） | 网络异常，请检查后端服务是否已启动 | — |

`ElMessage` 开启 `grouping` 合并重复提示，避免批量请求失败时刷屏。

调用方可通过 `catch (e)` 读取 `e.code` 做分支处理（步骤 7 的 10012 → 跳设置页即依赖此约定）。
