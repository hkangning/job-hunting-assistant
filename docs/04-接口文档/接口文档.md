## 1. 通用规范

### 1.1 基础约定

- Base URL：`http://localhost:8000/api/v1`（前端开发代理 `/api` → 8000 端口）
- 在线接口文档（FastAPI 自动生成，服务启动后可访问）：Swagger UI `http://localhost:8000/docs`（可交互调试，展开接口 → Try it out → Execute）、ReDoc `http://localhost:8000/redoc`（只读版）
- 数据格式：JSON（UTF-8）；文件上传 `multipart/form-data`；流式接口 `text/event-stream`（SSE）
- 时间格式：`YYYY-MM-DD HH:mm:ss`（本地时间）；日期 `YYYY-MM-DD`
- 分页：请求 `page`（从 1 起）+ `page_size`（默认 10，最大 50）；响应 `data: {total, items}`
- **鉴权**：除白名单 **`POST /auth/register`、`POST /auth/login`、`GET /health`** 三个端点外，**全部接口（含 SSE）均需携带请求头 `Authorization: Bearer <token>`**；Token 由登录/注册接口返回，有效期 = 勾选"30 天免登录"时 30 天、未勾选时 1 天；缺失/无效 → **401 + 80001**，过期 → **401 + 80002**（前端均清本地 Token 跳登录页）
- **数据隔离**：账号私有数据一律按 **Token 对应的登录账号**过滤与写入，请求体/查询参数中**不接受** `user_id`（传入亦忽略）；访问他账号资源一律返回 **404 + 10002**（与"资源不存在"完全一致，不暴露存在性）

### 1.2 统一响应体

```json
{ "code": 0, "message": "ok", "data": {} }
```

`code=0` 成功；非 0 见错误码表。SSE 接口不走此格式。

> **HTTP 状态码口径**：与 `code` **同源**——后端 `ErrorCode` 枚举以「码 + HTTP 状态码 + 默认文案」三元组绑定（`backend/app/exceptions.py`），上表逐条对齐实现；`40003`（步骤 26）、`60002`（步骤 24）两个码对应的功能尚未实现，状态码按同类码推定，实现时以此表为准。前端**判定一律以响应体 `code` 为准**，HTTP 状态码只服务于网关 / 访问日志 / 监控等中间层——mock 层请照本表取值，不再自行推断。

### 1.4 SSE 事件协议（全部流式接口通用）

```
event: start
data: {"message": "正在分析…"}                       // 连接建立后立即推送（感知延迟优化）

event: delta
data: {"text": "增量片段", "section": "match_score"}   // section 可选，标识报告段落

event: tool_call
data: {"tool_name": "create_application", "args": {...}}  // 仅 Agent 接口

event: done
data: {"record_id": 123, "extra": {...}}                  // 落库 id 与附加数据

event: error
data: {"code": 10010, "message": "..."}                   // 中途失败，已渲染内容保留
```

**实现口径**（协议层统一封装在 `backend/app/utils/sse.py`，各流式接口复用，业务侧只 `yield` 事件、不拼报文）：

| 约定 | 说明 |
|---|---|
| 报文格式 | 每个事件固定 `event: <名>\ndata: <JSON>\n\n`，`data` 为 UTF-8 JSON（中文不转义）；响应头带 `Cache-Control: no-cache` 与 `X-Accel-Buffering: no`（关闭 nginx 缓冲，避免部署到反向代理后事件被攒批） |
| `start` 时机 | **连接建立后立即推送**（进入流式处理的第一件事），先于任何 AI 调用与数据库查询，用于前端即时反馈；实测本机 5~21ms 到达 |
| 事件顺序 | 恒为 `start` → 若干 `delta`（`tool_call` 可穿插）→ `done` 或 `error` 之一收尾；`done` 与 `error` **互斥且不重复** |
| 输出节奏 | `delta` 文本经**输出节奏器**按 `SSE_PACE_CPS`（默认 **45 字/秒**）缓释：小步 1~4 字、标点后附加停顿（逗号 0.10s / 句末标点 0.18s / 换行 0.24s），把模型的块状输出平滑为连续出字观感。**只对超前等待**——上游（模型）本就慢于节奏时零额外延迟、**首字不受影响**（首个小步不等待）；**仅重排 `delta` 切分**，文本内容、事件序列与 `done` / `error` 语义均不变；**豁免段整块直通**——一次性 JSON 段（`dimensions` / `next_choices` / `tool_call` / `wrong_candidates`，保持「一个 `delta` 即完整 JSON」的段契约）与整句状态文案段（`progress`，前端覆盖式渲染、拆步会只剩零头）不拆步。**前端不得假设 `delta` 条数**——同一文本可能拆成多条小步，按拼接渲染即可；取 `SSE_PACE_CPS=0`（或负值）关闭节奏（测试环境建议关闭，避免等待拖慢用例） |
| `done` 载荷 | `record_id` 为落库记录 id（不落库的链路为 `null`），`extra` 为链路自定义附加数据（如字数 / 耗时统计）；由业务侧 `return` 提供，协议层统一收口 |
| 数据库会话 | 每个流式请求使用**独立会话**（不复用普通请求的会话），流结束即关闭 |
| 客户端断连 | 后端停止消费上游 AI 流并主动关闭与供应商的连接，**不再推送任何事件**；已渲染内容由前端保留；不视为异常、不记错误日志（仅记一条 INFO 日志便于排查）；**已生成内容按各链路约定收尾**——业务链路通常在自身清理逻辑中落半成品（JD 分析见 §3.6），不落库的链路（如 `/stream/demo`）直接丢弃 |
| 异常分派 | `BizException`（含 AI 链路四档细分，见 §1.3 注）→ 发送其 `code`；其余未预期异常 → 记录堆栈并发送 `10000`。两种情况下 `start` 与已发出的 `delta` **均不撤回** |
| 心跳 / 重连 | **不实现**——首字延迟 < 2s、链路短，且不做 `Last-Event-ID` 续传；断连即结束本次流式请求，前端需重新发起 |

前端因 `EventSource` 不支持 POST，统一使用 `fetch` + `ReadableStream` 手工解析（见系统设计 5.1 / 2.2）。

## 3. 接口详述

### 3.1 通用

**GET /health**

| 参数 | 位置 | 类型 | 必填 | 说明 |
|---|---|---|---|---|
| - | - | - | - | - |

响应：`{"code":0,"message":"ok","data":{"status":"ok"}}`。**免鉴权**，不含任何账号信息（原 `llm_configured` 字段随多账号改造移除，"是否已配置 AI"改由 `GET /auth/me` 返回，见 §3.2）。

**POST /stream/demo**（**SSE**，流式协议自检，步骤 11 起提供）

| 参数 | 类型 | 必填 | 说明 |
|---|---|---|---|
| message | string | 是 | 用户输入文本（1~500 字），原样交给当前账号的 AI 配置流式回答 |

- 用途：**开发与联调自检端点，非业务接口**——前端打字机组件（`StreamText`）在业务链路落地前用它联调渲染；测试侧用它做 SSE 协议单测（事件顺序 / 断连 / 异常路径）的靶子；
- 事件流：`start` → `delta`×N → `done`；`done.extra` 携带 `{chars, first_token_ms, elapsed_ms}`（本次输出字数 / 首 token 延迟 / 总耗时），`record_id` 为 `null`（**不落库**）；
- AI 调用走当前账号的 AI 配置（与业务链路同一出口 `llm_client`），失败按 §1.3 注的四档错误码发 `error` 事件（未配置供应商 → 10012）；
- 需携带 `Authorization`；不做业务数据隔离（无业务数据）；
- **入参校验先于流式建立**——`message` 缺失 / 空串 / 超长（>500 字）在进入流式处理**之前**即被拦下，返回的是**普通统一响应体**（`10001`，`Content-Type: application/json`），**不会**产生 `start` 事件或 SSE `error` 事件；其余失败（AI 配置缺失 / 调用失败等）发生在流式处理内，按上述事件流规则以 `error` 事件下发。前端据此区分「请求没发出去」与「流中途失败」两类提示。

### 3.2 账号与鉴权

**POST /auth/register**（**免鉴权**）

| 参数 | 位置 | 类型 | 必填 | 说明 |
|---|---|---|---|---|
| username | body | string | 是 | 登录名，3~20 位字母/数字/下划线，全站唯一（不区分大小写） |
| password | body | string | 是 | 密码，**≥6 位**（不强制字符类型） |
| nickname | body | string | 否 | 昵称，**≤50 字符**，默认取用户名（提交空串亦取用户名），可在个人中心修改 |
| email | body | string | 否 | 邮箱，**≤100 字符**，填写时校验格式且全站唯一（**不区分大小写**；为后续高级功能预留） |

响应 `data`：`{"token":"<JWT>","expires_at":"2026-09-26 12:00:00","user":{"id":1,"username":"hkn","nickname":"hkn","avatar":null,"role":"ADMIN","plan":"FREE","created_at":"..."}}`

- 注册成功**自动登录**，直接返回 Token（**有效期 1 天**，注册流程不含免登录选项）；
- 注册时自动创建该账号的画像空记录与账号级默认配置（见数据库设计 §4）；**首个注册账号 `role=ADMIN`**，其余 `USER`（本期无权限差异）；
- 用户名重复 → **80003**；邮箱被其他账号占用 → **10003**；密码 <6 位 → **80006**；长度或格式不符 → **10001**。

**POST /auth/login**（**免鉴权**）

| 参数 | 位置 | 类型 | 必填 | 说明 |
|---|---|---|---|---|
| username | body | string | 是 | 登录名 |
| password | body | string | 是 | 密码 |
| remember_me | body | bool | 否 | 勾选"30 天免登录"传 `true`（默认 `false`） |

响应 `data`：同注册（`token` / `expires_at` / `user`）。`expires_at` 按 `remember_me` 计算：**true = 30 天，false = 1 天**。

- 用户名或密码错误 → **80004**（统一文案，**不区分**用户名是否存在，防枚举）；
- 连续失败 5 次 → 锁定 5 分钟，期间即使密码正确也返回 **80005**（`message` 含剩余锁定时间）；登录成功清零计数并更新 `last_login_at`。

**GET /auth/me**

无参数。响应 `data`：

| 字段 | 类型 | 说明 |
|---|---|---|
| id | int | 账号 id |
| username | string | 登录名（个人中心只读展示） |
| nickname | string | 昵称 |
| email | string/null | 邮箱 |
| avatar | string/null | 头像相对路径，null = 用默认头像 |
| role | string | `USER` / `ADMIN` |
| plan | string | `FREE` / `PRO`（预留） |
| created_at | datetime | 注册时间 |
| last_login_at | datetime/null | 上次登录时间 |
| **llm_configured** | bool | 当前账号是否已有生效的 AI 供应商配置（false 时概览提示"未配置 AI"） |

**前端启动校验入口**：路由守卫以本接口判断本地 Token 是否仍有效（401 → 80001/80002 → 清本地 Token 跳登录页）。

**PUT /auth/profile**

| 参数 | 位置 | 类型 | 必填 | 说明 |
|---|---|---|---|---|
| nickname | body | string | 否 | 昵称，**≤50 字符**；传空串或 `null` 表示回退为用户名 |
| email | body | string | 否 | 邮箱，**≤100 字符**；格式校验 + 全站唯一（**不区分大小写**，重复 → 10003）；传空串或 `null` 表示清空 |

响应 `data`：更新后的账号信息（同 `GET /auth/me` 结构）。**用户名不可修改**。

- **部分更新语义**：只更新请求体中出现的字段（未提交的字段保持原值）；`nickname` 提交空串/`null` 回退为用户名，`email` 提交空串/`null` 置空；
- 长度超限 → **10001**；邮箱格式非法 → **10001**；邮箱被其他账号占用 → **10003**。

**PUT /auth/password**

| 参数 | 位置 | 类型 | 必填 | 说明 |
|---|---|---|---|---|
| old_password | body | string | 是 | 原密码 |
| new_password | body | string | 是 | 新密码，**≥6 位** |

- 原密码错误 → **80007**；新密码 <6 位 → **80006**；
- 成功返回 `data: null`，**当前 Token 立即失效**（含"30 天免登录"的旧 Token，再用旧 Token 请求 → **401 + 80002**）——前端收到成功后清除本地 Token 并跳登录页重新登录。

**POST /auth/avatar**（`multipart/form-data`）

| 参数 | 位置 | 类型 | 必填 | 说明 |
|---|---|---|---|---|
| file | form-data | file | 是 | 头像图片：jpg / jpeg / png / webp，**≤2MB** |

响应 `data`：`{"avatar":"uploads/avatars/1_a3f9c2d1.png"}`（相对路径，前端拼接后端地址即可直接访问，如 `http://localhost:8000/uploads/avatars/1_a3f9c2d1.png`——后端已把 `uploads/` 挂在 `/uploads` 静态路径下，前端**无需**做路径改写）。

- 前端先压缩为 **256×256** 再上传，后端**仍校验**类型与体积（不符 → 10001），并做兜底处理：Pillow 验真（非图片 → 10001）、最长边 >256 时等比缩放（只缩不放）、jpg/jpeg 且图像模式非 RGB/L 时转 RGB；
- 新头像落盘成功后再更新库并**同步删除旧文件**（同一请求内完成）；上传失败保留原头像。

**DELETE /auth/avatar**：恢复默认头像（删除自定义文件、`avatar` 置空），`data: {"avatar": null}`。

### 3.3 AI 供应商配置

**GET /llm-providers**

无参数。响应 `data`：

```json
{"active":"deepseek",
 "providers":[
   {"provider":"deepseek","name":"DeepSeek","group":"国内",
    "base_url":"https://api.deepseek.com","needs_key":true,"key_set":true,
    "model":"deepseek-flash","is_active":true},
   {"provider":"ollama","name":"Ollama（本地）","group":"本地",
    "base_url":"http://localhost:11434/v1","needs_key":false,"key_set":false,
    "model":"","is_active":false}]}
```

- 返回**注册表全部 12 项**（未配置的也在列表中，供前端渲染卡片），`group` 取值：国内 / 国外 / 聚合 / 本地 / 自定义；
- `needs_key` 为该供应商**是否需要 API Key**（注册表静态属性，`ollama` 本地部署为 `false`、其余 11 家为 `true`）。前端据此判断「免 Key 供应商」（免 Key 项无 Key 也可保存 / 激活 / 拉模型），**不要按供应商标识硬编码**——注册表新增免 Key 项时硬编码会静默失配；
- `key_set` 仅表示当前账号在该供应商下**是否已存 Key**（**永不回显明文或片段**）；`needs_key=false` 的供应商 `key_set` 恒为 false 且不影响使用；
- `model` 为该账号在该供应商下所选模型，**未选择时为空串 `""`**（= 用注册表默认模型）；`active` 为当前生效供应商标识（无则 null）。

**PUT /llm-providers/{provider}**

`provider` 为注册表标识之一（非法 → 10001）。

| 参数 | 位置 | 类型 | 必填 | 说明 |
|---|---|---|---|---|
| api_key | body | string | 否 | 密钥；**省略或留空 = 不修改已存 Key**（首次配置必填；`needs_key=false` 的供应商可空）；**传新值时旧模型缓存一并作废**（换 Key 后重新拉取，避免命中旧缓存掩盖无效 Key）；入库前 Fernet 加密 |
| base_url | body | string | 否 | 覆盖注册表默认端点（应对端点变更）；传空串 = 恢复默认 |
| model | body | string | 否 | 该供应商下所选模型 ID（候选来自模型列表接口）；传空串 = 用注册表默认模型 |

响应 `data`：该供应商的配置项（结构同 GET 列表中的单条）。约束：每账号每供应商一行（`user_id + provider` 唯一），重复保存走更新；**保存不改变当前激活项**（激活见下）；**首个保存的供应商自动生效**（账号尚无激活行时，见数据库设计 3.17）；`custom` 未填端点 → 10001。

**DELETE /llm-providers/{provider}**

删除当前账号在该供应商下的全部配置（Key / base_url / model / 模型缓存），`data: null`。**仅影响该供应商**，其余不受影响。

- 该供应商**尚未配置**（无配置行）→ **10002**；

- 若删除的是**当前激活项**，`active` 变为 null，AI 功能进入"未配置"状态（后续 LLM 调用返回 10012），前端须二次确认后提交。

**POST /llm-providers/{provider}/activate**

无请求体。把该供应商置为**当前生效**（同一事务内取消该账号其他行的激活位，保证至多一行生效），`data: {"active":"deepseek"}`。

- 切换后**立即生效**，无需重启、无需重填 Key（已存配置保留，切回即用）；
- 该供应商尚未配置 Key（`key_set=false` 且 `needs_key=true`）→ 10001，提示先填写并保存 Key。

**GET /llm-providers/{provider}/models**

| 参数 | 位置 | 类型 | 必填 | 说明 |
|---|---|---|---|---|
| refresh | query | bool | 否 | `true` = 强制重拉（默认走 24h 缓存） |
| api_key | query | string | 否 | **临时探测**的 Key（**不落库**）；省略或留空 = 用当前账号已存 Key |
| base_url | query | string | 否 | **临时探测**的端点（`custom` 必填，其余可省略）；省略或留空 = 用账号已存端点 / 注册表默认值 |

响应 `data`：`{"models":[{"id":"glm-4.7-flash","display_name":"GLM-4.7 Flash"}],"source":"remote","fetched_at":"2026-09-25 12:00:00"}`

- **传 `api_key` 或 `base_url` = 临时探测**（与 `POST /llm-providers/test` 同口径）：**不读缓存、不写缓存、不落库**，供「Key / 端点已填、尚未保存」时先看有哪些模型可选——结果属于「未保存的配置」，若写进缓存会污染已存 Key 的模型列表。**已保存的配置无需传参**（传了会绕过 24h 缓存、每次实时拉取）；
- 两个参数**均不传**时：Key 取**当前账号已存配置**；结果缓存 24h（存 `llm_provider_config.models_cache`，按 provider + base_url 维度）；**未保存过配置的供应商无处落缓存，每次实时拉取**；
- 未传 `api_key` 且该供应商**未配置 Key**（`key_set=false` 且 `needs_key=true`）→ **不报错，回退内置模型表**（`source="builtin"`）——供应商的 `GET /models` 需鉴权、无 Key 拿不到实时列表，故给内置清单，**选完供应商即可先看到可选模型**；填 Key 保存后再拉取即得全量实时列表（**保存配置、连通性测试、激活仍强制填 Key**，此处放宽只为预览，不代表可以免 Key 使用 AI 能力）。**例外**：**自定义供应商且传了 `base_url`**——自建端点是否需要 Key 由端点本身决定（本地 LM Studio / vLLM / 内网网关通常不校验），注册表静态属性判不了，故无 Key 时以占位值发出请求；端点确实要求鉴权则回 **10013**；
- 未传 `base_url` 且 `custom` 未填端点 → 10001；
- `source="builtin"` = **内置模型表**（`fetched_at` 为 `null`，非缓存结果），两种来源均**不报错**：①**未配 Key** 的预览清单（前端标注"内置清单（填写 Key 后拉取完整列表）"）；②**拉取失败**（网络不通等非鉴权类失败的回退，前端标注"内置列表（上次拉取失败）"）；
- 已存 Key 或传入的临时 Key 无效 → **10013**（鉴权类失败**不回退**内置表，否则会掩盖 Key 配置错误）；
- 远程拉到的模型**跨供应商查内置模型表**补展示信息——模型 ID 全局唯一，经聚合 / 自定义供应商调用的已知模型（如 `glm-4.7-flash`）同样能拿到中文展示名；内置表未记载的新模型以 ID 原样展示。

**POST /llm-providers/test**

| 参数 | 位置 | 类型 | 必填 | 说明 |
|---|---|---|---|---|
| provider | body | string | 是 | 待测供应商（注册表标识） |
| api_key | body | string | 否 | 待测 Key；**省略则用当前账号已存 Key**（均不落库、不改配置） |
| base_url | body | string | 否 | 同 PUT 语义（`custom` 必填） |
| model | body | string | 否 | 待测模型，缺省用注册表默认 |

行为：向供应商发送一条最小消息验证连通性（**不落库、不保存配置**）。成功 `data: {"message":"ok","model":"实际模型名"}`；失败 **10013**，`message` 携带具体原因（Key 无效 / 网络不通 / 模型不存在）；`provider` 非法 → **10001**，未配置 Key 且请求未传 → **10012**（**与 `models` 的免 Key 豁免同口径、但不回退内置表**：自定义供应商传了 `base_url` 时以占位值试连，端点真要鉴权则回 10013；其余供应商缺 Key 直接 10012 引导去填——连通性测试测的就是 Key 与端点，缺 Key 测不出所以然）。

> `api_key` / `base_url` 的取值口径与 `GET /llm-providers/{provider}/models` 的**临时探测参数**一致（传值优先、省略用已存配置）——两个探测接口同口径，前端可统一按「表单当前值优先、留空回落到已存配置」构造请求。

| **match_reminder_count** | int | **命中订阅的未读提醒数**（`reminder_type=INFO_MATCH` 且未读）——供概览「校招情报摘要」区块的计数展示 |
| **stats** | object | **个人中心数据概览**：`{application_count, wrong_question_count, interview_count}`——当前账号的投递数 / 错题总数 / 模拟面试会话数 |

- `stats` 三个计数均按**登录账号**统计（以登录态过滤），跨账号互不可见，供个人中心数据概览卡片展示；其中 `stats.wrong_question_count` 为**错题总数**，与顶层 `wrong_question_count`（**到期未复习**数，供提醒用）语义不同，二者不可混用；
- `campus_events` / `top_job_postings` / `match_reminder_count` 三项供概览「校招情报摘要」区块使用（SRS §3.1 第 5 条）：宣讲会/双选会与岗位**一并在本接口返回**，前端无需再并发调用 `/campus-events` 与 `/job-postings`；`top_job_postings` 与 `/job-postings` 共用同一打分与隔离口径（公共岗位 + 本账号投喂）；

- **区块判定口径**（步骤 9 实现细则，供前端理解与用例对齐）：① `upcoming_events`——状态非 `CLOSED` 且 `next_event_at` 落在**当前时间起 7 日内**（已过时点不再展示），按时间升序；② `follow_ups`——状态仍处 `APPLIED` / `WRITTEN`、投递日期距今**满 3 天**、且**未安排未来的笔试/面试**（`next_event_at` 为空或已过；已安排下一步的视为有进展，不出现在此列表），`days` = 投递日期距今天数，按 `days` 降序；③ 顶层 `wrong_question_count`——`next_review_at ≤ 当前时间` 且未掌握（`mastered_at` 为空），已掌握的错题不计入；④ `application_stats` 与 `stats.application_count` 均统计**全部状态**（含已结束）。

### 3.6 JD 匹配分析

**POST /stream/jd-analysis**（SSE）

| 参数 | 类型 | 必填 | 说明 |
|---|---|---|---|
| jd_text | string | 条件必填 | JD 原文（≤10000 字）；**传 `application_id` 时可省略**——自动取该投递已填的 `jd_text`；两者都取不到 → 10001 |
| application_id | int | 否 | 关联投递记录 |

事件流：`delta`（section 依次为 `match_score/scores/strengths/gaps/advice`）→ `done`（`record_id` = jd_analysis_report.id；`extra` 携带 `{chars, first_token_ms, elapsed_ms}`，口径同 `/stream/demo`）。用户中途断开：已生成内容落库并标记为**未完成**（`is_finished=false`）。

**实现口径**：

| 约定 | 说明 |
|---|---|
| 校验先于流式建立 | `application_id` 不存在或非本人所有 → **404 + 10002**；**解析后的 JD 原文**为空或超 10000 字 → **400 + 10001**（未传 `jd_text` 时取该投递已填的 `jd_text`，投递未填且未传 → 同样 10001）。两类校验都在流式响应建立**之前**完成，按**普通响应体**返回，不产生 SSE 事件 |
| 画像为空 | **不阻塞**：画像未填写时照常分析，prompt 中标注「尚未填写画像」，由 AI 改按 JD 自身与常见岗位要求判断 |
| `section` 语义 | 仅为**段落锚点**，供前端分段定位/折叠；段落标题行本身**随 `delta` 原样下发**，故 `report_text` 恒等于全部 `delta` 的拼接（含标题行）。AI 输出未按模板给出标题时**沿用当前 `section`**；全程识别不出标题则不下发 `section` 字段（纯文本降级，前端按无锚点渲染） |
| `score` 提取 | 从报告文本匹配「综合匹配度：XX」——兼容全角/半角冒号与 markdown 加粗；取不到或不在 0~100 范围记为 `null` |
| 中途失败 | 发 `error` 事件（AI 链路四档见 §1.3 注），**不落库**：失败报告不保留，前端重新发起即重跑。**上游流被截断**（IS-56，流结束未收到 `finish_reason`）计入本行——按 10010 报错、已生成内容**不落库**（与下行「客户端断开」的落半成品相反：那是客户端主动断开、已生成部分有效；截断源自上游故障，统一走失败口径、重发即重跑） |
| 客户端断开 | 与"失败"不同——已生成内容**原样落库**并标记 **`is_finished=false`**（落库文本 = 断开前已下发的全部 `delta` 拼接，与完整报告同一口径，前端无需二次处理）；前端**据此识别「未完成」**，不再用 `score` 是否为空推断（断点落在评分行**之后**时 `score` 已有值、判据失效）；前端重新发起即再次分析，一条内容都没生成时不落库 |

**GET /jd-reports**（query：application_id 可选、page、page_size）

items：`[{id, application_id, company, score, is_finished, created_at}]`（company 取自关联投递联表，未关联或投递已不存在时为 `null`）。

- 排序：按生成时间 `created_at` 倒序，同一秒内按 `id` 倒序（新旧稳定可辨）；
- 分页：`page` 从 1 起，`page_size` 默认 **10、最大 50**（越界 → 10001）；
- `application_id` 筛选只在本账号记录内匹配，查无结果返回空列表（不报错）。

**GET /jd-reports/{id}**：`data:{id, application_id, jd_text, report_text, score, is_finished, created_at}`。不存在或不属于当前账号 → **404 + 10002**（两种情形均返回同一错误码，不可区分）。

**字段说明**：`is_finished` —— 报告是否完整生成：`true` 正常完成 / `false` 客户端断连的半成品（**内容不全**）。列表项与详情均返回该字段，前端据此显示「未完成」标记（**不要**改用 `score` 是否为空推断）。

### 3.7 AI 模拟面试

**POST /interview-sessions**

| 参数 | 类型 | 必填 | 说明 |
|---|---|---|---|
| application_id | int | 否 | 关联投递（有则 company/position 从中带入） |
| company / position | string | 条件必填 | 未传 application_id 时两者必填 |
| direction | string | 否 | 面试方向，默认 `GENERAL`（不限方向）；也可取任一领域枚举值（如 `JAVA` / `REDIS`）做专项面试 |
| question_count | int | 否 | 题量 3~15，默认 8 |
| intensity | string | 否 | 面试强度（`LARGE` 大厂 / `MEDIUM` 中厂 / `SMALL` 小厂），默认 `MEDIUM`；决定出题深度、追问力度与评分严格度（见下「面试强度」） |

**题源范围（本版）**：出题上下文取两类——传 `application_id` 时以该投递的**公司 / 岗位 / JD 原文**（JD 取自投递记录的 `jd_text`，截断注入，控制 token）为背景；未传时按公司 / 岗位自述 + `direction` 在对应领域内随机出题。**画像经历题源已随面试阶段化启用**——画像已填写经历条目（§3.12）时，项目深挖阶段注入经历条目作为提问依据（见下「面试阶段化」）。需求规格说明书 FR-007 题源表中的**错题本 / 面经 / 自定义**三类**列为后续增强**（涉及创建参数与出题链路扩展，实施时另行补充契约），本版无对应参数。

响应：`data = session DTO`：

```json
{"id":1,"application_id":1,"company":"浩鲸科技","position":"Java 开发",
 "direction":"JAVA","question_count":8,"intensity":"MEDIUM",
 "stages":[{"stage":"INTRO","count":1},{"stage":"TECH","count":5},{"stage":"PROJECT","count":2}],
 "status":"ACTIVE","summary":null,
 "created_at":"...","finished_at":null}
```

**GET /interview-sessions**（query：status 可选、page、page_size）：`data = {items, total}`，按 `created_at` 倒序（同秒按 `id` 倒序）：

```json
{"total":3,"items":[{"id":1,"application_id":1,"company":"浩鲸科技","position":"Java 开发",
  "direction":"JAVA","question_count":8,"intensity":"MEDIUM",
  "stages":[{"stage":"INTRO","count":1},{"stage":"TECH","count":5},{"stage":"PROJECT","count":2}],
  "status":"ACTIVE","summary":null,
  "created_at":"...","finished_at":null,"qa_count":5}]}
```

`qa_count` = 已落库问答条数（含尚未作答的当前题），供列表显示进度（`qa_count/question_count`）。

**面试阶段化**：一场面试按 **自我介绍 → 技术问答 → 项目深挖** 三段推进，阶段计划在建会话时算好、随会话 DTO 的 `stages` 数组下发（按数组顺序推进，`count` 为该段题量）：

| 阶段 | 题量 | 说明 |
|---|---|---|
| INTRO | 1 | 自我介绍（开场固定 1 题） |
| TECH | 总题量 − 1 − 项目深挖段题量 | 技术问答（主体，八股与原理） |
| PROJECT | `min(4, max(1, 题量 ÷ 4 四舍五入))`，**仅画像已填写经历条目时启用** | 项目深挖（据画像经历条目提问，不问经历里没写过的项目） |

- 每题的阶段在落库时记入 `interview_qa.stage`（`INTRO` / `TECH` / `PROJECT`）；出题与点评的 prompt 按当前阶段分派（自我介绍侧重经历自述、技术问答出八股与原理、项目深挖据画像经历追问）；
- **画像无经历条目不设项目深挖段**（`stages` 仅 INTRO + TECH 两段，自我介绍 1 题 + 技术问答余量）——没有项目素材可问；
- **阶段化上线前创建的老会话** `stages` 为 `null`（前端降级为「第 N/M 题」不显示阶段标签），其新题按技术问答处理（经历回填后的续答同样不补阶段计划）。

**面试强度**：建会话时选择，随会话固定、**不可中途更改**（换档请新开一场）。三档的差异体现在**出题深度、追问力度与评分严格度**：

| 强度 | 取值 | 侧重 |
|---|---|---|
| 大厂 | `LARGE` | 偏原理与系统设计，追问更深（如「为什么这么设计、换一种会怎样」），评分更严 |
| 中厂 | `MEDIUM` | 兼顾原理与工程实操（默认档） |
| 小厂 | `SMALL` | 偏基础与实用性，以「能用对、讲得清」为准，追问浅、评分宽 |

`intensity` 字段随会话 DTO 下发；**强度上线前创建的老会话**该字段按 `MEDIUM` 兜底下发（不返回 `null`）。

**GET /interview-sessions/{id}**：session DTO + `qa_list`（按 `seq` 升序，含尚未作答的当前题）：

```json
{"id":1,"seq":1,"question":"...","answer":"...","is_voice":1,
 "voice_metrics":{...},
 "score":8,"review":"...","skipped":0,"created_at":"..."}
```

`voice_metrics` 为表达力指标快照（结构见数据库设计 §3.19），**语音作答且算出指标（`quality=OK`）时下发**——回看页据此复现指标卡片；非语音作答 / 作答过短 / 阶段化之前的存量文字作答为 `null`。

**POST /stream/interview-chat**（SSE）

| 参数 | 类型 | 必填 | 说明 |
|---|---|---|---|
| session_id | int | 是 | 会话 id |
| answer | string | 否 | 本题作答；**空串 = 请出当前该出的题**（首题开场 / 续出下一题 / 重发未答题，见实现口径 3） |
| skip | bool | 否 | true=跳过当前未作答的题（不计分，直接下一题） |
| segments | array | 否 | **语音作答时必传**（步骤 25 已启用）：前端 VAD 分句时间轴 `[{seq, start_ms, end_ms, text}]`（见 §3.13），供后端计算表达力指标（口径见实现口径 7）；文字作答不传 |

事件流：`delta`（section 依次 `review` → `next_question`；**开场轮与跳过轮只有 `next_question`，答满题量轮只有 `review`**）→ `done`（`record_id` = 本轮新落 `interview_qa.id`；`seq` = 本轮内容对应题序（前三种轮次即新题 seq，答满轮为最后一题 seq）；**语音作答且已算出指标时** `extra:{voice_metrics:{...}}`，字段结构见数据库设计 §3.19；**答满题量时** `extra:{session_finished:true}`，前端引导生成总结）。

**实现口径**（步骤 15 落地）：

1. **一轮一次性落库**——点评与下一题**全部生成完、流正常结束**后才写库（本轮作答补全 + 点评 + 新题同一事务）；**断连或中途失败不落任何记录**，前端重试即重发本轮（整轮重新生成，不会产生重复条目）；
2. **校验先于流式建立**——会话不存在 / 不属于当前账号 → **404 + 10002**；会话已结束 → **409 + 40001**；`skip=true` 但当前无未作答的题 → **400 + 10001**；**`answer` 非空但当前无待作答的题**（如上一轮流中断后携带旧答案重试）→ **409 + 40001**；**`skip` 与 `answer` 同时提交** → **400 + 10001**；以上均为**普通 JSON 响应体**，在 SSE 建立之前返回（前端需按普通响应处理，不会收到 `error` 事件）；
3. **空 `answer` 的语义 = 请出当前该出的题**——新会话（0 条问答）出首题；存在**未作答**的题则按该题原样重发（`next_question` 段，不新建条目，断线重试安全）；全部已答且未满题量则生成下一题；已满题量的会话已置 `FINISHED`，走第 2 条的 40001；
4. **跳过轮**——只生成下一题（**不出点评**）；被跳题 `skipped=1`、`answer` 空、`score` 空；跳过最后一题时无下一题，直接结束（同第 5 条）；
5. **答满题量**——最后一轮 `review` 后 `done.extra.session_finished=true`、不再出下一题，同事务将会话置 **`FINISHED`**（此后作答 / 跳过一律 40001）；总结生成走本组 `POST /stream/interview-summary`（已落地，见下）；
6. **切段格式**——模型输出以 `## 点评` / `## 下一题` 标题行分节，标题行随 `delta` 原样下发；`section` 仅作分段锚点，落库文本恒等于对应段的 `delta` 拼接（点评落 `review` 列、下一题落新条目题干列）。**首个标题行出现前的内容（模型寒暄或未按格式输出）整段丢弃**——既不下发也不落库；**防御模型越轮输出**：**答满题量轮**多输出的下一题段整段丢弃、**出题轮（开场 / 跳过 / 续出）**多输出的点评段整段丢弃（保证本节开头「哪些轮次有哪些段」的契约恒成立）。模型未产出本轮必需的段（出题轮无 `next_question`、作答轮无 `review`、非答满轮无 `next_question`）→ 建流后以 `error`（**10011**）结束、**本轮不落库**（落库只在流正常结束后一次性执行，见口径 1）。

7. **表达力指标（步骤 25 落地）**——`segments` 是表达维度的唯一数据来源（句间停顿只有前端知道，见 §3.13）：收到后由**纯函数**计算（零 token、即时返回，设计见系统设计 5.7），产出五项指标（语速 / 填充词密度 / 停顿点 / 有效时长占比 / 流畅度趋势）+ 基础量与 `quality` 标记。分派口径：
   - `quality=OK`——注入点评 prompt（模型结合指标与作答原话点评表达表现）、随 `done.extra.voice_metrics` 下发、整轮落库，**回看经详情 `qa_list` 的 `voice_metrics` 字段复现**；
   - `quality=TOO_SHORT`（作答总时长不足 10 秒）与不传 `segments` 的 `TEXT_ONLY`——**不产出表达维度**（不注入 prompt、不下发、不落库），内容点评照常；
   - `is_voice` 以**是否随作答传 `segments`** 为准（传空数组也记 1，被跳过的题不记）；指标只落本题（质量未达标时列空），`version` 供算法口径变更后识别旧数据。

**POST /stream/interview-summary**（SSE）

| 参数 | 类型 | 必填 | 说明 |
|---|---|---|---|
| session_id | int | 是 | 会话 id（须属当前账号；**0 条已完成问答亦可**，见实现口径 7） |

事件流：`delta`（section=`summary`；正文之后**可能**跟一段 `wrong_candidates`——一次性 JSON 的错题候选）→ `done`（`record_id`=session.id，会话置 FINISHED）。重复调用返回已有 summary（不重复计费）。**0 条已完成问答**时同样走 `start → delta → done`，`delta` 为固定说明文案（见实现口径 7）。

**错题候选段**（`section=wrong_candidates`，可选）：正文流完后，若模型从点评的「不足」中提取出具体八股知识点，追加一段**一次性 JSON**（`data.text` 即完整 JSON 字符串，不拆步；该段**可缺席**，前端不得依赖其存在）：

```json
{"candidates":[{"content":"JVM 垃圾回收的分代模型","answer":"……参考答案要点……","direction":"JVM"}]}
```

| 字段 | 类型 | 说明 |
|---|---|---|
| content | string | 知识点题干（非空，≤2000 字） |
| answer | string | 参考答案要点（非空，≤5000 字） |
| direction | string | 领域枚举（§3.8 `/practice/meta` 下发的 18 个领域值 **+ `GENERAL`（通用）**，共 19 选 1；`GENERAL` 不在 meta 列表中，前端渲染时给「通用」兜底文案） |

**0~5 条**（宁缺毋滥，无从提取时整段不出）。前端渲染为候选卡片，**用户逐条确认**后调 `POST /wrong-questions`（知识点形态，`source_type="INTERVIEW"`，见 §3.9）入错题本；返回 **10003** 表示该知识点已在错题本（属正常结果，前端宜渲染为非错误态）。

**实现口径**（步骤 16 后端部分落地）：

1. **校验先于流式建立**——会话不存在 / 不属于当前账号 → **404 + 10002**（**普通 JSON 响应体**，在 SSE 建立之前返回）；0 条已完成问答**不再拒绝**（IS-63：未作答的会话同样要能结束，见第 7 条）；
2. **进行中的会话同样允许生成**——「提前结束本场」即调用本端点生成总结并把会话置 `FINISHED`，**不要求答满题量**；总结覆盖已作答（含跳过）的全部轮次；
3. **已有总结直接回放**——直接以 `delta`（section=`summary`）重发已存文本、**不调用模型**（重复调用不重复计费），`done.record_id` 仍为该会话 id；
4. **正文段 section 恒为 `summary`、不切段**——正文为单段文本，模型未按任何格式输出也整段照发（与 `/stream/interview-chat` 的切段链路不同，无「标题行前内容丢弃」逻辑）；输出为空 → 建流后以 `error`（**10011**）结束。唯一例外是末段「`## 错题候选`」标题行——出现时其后的内容切入 `wrong_candidates` 段（见第 6 条）；
5. **全文随流落库**——落库的 `summary` 列即 `delta` 拼接（**不含候选段**），同事务将会话置 `FINISHED` 并记录 `finished_at`；**断连或中途失败不落库**（与 `/stream/interview-chat` 同口径，重试即重新生成）；
6. **错题候选段（失败静默降级、不落库、回放不含）**——①切段：「`## 错题候选`」标题行及其后内容**整段缓冲**，标题行与 JSON 均不下发、标题行不落库；正文段（标题行前）照常边流边发；②校验：JSON 经容错解析（容忍 ```json 围栏与前后杂文）→ **逐条校验**（`content` / `answer` 非空且不超长、`direction` 合法，**不合格的条目单独丢弃、不影响其余**）→ 按 `content` 去重 → 取前 5 条；校验后仍有条目即**一次性下发**（`section=wrong_candidates`）；③降级：候选段缺席 / JSON 不可解析 / 校验后一条不剩 → **静默跳过**（不报错、不发该段，仅记服务端日志），正文照常落库；④**候选不落库**——仅随本次流下发，故**已有总结的回放（第 3 条）不含候选段**，前端刷新 / 重新打开总结页时无候选卡片属预期；⑤**下发在落库之前**——候选段发完才写库；候选段处断连与正文段断连同口径（不落库、重试重新生成）。
7. **0 条已完成问答 = 落固定说明文案、不调模型**（IS-63 方案 A）——会话没有任何「已作答或已跳过」的轮次（含一种边界：**已出过题但一题未答**，其未作答条目不计入）时，不调用模型，直接以 `delta`（section=`summary`）下发固定文案「**本场未作答任何题目，无内容可总结。**」，同事务将文案写入会话 `summary` 并置 `FINISHED`、记录 `finished_at`；该分支**不依赖账号 AI 配置**（未配 Key 同样可用）、候选段自然缺席、`done.record_id` 同第 3 条（回放走第 3 条、回放同文案不调模型）。**动因**：未作答的会话此前无法结束（前端「结束本场」被本端点 400 拦住、会话卡在进行中）。

### 3.8 八股陪练

一场训练 = 一个**训练会话**（`POST /practice/sessions` 开出），每轮作答与点评走同一个流式端点（`POST /stream/practice-turn`），完成后结算（`POST /practice/sessions/{id}/finish`）。历史与掌握度各有查询接口。

**五种训练模式**：

| 模式 | 标识 | 玩法 | 轮次 | 通过判据（未通过即入错题本） |
|---|---|---|---|---|
| 快练 | `QUICK` | 一题一答一评，无追问（与原有形态一致） | 1 轮 | 评分 ≥ 6 |
| 面试官深挖 | `INTERVIEWER` | 顺着作答往下追，答不上**不打断**、记断点后继续追 | 1 + N（N ≤ 4） | 综合分 ≥ 6 **且**断点 < 2 |
| 教练引导 | `COACH` | 答不上**先给方向性提示**（不给答案），带到能自己说出来 | 1 + N（N ≤ 4，含提示轮） | 同面试官深挖 |
| 挑错纠错 | `DEBUG` | AI 给一段「听着顺但有雷」的答案，用户找错 | 1~2 轮材料与找错 | 找雷命中率 ≥ 60% |
| 费曼复述 | `FEYNMAN` | 不给提示，用自己的话讲一遍，AI 挑漏洞并追问 | 1 + 0~2 轮 | 关键漏洞 < 3 条 |

**追问链**（`INTERVIEWER` / `COACH`）按四层**攻击面**逐层深挖，每层只问一个问题、优先追参考答案里用户尚未答到的关键点；追满 4 层、判定已无深可挖、或用户主动结束——任一即止，**不硬凑层数**。

**GET /practice/meta**（无参数）

抽题筛选面板与模式选择的数据来源，避免枚举在前端硬编码：

```json
{"stacks":[{"value":"JAVA_BACKEND","label":"Java 后端",
            "domains":[{"value":"JAVA","label":"Java 基础"},{"value":"JVM","label":"JVM"}]}],
 "positions":[{"value":"JAVA","label":"Java 岗位","stacks":["JAVA_BACKEND","BACKEND_COMMON","COMMON"]}],
 "qtypes":[{"value":"SUBJECTIVE","label":"问答型"},{"value":"CHOICE","label":"选择题"},{"value":"SCENARIO","label":"场景题"}],
 "modes":[{"value":"QUICK","label":"快练","description":"一题一答一评，没有追问","max_rounds":1},
          {"value":"INTERVIEWER","label":"面试官深挖","description":"追到你答不上来，看你的知识边界在哪","max_rounds":5},
          {"value":"COACH","label":"教练引导","description":"答不上时先给提示，带到你能自己说出来","max_rounds":5},
          {"value":"DEBUG","label":"挑错纠错","description":"给你一段听着顺但有雷的答案，你来挑错","max_rounds":2},
          {"value":"FEYNMAN","label":"费曼复述","description":"不看答案用自己的话讲一遍，AI 挑漏洞","max_rounds":3}],
 "faces":[{"value":"BASIS","label":"依据","layer":1,"hint":"为什么这么做、原理是什么"},
          {"value":"BOUNDARY","label":"边界","layer":2,"hint":"什么情况下会失效、挂了怎么办"},
          {"value":"TRADEOFF","label":"取舍","layer":3,"hint":"为什么不用另一种方案、代价分别是什么"},
          {"value":"LANDING","label":"落地","layer":4,"hint":"具体到你的项目怎么配、量级多少、怎么验证"}],
 "time_limits":[30,60,90,120]}
```

- `stacks`：5 个技术栈，各自带下辖领域（两级筛选的第一级）；
- `positions`：岗位视角 = 若干栈的并集，前端把岗位展开成 `stacks` 数组后传给抽题接口，**后端不感知"岗位"概念**；
- `qtypes`：题型清单，供筛选项与场景题标识使用；
- `modes`：五种训练模式的清单（`label` / `description` 直接展示在模式选择卡片上；`max_rounds` 为**作答轮数上限**，供前端显示「第 2/5 轮」的进度）；
- `faces`：追问链的四层攻击面（`layer` 为层号 1~4，`hint` 为该层追什么），供前端渲染「第 2 层 · 边界」的追问进度——**层号与攻击面固定一一对应**（见数据库设计 §5）；
- `time_limits`：限时档位（秒）。**不传限时即不限时**；本数组为全量可选值，不做账号级配置。

**POST /practice/questions**

| 参数 | 类型 | 必填 | 说明 |
|---|---|---|---|
| stacks | array | 否 | 技术栈数组（可多选），元素为 `Stack` 枚举值；不传 = 不限栈 |
| directions | array | 否 | 领域数组（可多选），元素为 `Direction` 枚举值；不传 = 不限领域 |
| qtypes | array | 否 | 题型数组，元素 `SUBJECTIVE`/`CHOICE`/`SCENARIO`；不传 = 不限题型 |
| mode | string | 否 | 训练模式（枚举值），用于**排除与该模式不搭的题型**——`DEBUG`（挑错）/ `FEYNMAN`（费曼）**不出选择题**；不传 = 不限模式、不做排除；非法值 → 10001 |
| count | int | 否 | 抽题数，默认 1，最大 5 |
| strategy | string | 否 | 选题策略：`SMART`（默认，薄弱优先）/ `RANDOM`（纯随机）；非法值 → 10001 |

- 三个筛选条件为**与**关系：栈限定范围、领域进一步细化、题型再收窄；全部不传即全库随机；
- 命中题目不足 `count` 时按实际数量返回（不报错）；
- **`strategy=SMART`**（默认）按 `(100 - 该题所属领域当前掌握度) / 50 × 练习历史系数` 加权随机抽样——**掌握度越低的领域越容易被抽到**；练习历史系数为「练过的题 0.3 / 未练过的题 1.0」，即**练过的题权重下调但不清零、未练过的题有保底权重**，避免"反复出同一道题"与"一直看不到新题"两个极端。`RANDOM` 为纯随机，保留作为对照（让用户感受差异）。

响应：`data:{items:[{id, stack, direction, content, qtype, mastery, options}]}`。注意：**不含 answer**（防止先看答案）；`SCENARIO` 题的 `rubric` 同样不下发。

- `mastery`：该题所属领域的**当前掌握度**（整数 0~100，账号在该领域无练习记录时为 0），供前端标注「这是你的弱项」；
- `options`：**选择题选项数组**，`[{key, text}]`（如 `[{"key":"A","text":"可重复读（REPEATABLE READ）"}, ...]`）；**仅 `qtype=CHOICE` 有值**，其余题型为 `null`。数组**不含正确标记**（正确项只在服务端），可安全下发直接渲染为可点选项——前端**不必**把选项拼进题干，也不必自行判断对错。

**POST /practice/sessions**

开一场训练。

| 参数 | 类型 | 必填 | 说明 |
|---|---|---|---|
| question_id | int | 是 | 题目 id（来自抽题接口） |
| mode | string | 是 | 训练模式，`PracticeMode` 五值之一；非法 → 10001 |
| time_limit | int | 否 | 每轮限时秒数（30 / 60 / 90 / 120）；不传 = 不限时；非档位值 → 10001 |

响应：`data:{session_id, question_id, mode, status, time_limit, round_index, started_at}`——`status` 恒为 `RUNNING`、`round_index` 恒为 `1`（第一轮尚未作答）。

- **纯落库、零 LLM 调用**——开一场训练不消耗 token，第一轮内容由 `practice-turn` 产出；
- 同一道题可开多场，会话之间互不影响（历史记录因此是「同题的多场训练」而非「同题的一条记录」）；
- **选题与模式搭配校验** = 抽题接口的 `mode` 参数是**前置过滤**（服务端据此排除），本接口再兜底一次：`DEBUG` / `FEYNMAN` 配选择题 → 400 + 10001（抽题时漏传 `mode` 或客户端自行换题时兜住，不让不搭的组合开起来）。

**POST /stream/practice-turn**（SSE）

**每轮统一入口**——首次调用即「初始作答」，之后为追问轮 / 提示轮 / 复述轮 / 找错轮。`QUICK` 模式即「只有一轮的会话」，点评链路完全同一套。

| 参数 | 类型 | 必填 | 说明 |
|---|---|---|---|
| session_id | int | 是 | 会话 id；不存在或不属于当前账号 → 404 + 10002（不可区分） |
| user_input | string | 否 | 本轮作答；`action=HINT` 与 `DEBUG` 取材料时不需要。**选择题的各作答轮（首轮与追问轮）**传**选项标识**（如 `"B"`），不传选项文本 |
| action | string | 否 | `SUBMIT`（默认）/ `HINT`（求提示）/ `END`（主动结束本场）；非法 → 10001 |
| elapsed_ms | int | 否 | 本轮耗时毫秒（限时模式由前端计时上报，供复盘） |
| timed_out | bool | 否 | 是否超时自动提交，默认 `false` |

**入参校验先于流式建立**：`session_id` 无效 → 404 + 10002；`action` 非法、**会话已是终态（`FINISHED` / `ABORTED`）仍提交** → 400 + 10001——三者均按**普通响应体**返回，不产生 SSE 事件（沿用 §3.6 同口径）。

事件流：`start` → 若干 `delta` → `done`。

`delta` 的 `section` 按**时机**分流：

| section | 出现时机 | 形态 |
|---|---|---|
| `round_score` | 每轮点评的首个 section | 流式（本轮评分 + **承接作答原话**的一句自然评语，不用判词式开场） |
| `review` | 每轮 | 流式（与用户答案的**具体差距点**） |
| `dimensions` | 场景题（沿用既有口径，见下方） | 一次性 JSON |
| `hint` | 求提示时 / 教练模式降级给提示时 | 流式（**只给方向不给答案**） |
| `material` | `DEBUG` 模式给带错答案时 | 流式（一段「听着顺但有雷」的候选人答案） |
| `next_question` | 需要继续追问时 | 流式（下一问，**一次只问一个**） |
| `next_choices` | 选择题的追问轮、且该问**有唯一答案** | 一次性 JSON（下一轮的可点选项，**不含正确项**，见下方） |
| `summary` | 本场最后一轮 | 流式（整场一句话总结 + 该补什么） |
| `reference_answer` | **仅 `QUICK` 模式** | 流式（其余模式的参考答案推迟到结算，见「实现口径」） |

**每轮的实际序列**（按模式与时机）：

| 时机 | section 序列 |
|---|---|
| `QUICK`（唯一一轮） | `round_score` → `review` →（场景题插 `dimensions`）→ `reference_answer` |
| `INTERVIEWER` / `COACH` 中间轮 | `round_score` → `review` →（场景题插 `dimensions`）→ `next_question` |
| `COACH` 提示轮 | `hint` |
| `FEYNMAN` 复述轮 | `round_score` → `review` →（有漏洞时）`next_question` |
| `DEBUG` 给材料轮 | `material` |
| `DEBUG` 找错轮 | `round_score` → `review` |
| **选择题作答轮**（`CHOICE`，首轮与追问轮同形） | `round_score`（评分 + 对错）→ `review`（正确选项 + 解析），**零 token 即时产出**（不调 LLM） |
| **选择题的追问轮**（下一轮可点选时） | 上面一行之后接 `next_question` → **`next_choices`**（选项数组，一次性 JSON）；某一轮模型造不出唯一答案则**无 `next_choices`**，下一轮回到开放作答序列 |
| **本场最后一轮** | `round_score` → `review` →（场景题插 `dimensions`）→ `summary` |

`next_choices` 为**一次性 JSON**（非流式增量）：

```json
{"options":[{"key":"A","text":"快照读不会阻塞写入"},{"key":"B","text":"插入意向锁与间隙锁冲突"},{"key":"C","text":"事务隔离级别降到读已提交"}]}
```

- **只有 `options`**——每项含 `key`（从 `A` 起连续）与 `text`；正确项与解析**留在服务端**，与抽题响应同口径（前端拿不到答案）；
- 项数 3~4、键从 `A` 起连续；模型输出不合法（项数不对 / 键不连续 / `answer` 越界 / JSON 坏）时**整段不下发**——前端按「本轮有无选项」自动切回文本框（与首轮同一套判断），无需特判；
- 下一轮提交时**照样传选项标识**（与首轮同形），服务端按上一轮下发的选项判定。

`dimensions` 为**一次性 JSON**（非流式增量），四个维度为场景题的评分标尺：

```json
{"framework":8,"quantification":5,"tradeoff":7,"fallback":6}
```

- 四项含义：**解题框架** / **量化估算** / **取舍权衡** / **兜底降级**，各 0~10 分，缺项按 0 计；
- 展示口径：前端按四项分项 + **总分**（`round_score` 给出的评分）呈现，参考框架（`reference_answer`）**是参考不是标准答案**。

`done` 事件：`{record_id, extra}`。

| 字段 | 说明 |
|---|---|
| `record_id` | 本轮 `practice_record.id` |
| `extra.should_finish` | 本场是否**该结算了**（最后一轮 / 主动结束）——前端据此调 `finish` |
| `extra.layer` / `extra.face` | 下一轮的**层号与攻击面**，供前端渲染「第 2 层 · 边界」的追问进度；**无下一轮时为 `null`** |

**POST /practice/sessions/{id}/finish**

结算（路径参数 `session_id`，无请求体）。

响应结构：

```json
{"session_id":12,"mode":"INTERVIEWER","question_id":88,"overall_score":6,"passed":false,
 "rounds":[{"index":1,"kind":"OPENING","score":7,"is_break":false}],
 "break_face":"BOUNDARY","hint_count":1,
 "reference_answer":"……","gaps":["未提及缓存击穿的兜底","没给出量级估算"],
 "mastery_delta":{"direction":"REDIS","before":42,"after":38},
 "wrong_question_id":31}
```

| 字段 | 说明 |
|---|---|
| `overall_score` | 整场综合分 0~10：各轮评分聚合，**不含提示轮与材料轮**（二者无评分）；**零轮结算（一场未作答）为 `0`**、不返回 `null`（`null` 仅用于**未结算**的会话） |
| `passed` | 是否通过：按各模式的通过判据判定（见本节首表） |
| `rounds[].is_break` | 该轮是否记为**断点**（答不上 / 教练模式下提示后仍答不出；限时内一字未写亦计） |
| `break_face` | **首个**断点所在层级（`BASIS` / `BOUNDARY` / `TRADEOFF` / `LANDING`）；全程无断点为 `null` |
| `hint_count` | 本场求提示次数 |
| `reference_answer` | 完整参考答案（**追问模式在此才给**） |
| `gaps` | 相对参考答案的**缺口清单**：从各轮点评汇总（服务端汇总，不额外调 LLM），去重后上限 **5 条**、单条截断 50 字 |
| `mastery_delta` | 本场对**该题所属领域**掌握度的影响（`before` / `after`，0~100）；`direction` 为该领域 |
| `wrong_question_id` | 未通过时自动入本产生的错题条目 id；**该题已在错题本则更新复习档位并返回原 id**；通过或未入本为 `null` |
| `rounds[].timed_out` | 该轮是否用尽限时（由服务端按 `elapsed_ms >= 限时秒数 × 1000` 推导，**不取请求体传入值**）；会话未限时恒为 `false` |

- **纯计算、不调 LLM**——所有输入都已在库（各轮评分与点评、会话上的断点与提示次数），聚合与判通过走固定规则；
- **`RUNNING` 与 `FINISHED` 均可调用**：中途退出后按当前进度结算（用户主动结束的场景）；已结算的会话重复调用**幂等**——**不重复入本、不重复重算掌握度**，除 `mastery_delta` 外其余字段与首次结算一致（该会话已不再触发重算，`mastery_delta.before` 与 `after` 均取该领域当前值，即增量为「当前值 → 当前值」）；
- `ABORTED` 的会话不可结算 → 400 + 10001；
- 不存在或不属于当前账号 → 404 + 10002。

**GET /practice/sessions**（query：`mode` 可选、`page`、`page_size`）

训练历史列表，按 `started_at` 倒序（同秒按 `id` 倒序）；分页默认 **10**、上限 **50**。

响应：`data:{total, items:[{id, question_id, question_content, mode, status, time_limit, overall_score, passed, break_face, round_count, started_at, finished_at}]}`（分页响应统一形态，`page` / `page_size` 为请求参数、不回显）。

- `question_content` 为题干预览（截断至 60 字），供列表直接展示；
- `overall_score` / `passed` / `break_face` 在**未结算时为 `null`**；
- `time_limit` 为开一场时设定的每轮限时秒数，未设限时为 `null`；
- `round_count` 为本场已完成的轮数（含提示轮与材料轮）；
- `mode` 筛选传非法值 → 10001；查无结果返回空列表（不报错）。

**GET /practice/sessions/{id}**

单场回看：会话信息 + 逐轮记录（按 `round_index` 升序）。

响应：

```json
{"id":12,"mode":"INTERVIEWER","status":"FINISHED","time_limit":60,
 "question":{"id":88,"content":"……","qtype":"SUBJECTIVE","stack":"BACKEND_COMMON","direction":"REDIS"},
 "overall_score":6,"passed":false,"break_face":"BOUNDARY","hint_count":1,
 "rounds":[{"index":1,"kind":"OPENING","user_answer":"……","score":7,"review":"……","elapsed_ms":45000,"timed_out":false,"created_at":"2026-09-28 21:03:11"}],
 "reference_answer":"……"}
```

- `time_limit` 为开一场时设定的每轮限时秒数，未设限时为 `null`——**续练（`RUNNING` 会话接着作答）据此恢复倒计时**，与 `POST /practice/sessions` 入参同名同义；
- `user_answer` / `score` / `review` 在**提示轮**为空（那一轮用户没作答、AI 也没评分；`user_answer` 为**空串**、`score` 为 `null`）；`DEBUG` 的**材料轮**其 `round_kind` 记 `HINT`、`review` 存材料全文；

- **`reference_answer` 仅在会话已结算时返回**，`RUNNING` 时为 `null`——追问中给答案等于泄题；
- 不存在或不属于当前账号 → 404 + 10002（不可区分）。

**GET /practice/mastery**（query：`stack` 可选）

掌握度列表（可视化数据源），按技术栈分组。

```json
{"groups":[{"stack":"JAVA_BACKEND","label":"Java 后端","average":62,
            "domains":[{"direction":"JAVA","label":"Java 基础","mastery":75,
                        "answered_count":12,"covered_count":8,"last_practiced_at":"2026-09-27 20:11:03"}]}]}
```

| 字段 | 说明 |
|---|---|
| `average` | 该栈下**有记录领域**的掌握度均值（整数）；全无记录则不出现在 `groups` 中 |
| `mastery` | 该领域当前掌握度 0~100（公式见 SRS §3.6 / 系统设计 §5.10） |
| `answered_count` | 累计作答轮次（含追问轮，**不含提示轮**） |
| `covered_count` | 该领域练过的**不同题目**数 |

- `stack` 筛选传非法值 → 10001。

**实现口径**（本节补充说明，不新增端点）：

1. **参考答案的发放时机**——`QUICK` 模式**当轮**给；**其余模式推迟到整场结算**（`finish` 响应与会话详情）。追问过程中不给答案，否则后几层用户会照着念，追问失去意义；
2. **埋雷清单不下发**——`DEBUG` 模式的埋雷清单（模型从参考答案中抽掉或篡改的点）由服务端内部持有，**不作为 section 下发、不落库**；命中判定由模型在找错轮重新对照参考答案得出；
3. **跨账号一律 404 + 10002**——会话的取用、提交、结算、回看四处统一口径，与「不存在」不可区分（沿用账号体系口径）；
4. **会话终态不可再提交**——`FINISHED` / `ABORTED` 的会话收到 `practice-turn` 请求 → 400 + 10001；
5. **中途退出不丢数据**——每轮**点评产出后**即落库；用户中途关页面或主动 `END`，已答轮次全部保留，可按当前进度调 `finish` 结算；
6. **限时超时**——不报错，正常提交已写内容并带 `timed_out=true`；**一个字都没写就超时 → 该轮计为断点**；评分不因超时直接扣分，但点评需点明「超时未答完」；
7. **入错题本与复习规则**——场景题与八股题**共用同一套**规则（未通过即入本、四档复习档位），与 §3.9 一致；
8. **AI 追问不单独占轮**——追问只作为 `next_question` 段下发，不落 `practice_record`；「追问轮」（`round_kind=FOLLOW_UP`）指用户**被追问后作答**的那一轮；
9. **未产出点评的轮次不落库**——断连 / 报错的轮次既不入库、也不占轮号，重连续跑从下一个轮号接续（回看里不出现空洞）；
10. **整场无作答不入本**——结算时若一场里没有任何有效作答，未通过的判定照常给出，但**不写错题本**（避免「打开就退出」污染错题本）；
11. **已掌握的题再答错重新入本**——该题已在错题本且此前已标记掌握时：清空 `mastered_at`（退出已掌握）、复习档位重置回第 1 档、答错次数累加；
12. **选择题的作答与判定**——`CHOICE` 题的**各作答轮（首轮与追问轮）**都走服务端规则判定（**零 token、即时返回**）：提交的 `user_input` 为**选项标识**（如 `"B"`），服务端按该标识从**本轮可用的选项集**取出选项文本、与正确项 **归一化后精确比对**（两侧同口径展开：首轮的正确项来自题库、是文本，追问轮由模型给出、是标识；不用包含匹配——单字符标识会被 `"AB"` 这类组合误判）；本轮 `review` 段给出**对错 + 正确选项 + 解析**（此反馈不属第 1 条所指的参考答案，不受"追问中不给答案"约束）；**落库的 `user_answer` 是展开后的选项文本**（回看与后续追问上下文自然可读）。**本轮可用的选项集**：首轮取题库 `options`，追问轮取**最近一轮下发的 `next_choices`**（提示轮不写该列，故提示之后仍用同一套选项）；追问轮没有可用选项（模型造不出唯一答案、或输出不合法被丢弃）则该轮**回到开放作答**交 LLM 点评，其后的追问照样尝试下发。`DEBUG` / `FEYNMAN` 两模式与选择题形态不搭——**抽题时即排除选择题**（见 `POST /practice/questions` 的 `mode` 参数），开一场接口再兜底校验（`DEBUG` / `FEYNMAN` + 选择题 → 400 + 10001）。**选择题的二值评分不参与「已挖到底」短路**（`EXHAUSTED_SCORE` 判据）：对 10 / 错 0 命中该判据会让选择题一场只走一轮，与「从首轮到四层追问」的形态不符。

**POST /questions**

| 参数 | 类型 | 必填 | 说明 |
|---|---|---|---|
| direction | string | 是 | 方向 |
| content | string | 是 | 题干 |
| answer | string | 是 | 标准答案 |
| qtype | string | 否 | 默认 SUBJECTIVE |
| source | string | 否 | 默认 AI_GENERATED |

`stack` 由 `direction` 按固定映射**自动推导**（见数据库设计 §5），无需传入。

- 本接口用于**知识点建题**（错题本入本时自动补齐题库记录，见 §3.9），**不支持建选择题**——`qtype` 传 `CHOICE` 时无选项数据可填，判定链路不成立；选择题由题库种子提供（`options` / `explanation` 随种子导入）。

### 3.9 错题本

**GET /wrong-questions**（query：status=`PENDING`待复习/`MASTERED`已掌握、`keyword` 可选、`direction` 可选、page、page_size）

- `keyword`：按题干模糊匹配（`question.content` LIKE `%keyword%`，语义与 `GET /applications` 的 `company` 参数同口径）；
- `direction`：按题目领域筛选（`question.direction` 枚举值，非法值 → 10001）；两者均只作用于本列表查询。

items：`[{id, question_id, content, qtype, options, direction, source_type, review_stage, next_review_at, wrong_count, mastered_at}]`（`content` / `qtype` / `options` 联表 question）。

- `qtype`：题型（`SUBJECTIVE` / `CHOICE` / `SCENARIO`），前端据此决定作答区形态；
- `options`：**选择题选项数组**（`[{key, text}]`，**不含正确标记**，可安全下发）；**仅 `CHOICE` 有值**，其余题型为 `null`；非选择题与题干一起按原形态展示。

排序：**未掌握优先 → 到期先后（`next_review_at` 升序）→ `id` 升序**。分页默认 10、上限 50（越界 → 10001）。`status` 传非法值 → 10001。

**POST /wrong-questions**：两种请求形态（对应两类入本来源）：

- 题库题：`{question_id}`（须存在于题库且未入本，冲突返回 10003）——入本后 `source_type` 记 **`MANUAL`**；
- 面试 / 练习知识点（不在题库）：`{content, answer, direction, source_type:"INTERVIEW"|"DRILL"}`——后端先自动创建 question（source=AI_GENERATED）再入本（`INTERVIEW` 来自模拟面试点评、`DRILL` 来自练习模式点评，见 §3.7 / §3.15）。

两形态的入本初始态一致：`review_stage=1`、`next_review_at = 现在 + 1 天`、`mastered_at=null`；`wrong_count=0`（手动添加与知识点入本都不是"答错"，不计入答错次数——与陪练入本的 `wrong_count=1` 相区分）。

**DELETE /wrong-questions/{id}**：`data: null`。

**POST /wrong-questions/{id}/review**

| 参数 | 类型 | 必填 | 说明 |
|---|---|---|---|
| answer | string | 是 | 复习作答；**选择题传选项标识**（如 `"B"`），其余题型传作答文本 |

响应 `data`：

```json
{"correct":true,"explain":"判定解析/标准答案","review_stage":2,
 "next_review_at":"2026-09-26 00:00:00","mastered":false}
```

判定：`CHOICE` 题按选项标识取出选项文本、与正确项**归一化后精确比对**（零 token，与 §3.8 实现口径第 12 条同一套逻辑）；`SUBJECTIVE` 与 `SCENARIO` 题均走 LLM 判定（非流式 JSON 输出），判定依据分别为标准答案、标准答案 + 四维标尺。档位推进规则见数据库设计 3.9。

**实现口径**（本节补充说明，不新增端点）：

1. **`review_stage` 的 5 是终态**——1~4 为待复习档位（对应 1 / 3 / 7 / 15 天间隔），答对推进一档，**推进到 5 即置 `mastered_at`**，此后 `next_review_at` **不再更新**（保持最后一次的值），列表里也不再计入待复习；到期判定统一用 `review_stage < 5`；
2. **复习判定后重算掌握度**——每次复习判定与每次删除，都按该题所属领域重算一次领域掌握度（口径见系统设计 §5.10），响应 `mastered` 与掌握度曲线同源；
3. **LLM 判定解析失败重试 1 次**——模型未按要求输出 `{"correct", "explain"}` 时**重试一次**，仍解析不出 → **502 + 10011**，且**档位不动、数据不落库**（与 §3.6 中途失败不落库同口径）；`correct` 允许模型返回字符串 `"true"` / `"false"`（自动归一化）；
4. **跨账号与不存在不可区分**——复习判定 → 404 + **30002**（错题本专用码）；删除 → 404 + **10002**（通用码）；两端点均与"该条目根本不存在"同码；
5. **`answer` 校验**——空串或全空白 → 400 + **10001**（复习是"作答"动作，不允许空提交）；
6. **知识点形态复用题库**——`{content, ...}` 形态先按题干在题库中查重：**已在题库则复用该题、不重复建题**；查无才建新题（`qtype` 默认 `SUBJECTIVE`、`source=AI_GENERATED`、`stack` 由 `direction` 按固定映射推导，同 §3.8 的 `POST /questions`）；
7. **选择题复习与陪练同口径**——列表项即带 `qtype` 与 `options`（**不含正确标记**），前端直接渲染为可点选项、提交选项标识；服务端按标识展开后比对，`explain` 给出正确选项与对照说明。与 §3.8 共用同一套比对逻辑，**两侧不各写一套**。

### 3.10 面经整理

**POST /experiences**：`{company?, position?, source?, original_text}`（original_text ≤10000 字）。响应 experience DTO（含 id）。**只存原文，不触发提取**。

**GET /experiences**（page、page_size）：items：`[{id, company, position, source, item_count, created_at}]`（不含原文，列表精简）。

**GET /experiences/{id}**：experience 全文 + `items:[{id, question, answer_points, source_type}]`。

**DELETE /experiences/{id}**：级联删条目。

**POST /stream/experience-extract**（SSE）

| 参数 | 类型 | 必填 | 说明 |
|---|---|---|---|
| experience_id | int | 是 | 已保存的面经 id |

事件流：`start`（提取开始状态文案）→ `delta`（提取进度状态文字，不逐字展示 JSON）→ `done`（`extra:{company, items:[{id, question, answer_points}]}`，条目已落库、`company` 为回填后的最终值（可能为 null））。提取失败发 error（code 40002），原文仍在，前端提供重试；提取期间面经被删除（多标签页）发 error（code 10002）。

**GET /experience-items/search**（query：keyword 必填 ≤50 字、page、page_size）

items：`[{id, experience_id, company, question, answer_points}]`（company 联表 experience）。

**实现口径**：

1. **进度 `delta` 的 `section` 恒为 `progress`**——整句状态文案（开头一条「正在阅读原文…」，此后每识别到新条目补一条「已提炼 N 条…」），**模型输出原文不外发**；`progress` 属节奏豁免段（见 §1.4），整句直通不拆步；前端为覆盖式渲染（后一条覆盖前一条），按"最后一条即当前状态"处理，**不得假设条数**（模型未按格式输出时可能只有开头一条）；
2. `done.extra` 为 `{company, items}`——`items` 元素为 `{id, question, answer_points}`（**含落库 id**，供前端重拉详情失败时兜底渲染）；`company` 为**回填后的最终值**（未手填且未识别到 → `null`，前端可据此直接刷新展示、免一次重拉详情）；`record_id` 为面经 id；
3. **提取即替换**——提取成功后同一事务内清空该面经已有条目、写入新条目并更新 `item_count`；重复提取不翻倍、不追加；
4. **条目清洗**——`question` 缺失或空白整条丢弃；`question` >2000 字 / `answer_points` >5000 字按上限截断；单次最多 50 条（超出截尾）；`answer_points` 缺失记 `null`；
5. **失败口径**——输出无法解析为 JSON 或 0 条有效条目 → error **40002**（原文与已有条目保持原样，前端提供重试）；LLM 失败按四档细分码（10010~10012，见 §1.3 注）原样下发；**均不做自动重试**；
6. **时序**——流正常结束才落库；客户端断连或中途失败**不落库**（重试即完整重跑）；
7. 列表按 `created_at` 倒序（同秒按 `id` 倒序）、不含原文；详情 `items` 按 `id` 升序（即提取顺序）；`company` / `position` / `source` 传空串按未填处理（响应为 `null`）；
8. 检索按 `question` 模糊匹配，`keyword` 需含非空白字符（≤50 字、空白 → 400 + 10001）；结果按 `id` 倒序；跨账号与不存在一律 404 + 10002；
9. **公司名识别与回填（手填优先）**——模型输出含 `company`（原文提到的面试公司名；未提、提到多家或无法确定记 `null`）；**仅在账号未手填 `company` 时回填**，已有值不覆盖；识别结果为 `null`、非字符串或格式异常时**不回填、不报错**（条目照常解析落库）；超 100 字截断（列宽上限）；
10. **提取期间被删除的并发防御**——落库前以**当前读**（`SELECT ... FOR UPDATE`，绕过事务快照）校验面经仍在：已被其他会话删除（多标签页场景）→ error **10002**、**不落任何条目**（区别于撞外键走 10000 兜底）；校验与落库同一事务加锁，并发的删除不会造成「条目插入已删面经名下」。

### 3.11 全局 Agent

**POST /stream/agent-chat**（SSE）

| 参数 | 类型 | 必填 | 说明 |
|---|---|---|---|
| conversation_id | int | 否 | 不传则新建会话（done 事件回 id），传入但不属当前账号 → 404 + 10002 |
| message | string | 是 | 用户输入（1~2000 字，空白 → 400 + 10001） |

事件流：

```
delta      → Agent 文字回复增量（含「参数不全时的追问」与「查询结果的文字总结」）
tool_call  → {tool_name, args}：写操作类工具（新增投递 / 状态流转）参数齐备时下发——
             前端据此渲染"确认卡片"，用户确认后调本节 POST /agent/tools/{tool}/execute 执行
done       → {record_id, conversation_id, extra: null}
             record_id = 本轮最后一条 Agent 消息 id
```

**工具分派**：意图路由（`APPLICATION` / `PRACTICE` / `EXPERIENCE` / `CHAT`）先在关键词表上快筛、未命中再交模型分类（分类结果非法归 `CHAT`）；每次请求只向模型下发该意图对应的工具组，`CHAT` 不下发工具、直接流式闲聊。

查询类工具（查投递 / 搜面经 / 出题 / 今日概览）由后端直接执行：先以文字流式总结结果，末尾补一段 `section="result"` 的 `delta` **一次性 JSON**——`{"type": "<tool_name>", "data": {...工具结果}}`（该段整块直通、不受输出节奏影响），供前端渲染结构化卡片。

**实现口径**：

1. **写操作出卡片、不落库**——`tool_call` 的 `args` 为完整参数、前端原样交给执行接口；模型绝不直接写库；
2. **参数不全降级为追问**——以普通 `delta` 追问缺失字段（如"公司名称"），**不报错**、正常 `done`，本轮照常落库；`50001` 仅用于执行接口；
3. **状态流转按公司名定位**——`update_application_status` 未传 `application_id` 但传了 `company` 时，按公司名模糊匹配本账号最近一条投递；匹配不到 → 追问请用户给出更准确的公司名或记录 id；转 `CLOSED` 缺 `close_reason` → 追问结束原因；
4. **会话延迟创建**——流正常结束才落库（会话不存在则新建）；客户端断连或中途失败**不落任何消息**（重试 = 整轮重发）；
5. **历史上下文**——最近 10 轮对话（单条截断 400 字）；`TOOL` 行仅存档、不进模型上下文；
6. **画像注入**——`APPLICATION` / `EXPERIENCE` 意图注入画像摘要，`PRACTICE` / `CHAT` 不注入；
7. 消息落库形态——查询类工具结果以 `TOOL` 行落库，助手文字（前置文字 + 查询总结）合并为一行 `ASSISTANT`。

**POST /agent/tools/{tool}/execute**

| tool | 请求体 | 说明 |
|---|---|---|
| create_application | 同 POST /applications 请求体，但 **`jd_text` 可选**（Agent 录入路径豁免必填——模型从消息中提取到 JD 就带上、没有则空入库，后续可在投递详情页补填；**表单路径 `POST /applications` 的必填口径不变**） | 执行入库，返回 application DTO |
| update_application_status | `{application_id, status, remark?, close_reason?}`（转 `CLOSED` 时 `close_reason` 必填、仅 `CLOSED` 时可有值，同 `PATCH /applications/{id}/status`） | 状态流转，返回 application DTO |

执行口径：参数缺失 / 非法 → 400 + **50001**；工具名不是写操作类 → 400 + 10001；投递不存在或不属当前账号 → 404 + 10002。

实现口径：

1. **请求体宽收**——两个工具参数集不同，请求体按字典接收、参数校验由服务层完成（宽转支持字符串数字 id、中文状态标签，如 `"3"` 与 `"面试中"`），保证「参数缺失 / 非法 → 50001」口径不被请求校验层拦截；请求体本身非 JSON 对象（如数组）→ 400 + 10001；
2. **执行与对话流解耦**——本端点**不落会话消息**（请求体不关联 `conversation_id`）；会话内 `TOOL` 行仅由查询类工具在 `/stream/agent-chat` 流内产生；
3. **无幂等键**——同一卡片重复提交会重复执行（前端在确认后即时禁用按钮或乐观更新），后端不校验「是否已执行过」。

**GET /agent/conversations**（page 默认 1、page_size 默认 10 / 上限 50）：`data = {total, items}`，items 为 `[{id, title, updated_at}]`，按最近活动（`updated_at`）倒序、同秒按 `id` 倒序。

**GET /agent/conversations/{id}/messages**：`[{id, role, content, tool_name, created_at}]`，按时间正序（同秒按 `id` 升序）；`role` 取 `USER` / `ASSISTANT` / `TOOL`（工具执行结果，`tool_name` 有值）；跨账号与不存在一律 404 + 10002。

### 3.12 画像与设置

**GET /profile / PUT /profile**：PUT 请求体为 user_profile 表全部业务字段（name/school/major/degree/gpa/english_level/experiences/target_position/target_city/skills/weaknesses/note）。skills/weaknesses 为逗号分隔字符串，experiences 为**结构化经历条目数组**（结构见下）。画像**按账号隔离**——每账号一份，请求体不接受 `user_id`（归属由登录态决定）。

**`experiences`（结构化经历条目）**：数组元素结构如下，**可增删条目**（有人一段实习、有人两段项目，按需添加）：

| 字段 | 必填 | 说明 |
|---|---|---|
| type | 是 | 经历类型：`PROJECT` 项目 / `INTERNSHIP` 实习 / `CAMPUS` 校园（其余取值 → 10001） |
| title | 是 | 名称（≤100，空串 → 10001） |
| org | 否 | 所属公司 / 组织（≤100） |
| role | 否 | 担任角色（≤50） |
| period | 否 | 时间段自由文本（≤50，如 `2026-07 ~ 2026-09`） |
| description | 否 | 经历描述（≤2000） |

- 条数上限 **10**；传空数组或 `null` 表示清空；
- 本字段是 **JD 匹配分析与模拟面试项目深挖段的依据**（见 §3.6 / §3.7）；原 `resume_text`（简历全文）字段**已废弃、不再返回**（数据库列同步删除，见数据库设计 v1.19）。

**POST /profile/resume**（multipart，字段 `file` = 简历文件）：上传简历，AI 抽取画像字段（含**结构化经历**）。

| 约束 | 说明 |
|---|---|
| 格式 | `.pdf` / `.docx`（按扩展名判定）；PDF 取文字层逐页提取，Word 提取段落 + 表格逐行（简历常用表格排版，漏掉会丢大段内容） |
| 体积 | ≤ **10MB** |
| 落库 | **纯解析不落库**——结果回给前端填入表单，用户核对修改后走 `PUT /profile` 保存 |

响应：`data = {extracted}`：

```json
{"extracted":{"name":"张三","school":"南京理工大学","major":"软件工程","degree":"本科",
  "gpa":"3.20/4.00","english_level":"CET-6 441","skills":["Java","MySQL","Redis"],
  "experiences":[{"type":"INTERNSHIP","title":"Java 开发实习","org":"某科技公司",
    "role":"后端开发","period":"2026-07 ~ 2026-09","description":"参与企业管理系统定制开发…"}]}}
```

- `extracted` 为 AI 结构化抽取的画像字段（与 `PUT /profile` 各字段同名同义；`skills` 为字符串数组、`experiences` 为结构化经历条目数组，结构同 §3.12 上文）；已按各字段长度上限截断（超长会因前端回填保存被 422 拦下，故在解析侧先收口）；
- **AI 抽取失败不报错**——未配 Key（10012）/ 调用失败 / 输出异常时 `extracted` 为 `null`（前端提示手动填写）；全部字段为空同样记 `null`；
- 扩展名不符 / 文件为空 / 超 10MB / 无法提取文字（损坏、加密、扫描件 PDF）→ **400 + 10001**（附具体原因文案）；
- 文件内容按当前登录账号的配置解析、不落库、不跨账号留痕。

**GET /settings**：

```json
{"tts_enabled":false,"voice_enabled":false,"default_question_count":8,
 "asr_provider":"funasr","tts_voice":"zh-CN-XiaoxiaoNeural","asr_key_set":false,
 "guide_done":false,"crawl_enabled":false}
```

- `tts_enabled` / `voice_enabled` / `default_question_count` / `asr_provider` / `tts_voice` / `guide_done` 为**账号级**配置（随账号各自保存）；
- `guide_done` 为新手指引已读标记（默认 `false`）：走完引导或点「跳过」由前端置 `true`，之后登录不再自动弹出；个人中心「重看新手指引」只重播、不改本字段（P2）；
- `asr_provider` 取值 `funasr`（默认，本地模型，无需 Key）/ `xunfei`（云端备选）；
- `tts_voice` 为 edge-tts 音色名，默认 `zh-CN-XiaoxiaoNeural`（晓晓），可选值见 **§3.13 `GET /tts/voices`**；
- `crawl_enabled` 为**系统级**配置（面向整站公共数据，任一账号修改即全局生效，见 SRS 4.1）——它是校招信息采集的**总开关**，**具体抓哪些学校由 §3.16 `/crawl-sources` 维护**（原 `crawl_url` 单站点地址已废弃、不再返回）；
- `asr_key_set` 仅告知是否已配置讯飞语音 Key，**不回显明文**；默认 `asr_provider=funasr` 时恒为 `false`（本地模型无需凭据）；
- **LLM 供应商相关字段已全部迁出本接口**（原 `llm_provider` / `llm_model` / `llm_base_url` / `llm_key_set`），统一由 **§3.3 `/llm-providers`** 组管理。

**PUT /settings**：可更新 `tts_enabled` / `voice_enabled` / `default_question_count` / `asr_provider` / `tts_voice` / `guide_done` / `crawl_enabled`；`asr_app_id` / `asr_api_key` 传值则以 Fernet 加密后覆盖，传空串不修改。**部分更新语义**——只提交需要变更的字段，未提交的保持原值。

校验口径：`default_question_count` 取 **1~50** 整数；`asr_provider` 仅接受 `funasr` / `xunfei`；`tts_voice` 必须命中 **§3.13 `GET /tts/voices`** 音色清单（去除首尾空白后比对，非法 → **10001**）；`tts_enabled` / `voice_enabled` / `guide_done` / `crawl_enabled` **严格要求布尔值**（传字符串、数字等非布尔值一律 **10001**，不做隐式转换）；以上任一越界或非法 → **10001**。

### 3.13 语音（P2）

模拟面试与练习模式的长时长语音交互由**前端 VAD 断句 + 逐句调用转写**实现：前端 VAD 按当前语速**自适应判定静音阈值**（快 1.6s / 正常 2.65s / 慢 3.6s），切出 3~15s 片段即上传，转写文本**累积回填**到作答框，用户全程连续说话、整场不限轮次与总时长。播报侧由后端合成音频返回，前端 `<audio>` 播放、可随时打断。

**POST /asr/transcribe**（multipart：`file`=音频片段，webm/ogg/wav，单片段 ≤2MB）

响应：`data:{text:"转写文本",duration_ms:1200}`（失败 **60001**）。仅转写回填，**不落库**。

- 供应商由账号的 `asr_provider` 决定：`funasr` 走**本地模型**（进程内推理，不出网；服务启动时后台预热模型，日常使用首句无需等待冷加载——预热未完成或失败时首次调用触发加载、略慢）；`xunfei` 走云端接口（需已配 Key，未配 → 60001）；
- 单次请求对应**一个语音片段**而非整场录音——长时长的实现方式，故服务端不限制轮次与累计时长；
- **实现口径（步骤 24 落地）**：
  - 上传校验**先于引擎调用**——字节为空 / 超过 2MB / 不可解码（含无音频流）→ **10001**；
  - `duration_ms` 按解码后 16k 单声道采样数推算（与容器格式无关，同一音频换容器时长一致）；
  - 本地转写为**单片段整段调用**——服务端不按 600ms 分块流式处理（片段已由前端 VAD 切成 3~15s 短句），模型为**非流式**（`paraformer-zh`，Seaco-Paraformer），整段一次送入、输出完整；模型进程内**单例 + 启动预热**（服务启动时后台线程提前加载、不阻塞服务就绪；预热未完成或失败时首次转写懒加载兜底），日常使用单次转写为秒级（热推理实测约 8 倍实时，14 秒音频约 1.7 秒）；
  - **无有效语音信号**的片段（纯静音 / 仅环境底噪）**直接返回空文本**（`text=""`、`duration_ms` 照常返回）、不进引擎——非流式模型对这类输入会幻觉输出（实测「嗯没有没有」）；前端累积回填时跳过空文本即可，无需特殊处理；
  - 讯飞按官方 RTASR 协议实现（`wss://rtasr.xfyun.cn/v1/ws`），**尚未用真实凭据联调**；未配凭据与凭据解析失败均 → **60001**；
  - 音频与转写文本**均不落库**。

**分句时间轴（`segments`）约定**：VAD 在前端执行，**句间停顿只有前端知道**——前端在**提交作答**时（`/stream/interview-chat` 或 `/stream/drill-review`，见 §3.7 / §3.15）须一并上传 `segments`：`[{seq, start_ms, end_ms, text}]`（每句序号、起止毫秒、该句原始转写文本）。后端据此计算语速 / 填充词密度 / 停顿点 / 有效时长占比 / 流畅度趋势五项表达力指标（口径见 SRS §3.11、设计见系统设计 5.7）。**该字段是表达维度的唯一数据来源**——不传则本次作答只出内容点评、不出表达点评；`POST /asr/transcribe` 接口本身不变（仍只做单片段转写、不落库）。

**POST /tts/synthesize**

```json
{"text":"这道题可以从三个层面回答","voice":"zh-CN-XiaoxiaoNeural"}
```

- `voice` 可省略，缺省用账号的 `tts_voice` 配置；
- 响应：**音频流**（`audio/mpeg`，直接作为 `<audio src>` 播放），**不走统一响应体**；
- 失败 → **标准响应体 + 60002**（前端静默降级，该句不播报）；
- 服务端按 `sha1(text + voice)` 缓存合成结果（`backend/cache/tts/`），同一文案 + 同一音色**只合成一次**；命中缓存直接返回；
- **实现口径（步骤 24 落地）**：
  - `text` 必填，去除首尾空白后 **1~2000 字**（空白或超长 → **10001**）；`voice` 显式传入时须命中音色清单（非法 → **10001**）；
  - 缓存为**本地文件缓存**，缓存键 = `sha1(文本去首尾空白 + "\n" + 音色)`；命中时直接读文件返回、**零网络调用**（断网亦可复播已缓存内容）。

**GET /tts/voices**：返回可选音色列表 `data:[{id:"zh-CN-XiaoxiaoNeural",name:"晓晓",gender:"Female",style:"温暖亲和"},...]`，供设置页下拉选择（默认音色置顶）。当前清单共 **14 个中文音色**（普通话 8 / 粤语 3 / 台湾 3），随账号所配音色置顶。

### 3.14 定时引擎

**POST /reminders/run**：立即执行每日任务（开发/演示用），返回 `data:{generated: n}`。**多账号下遍历全部账号执行**——每个账号按其自身投递记录与错题生成提醒（提醒文案用该账号自己的 AI 配置）；**校招信息采集为公共任务、全站执行一次**（逐源抓取 + 去重/变更检测/归档，见 §3.16），采集完成后对每个账号跑一遍**订阅匹配**（候选为当日新入库 / 变更的**公共信息**，本账号投喂记录**不参与推送**——避免自己录入的岗位提醒自己，详见 §3.16），命中的提醒计入 `generated`。

**GET /reminders**（query：date 可选、checked 可选、page、page_size）

items：`[{id, reminder_type, ref_id, ref_type, content, remind_date, checked}]`。

- `ref_type` **仅 `reminder_type=INFO_MATCH` 时有值**（`campus_event` / `job_posting`），用于前端跳转到对应信息详情；其余类型为 `null`；

**PUT /reminders/{id}/check**：标记已读，`data: null`。

**实现口径**（步骤 20 落地）：

1. **`date` 为「恰好该日」**——筛选 `remind_date == date` 的提醒（提醒生成即当天，不是「该日起」的累积口径）；列表排序 `remind_date` 倒序、同日按 `id` 倒序；
2. `page` 默认 1、`page_size` 默认 **10**、上限 **50**（越界或非法日期 → 10001）；`checked` 为布尔筛选，前端取未读数用 `checked=false&page_size=1` 读 `total`（徽标口径，见接口文档 §3.4 同款约定）；
3. **未读徽标判定**：`checked` 字段以布尔值下发（库内存 0/1），前端按布尔判断即可；
4. **`ref_type` 当前恒为 `null`**——该字段仅为校招情报命中（`INFO_MATCH`，步骤 22 起生成）预留，现阶段三类提醒（FOLLOW_UP / WRONG_QUESTION / INTERVIEW）均无值；
5. **生成判定**（与 `GET /overview` 同口径、纯规则不调 AI）：FOLLOW_UP = 投递处于跟进状态（`APPLIED` / `WRITTEN`）且**距投递满 3 天**且**无未来笔试 / 面试安排**；WRONG_QUESTION = 错题**已到复习时间**（`next_review_at <= 当前`）且未掌握；INTERVIEW = 投递未结束且未来 **7 日内**有笔试 / 面试安排；
6. **文案生成**：该账号全部新条目**一次性批量交 AI 改写**（chat_json，20~50 字口语化）；未配 AI（10012）/ 调用失败 / 输出不合法 → **该条回退固定模板文案**（如「{公司} · {岗位} 已投递 {N} 天仍无进展，建议主动跟进」），提醒**照常生成不带错**；
7. **幂等**：同一账号同一天同一对象（同 `reminder_type + ref_id`）**不重复生成**——重复触发 `/reminders/run` 返回 0，不影响已生成条目；任务执行中再次触发**直接返回 `generated: 0`**（不排队、不报错）；
8. **`/reminders/run` 多账号**：遍历全部账号逐个生成、逐个提交，**单个账号失败（如 AI 配置异常）不影响其他账号**；`generated` 为本次**实际新增**的提醒总数；
9. **标记已读幂等**：已读条目重复标记仍返回 200；**不存在或跨账号 → 404 + 10002**（与其他资源同口径）。

### 3.15 练习模式（FR-020，P2）

同一道题反复练的练习形态，与模拟面试**共用转写、表达力指标与点评底座**（见系统设计 5.7）。**路径前缀为 `/drills`**——项目内 `practice` 专指八股陪练（§3.8），两者不可混用。

**GET /drills**（query：`archived` 可选 bool、`source` 可选、`page`、`page_size`；**默认只返回未归档**）

items：`[{id, title, source, ref_id, archived, attempt_count, last_score, best_score, created_at, updated_at}]`——`attempt_count` / `last_score` / `best_score` 为聚合字段，供列表页直接展示进度概况。

**POST /drills**

| 参数 | 类型 | 必填 | 说明 |
|---|---|---|---|
| title | string | 是 | 题目标题（≤50 字） |
| question | string | 否 | 完整题面；不传则由 AI 按 `title` + 来源生成 |
| source | string | 否 | 来源枚举（见 SRS §4.1），默认 `CUSTOM` |
| ref_id | int | 条件必填 | `source` 非 `CUSTOM` 时必填（来源实体 id）；后端校验归属，不属于当前账号 → 10002 |

响应：`data = topic DTO`。**只记来源不复制内容**——`ref_id` 用于回跳与标注，题面以本次写入的 `question` 为准。

**GET /drills/{topic_id}**：topic DTO + `attempts` 摘要数组：

```json
{"id":1,"title":"自我介绍","question":"...","source":"INTRO","ref_id":null,
 "archived":0,"created_at":"...","updated_at":"...",
 "attempts":[{"id":9,"seq":3,"is_voice":1,"score":8,"duration_ms":68000,"created_at":"..."}]}
```

`attempts` 摘要**不含点评全文与指标**（控制体量），完整内容走单次详情接口。

**PUT /drills/{topic_id}**：部分更新语义（只更新请求体中出现的字段）——`title` / `question` / `archived`（`true` 归档、`false` 恢复）。归档后：默认列表不展示、**不可再提交作答**（→ 40003），历史记录仍可查看。

**GET /drills/{topic_id}/attempts/{attempt_id}**：单次练习完整 DTO：

```json
{"id":9,"topic_id":1,"seq":3,"answer":"...","is_voice":1,"voice_metrics":{...},
 "score":8,"review":"...","duration_ms":68000,"created_at":"..."}
```

`voice_metrics` 结构见数据库设计 §3.19；非语音作答或作答过短为 `null`。

**GET /drills/{topic_id}/progress**：跨次进步对比。

```json
{"topic_id":1,"attempt_count":3,
 "items":[{"seq":1,"score":5,"duration_ms":95000,"speech_rate":210,"filler_count":12,"pause_count":3,"speech_ratio":0.71},
          {"seq":3,"score":8,"duration_ms":68000,"speech_rate":235,"filler_count":4,"pause_count":1,"speech_ratio":0.85}],
 "deltas":{"score":3,"duration_ms":-27000,"filler_count":-8,"pause_count":-2}}
```

- `items` 按 `seq` 升序给出全部记录，供前端画趋势线；
- `deltas` 为**最近一次 vs 上一次**；练满 **2 遍**才返回（首遍无对比对象，`deltas` 为 `null`）；
- **口径版本不一致的记录不参与对比**（`voice_metrics.version` 不同即跳过——宁可少展示一次对比，也不给出失真曲线，见系统设计 5.7）；文字作答的记录表达指标为 `null`，不参与表达指标对比。

**POST /stream/drill-review**（SSE）

| 参数 | 类型 | 必填 | 说明 |
|---|---|---|---|
| topic_id | int | 是 | 题目 id（须属于当前账号且未归档，归档 → 40003） |
| answer | string | 是 | 本次作答文本 |
| is_voice | bool | 否 | 默认 false |
| segments | array | 否 | **语音作答时必传**：分句时间轴（格式同 §3.7），供计算表达力指标 |
| duration_ms | int | 否 | 作答耗时（毫秒），前端计时上报 |

事件流：`start`（"正在点评…"）→ `delta`（section 依次 `score` / `review`）→ `done`（`record_id` = 新 drill_attempt.id，含 `seq`；语音作答且已算出指标时 `extra:{voice_metrics:{...}}`）。

- **表达力指标先于点评返回**：指标由纯函数在落库前算出（毫秒级、零 token），随 `done` 一次性下发，前端先展示指标、再等点评流完；
- 点评中的知识点与模拟面试同口径提示入错题本候选（`source_type=DRILL`，用户确认后经 `POST /wrong-questions` 入本，见 §3.9）。

### 3.16 校招情报（FR-021 / FR-022）

多所高校就业网站的宣讲会 / 双选会 / 岗位聚合，含投喂通道、订阅规则与日历聚合。采集与处理口径见系统设计 5.9，表结构见数据库设计 §3.20~3.22。

**信息归属口径**：`campus_event`（宣讲会/双选会）与 `crawl_source`（信息源）为**公共数据**，全站共享；`job_posting` 为**混合**——自动抓取的岗位（`ingest_source=AUTO`）全员可见，**投喂的岗位（`ingest_source=FEED`）仅本账号可见**；`subscription`（订阅规则）为账号私有。

**来源站点口径**：`campus-events` / `job-postings` 及概览 `campus_events` / `top_job_postings` 中的 `source_site`，下发**来源学校名**（如「南京理工大学」）——由条目的来源站点标识映射源配置（`crawl_source`）的 `school_name` 得出（表内存储仍为站点标识，见数据库设计 3.13）；源已删除等映射不到时回退站点标识；跨源合并的条目记多个来源（逗号分隔，如「南京理工大学,东南大学」，**映射后同名去重**——同校多源合并不重复出现）；投喂岗位（`ingest_source=FEED`）无来源站点、为空。

**来源站点筛选**：两个列表接口的 `source_site` 查询参数按**来源学校名**筛选（与下发口径同名同义，取值建议直接采用 `GET /crawl-sources` 返回的 `school_name`）：含该校**任一来源**的条目命中（跨源合并条目、同校多源站点均命中）；按站点标识精确比对，不会因子域后缀相似误命中（如 `xnjust.91job.org.cn` 不因形似 `njust.91job.org.cn` 被命中）；传入未配置的学校名返回空集；投喂岗位无来源站点、不会被任何来源筛选命中。

**GET /campus-events**（宣讲会 / 双选会列表）

| 参数 | 位置 | 类型 | 必填 | 说明 |
|---|---|---|---|---|
| info_type | query | string | 否 | `TALK` 宣讲会 / `FAIR` 双选会；不传 = 全部 |
| city | query | string | 否 | 按**地点文本**模糊匹配（宣讲会/双选会地点多为校区，无独立城市字段，口径见数据库设计 3.13） |
| keyword | query | string | 否 | 标题 / 公司名模糊匹配 |
| source_site | query | string | 否 | 按来源学校名筛选（值同 `source_site` 下发口径）；含该校任一来源的条目命中，不传 = 全部；匹配语义见本节开头「来源站点筛选」 |
| date_from | query | date | 否 | 活动日期下界（含） |
| date_to | query | date | 否 | 活动日期上界（含） |
| include_expired | query | bool | 否 | 默认 `false`（只返回未过期）；`true` = 含 `EXPIRED` |
| sort | query | string | 否 | `time` 按活动时间升序（**默认**）/ `match` 按画像匹配度降序 |
| page / page_size | query | int | 否 | 默认 1 / 10 |

items：`[{id, title, company, event_date, location, major_req, source_url, source_site, info_type, status, changed_at, match_score}]`

- `status` 为 `ACTIVE` / `CHANGED`（内容已变更，前端打「已变更」角标）/ `EXPIRED`；`changed_at` 仅 `CHANGED` 时有值；
- `match_score` 为画像匹配打分（0~100，口径见系统设计 5.9），`sort=match` 时按其降序；**信息缺失的维度不加分也不隐藏**；
- `source_site` 为来源学校名，值形态（多来源 / 映射不到时的回退）见本节开头「来源站点口径」。

**GET /job-postings**（岗位列表）

| 参数 | 位置 | 类型 | 必填 | 说明 |
|---|---|---|---|---|
| city | query | string | 否 | 城市等值匹配 |
| company | query | string | 否 | 公司名模糊匹配 |
| job_type | query | string | 否 | `CAMPUS` / `INTERN` / `SOCIAL` |
| keyword | query | string | 否 | 岗位名 / 公司名模糊匹配 |
| source_site | query | string | 否 | 按来源学校名筛选（值同 `source_site` 下发口径）；投喂岗位无来源不会被命中，不传 = 全部；匹配语义见本节开头「来源站点筛选」 |
| status | query | string | 否 | 不传或传 `ACTIVE` = 返回 `ACTIVE` + `CHANGED`（已变更的一同展示）；传 `CHANGED` / `EXPIRED` = 按该值精确过滤；非法值 → 10001 |
| sort | query | string | 否 | `time`（默认，按 `first_seen_at` 降序）/ `match`（匹配度降序） |
| page / page_size | query | int | 否 | 默认 1 / 10 |

items：`[{id, title, company, city, edu_req, major_req, salary_text, job_type, deadline, source_site, source_url, ingest_source, status, first_seen_at, changed_at, match_score, is_applied}]`

- **结果 = 公共岗位（`user_id=0`）+ 本账号投喂的岗位**，其他账号的投喂记录**完全不可见**（跨账号隔离必测）；
- `is_applied` 按「公司 + 岗位名」比对**当前账号**的投递记录得出（**两侧均归一化后比较**——公司名去括号后缀、岗位名忽略空白与大小写，与去重指纹同一套归一化），供卡片显示"已投递"（见 SRS §3.18 业务打通）；
- `ingest_source` 区分 `AUTO` 自动抓取 / `FEED` 投喂——**投喂记录才有 `raw_excerpt`（原文摘录）**，自动抓取**不存正文**（NFR-016）。

**POST /job-postings/ingest**（投喂：抽取预览，**不入库**）

| 参数 | 类型 | 必填 | 说明 |
|---|---|---|---|
| text | string | 条件必填 | 粘贴的 JD 原文（**≤20000 字**；与 `url` 二选一，**同传 → 10001**） |
| url | string | 条件必填 | 招聘信息链接（**≤500 字**；走合规抓取：UA 标识 / robots 检查 / 同域限频 / **拒绝内网地址**，见系统设计第 6 章） |

响应 `data`：`{fields: {...岗位字段...}, missing: ["deadline","city"], source: "FEED", fetched_from: "url"}`

- `fields` 为 AI 抽取的结构化结果，`missing` 列出**未抽取到的字段**（前端标黄提示用户补充）；
- **本接口只返回预览、不落库**——用户确认后调用 `POST /job-postings` 入库（与 Agent 写操作出确认卡片同口径）；
- 抽取失败（LLM 输出不可解析）→ **70003**；链接需登录 / 被站点拒绝 / 内网地址 → **70003**（message 区分两类原因），前端提示并降级为手动填表；
- **未配置 AI 供应商（或 Key 无效）→ 10012**（引导去 AI 配置页；原文已就绪，配好 Key 直接重试即可，**不降级为手动填表**）。

**POST /job-postings**（确认入库）

请求体：岗位字段（`title` / `company` 必填，其余同列表字段，`raw_excerpt` 可回传原文供日后校对）。`user_id` / `dedup_key` / `ingest_source` 由服务端生成（`ingest_source=FEED`）。响应 `data = 岗位 DTO`。

- 同一账号内重复投喂（`UNIQUE(user_id, dedup_key)` 命中）→ 覆盖更新，不报错。

**DELETE /job-postings/{id}**：删除投喂岗位。**自动抓取的岗位不可删 → 10001**；不存在或非本账号 → 10002（不可区分，见系统设计 3.6）。

**GET /crawl-sources**（源清单）

items：`[{id, school_name, system_type, domain, params, enabled, last_crawl_at, last_status, last_error}]`

- `system_type` 为 `91JOB` / `BYSJY`（云就业）/ `JYSD`（才立方）；`params` 为该系统所需参数的 JSON 对象，按 `system_type` 取值——`91JOB` 必填 `xxdm`（学校代码）；`BYSJY` 必填 `panel_name` + `panel_id`（该校站点的菜单名与菜单 ID，两参数需成对匹配、单独一个无效）；`JYSD` 可选 `start_path`（列表入口路径，默认 `/teachin/index`）；三者均可选传 `max_pages`（翻页上限，默认 5、上限 50）。参数缺失时该源采集记失败并附原因；
- `last_status` 为 `OK` / `FAILED`（源疑似失效）/ `BLOCKED`（robots 禁止或持续 403，**已停止该源不重试**）/ `null`（从未抓取）；`last_error` 为失败原因摘要。

**POST /crawl-sources**

| 参数 | 类型 | 必填 | 说明 |
|---|---|---|---|
| school_name | string | 是 | 学校名称（≤100 字） |
| system_type | string | 是 | `91JOB` / `BYSJY` / `JYSD`，非法值 → 10001 |
| domain | string | 是 | 站点域名（仅 http/https） |
| params | object | 否 | 系统参数（按 `system_type` 取值） |

- 同一系统 + 同一域名重复登记 → **10003**；
- **新增一所学校 = 加一行配置，不写代码**。

**PUT /crawl-sources/{id}**：部分更新 `school_name` / `domain` / `params` / `enabled`；改 `system_type` 不支持（需删除后重建）→ 10001。**编辑后重置该源的最近采集状态**（清空 `last_status` / `last_error`，保留最近采集时间）——改完配置不受「每源每日 1 次」限制、可立即重新采集验证。

**DELETE /crawl-sources/{id}**：删除源。**已抓到的条目保留**（不连带删除，见数据库设计 3.20）。

**POST /crawl-sources/run**（手动触发采集，演示用）

| 参数 | 类型 | 必填 | 说明 |
|---|---|---|---|
| source_id | int | 否 | 指定单个源；不传 = 执行全部启用中的源 |

响应 `data`：`{total, ok, failed, blocked, items_new, items_updated, items_changed, expired, details: [{source_id, school_name, status, error, counts}]}`

- **单源失败不整体报错**——逐源结果计入 `details`，整体仍返回 200；**指定 `source_id` 且该源失败 → 502 + 70002**（单源粒度才报错，便于调试）；
- **手动触发 = 强制刷新**——不受采集总开关限制、不检查「每源每日 1 次」（后者是每日任务的跳过口径，见 §3.12 采集总开关），任何时刻可按需重跑；
- 执行完成后按新入库 / 变更的条目对全部账号跑一遍订阅匹配（步骤 22 已落地；候选口径同 §3.14 每日任务——仅公共信息）。

**GET /calendar**（日历事件聚合，FR-022）

| 参数 | 位置 | 类型 | 必填 | 说明 |
|---|---|---|---|---|
| start | query | date | 是 | 区间起（含） |
| end | query | date | 是 | 区间止（含）；`end < start` → 10001 |

响应 `data`：`[{event_type, title, event_at, ref_type, ref_id, company, location, status}]`——**一次请求返回四类事件**，前端不再并发拉两个列表：

| event_type | 数据来源 | 说明 |
|---|---|---|
| `TALK` / `FAIR` | `campus_event`（`event_date` 落在区间内） | 宣讲会 / 双选会；`status` 为活动状态（`ACTIVE` / `CHANGED` / `EXPIRED`）——**已过期（`EXPIRED`）但落在区间内的同样返回**，区间命中即返回 |
| `EXAM` | 当前账号 `application.next_event_at`，且 `status=WRITTEN` | 笔试；`title` 为岗位名、`location` 为空、`status` 为投递状态 |
| `INTERVIEW` | 当前账号 `application.next_event_at`，且 `status=INTERVIEW` | 面试（字段形态同 `EXAM`） |

- `ref_type` 为 `campus_event` / `application`，与 `ref_id` 一起供前端点击跳转；
- **排序 `event_at` 升序**（同一时间按来源与 id 稳定排序）；
- 空区间返回**空数组**，不报错；跨月查询按 `start`/`end` 区间取（前端按整月下发）。

**GET /subscriptions**（订阅规则列表）：items `[{id, name, keywords, companies, cities, info_types, enabled, created_at}]`——数组类字段直接返回**数组**（库中为 JSON 字符串，接口层转换）。

**POST /subscriptions**

| 参数 | 类型 | 必填 | 说明 |
|---|---|---|---|
| name | string | 是 | 规则名称（≤50 字） |
| keywords | array | 否 | 关键词数组（命中标题 / 公司名） |
| companies | array | 否 | 公司名数组 |
| cities | array | 否 | 城市数组（岗位按城市、宣讲会按地点文本） |
| info_types | array | 否 | `TALK` / `FAIR` / `JOB`，空 = 不限 |
| enabled | bool | 否 | 默认 `true` |

**匹配语义**：字段留空 = 该维度不限；**不同维度之间 AND、同一维度数组内部 OR**。数组字段服务端清洗：逐项去首尾空白、去空、**去重**、单项 ≤50 字、每维度 ≤20 项（超出截断）。

**订阅推送**：候选为**当日新入库 / 变更的公共信息**（`campus_event` + 公共岗位 `user_id=0`，均排除 `EXPIRED`）——本账号投喂记录**不参与推送**（避免自己录入的岗位提醒自己），其他账号的投喂记录任何情况下不得命中；命中写站内提醒（`reminder_type=INFO_MATCH` + `ref_type` 标识来源表，**模板文案不经 LLM**）。**同日去重按 `(user_id, reminder_type, ref_id, remind_date)`**——该唯一键**不含 `ref_type`**，两表 id 撞值时会合并为一条（已知边界，见数据库设计 §3.12）。

**PUT /subscriptions/{id}** / **DELETE /subscriptions/{id}**：修改（含 `enabled` 开关）/ 删除；不存在或非本账号 → 10002。PUT 为**部分更新**——未传字段保持原值，传**空数组 = 清空该维度**（回到「不限」）。
