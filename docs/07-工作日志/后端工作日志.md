## 合并事故修复（`tests/conftest.py`）

| 项 | 内容 |
|---|---|
| 完成日期 | 2026-09-24 |
| 性质 | **非开发计划步骤**，属分支合并后的回归修复 |
| 对应分支 | `backend` |

### 工作内容

**现象**：合入 `origin/frontend` 后 `pytest` 无法收集用例，报 `NameError: name 'Engine' is not defined`（`tests/conftest.py`），全量测试一条也跑不了。

**根因**：本步（步骤 3）改造 `conftest.py` 时用的是**逐用例替换全局 engine** 的隔离方案；而测试侧在步骤 2 交付的是**模块级 `DATABASE_URL` 环境变量**方案。两者被手工拼在一个文件里，且拼接时丢失了 `create_engine` / `sessionmaker` / `Session` 等 import。更深一层：`tests/test_database_init.py` 用的是模块级 `from app.database import engine`，**替换方案对此无效**（替换只改模块属性，改不掉用例里已绑定的名字），若保留替换方案，那 15 条建表冒烟会直接打在开发库上。

**处理**：**以模块级 `DATABASE_URL` 为唯一隔离底座**（test_database_init 依赖它，且对全部用例一视同仁），三个 fixture 改为基于全局 `engine` / `SessionLocal`；另加**每例 `_reset_database()`**（`drop_all` + `create_all`），避免用例间数据污染（如「导入全非法后应为 0 条」这类断言依赖空库）。

**顺带**：`pytest_sessionfinish` 的临时目录清理加三次重试——Windows 下句柄释放有延迟，一次 `rmtree` 可能出现「文件删掉、空目录留下」。

### 验证

| # | 验证项 | 命令 | 结果 |
|---|---|---|---|
| 1 | 全量测试 | `pytest` | **43 passed**（6 骨架 + 15 建表冒烟 + 22 投递） |
| 2 | 临时目录清理 | 跑完后检查系统临时目录 | 无 `jobpilot-test-*` 残留 |
| 3 | 开发库零污染 | 检查 `backend/app.db` 时间戳 | 未变（仍为步骤 2 产物） |

### 经验

**共享基础设施（conftest / 公共 fixture）在合并时不能"两边都留"**：两套隔离方案并存不是"更保险"，而是必崩——要么 import 缺失直接报错，要么两套机制互相架空、让某一批用例偷偷跑在开发库上。合并这类文件时以**一份为准**，另一份的增量改造到这一份上。

## npm 小版本差异致锁文件互改：定位与版本门槛收紧

| 项 | 内容 |
|---|---|
| 完成日期 | 2026-09-24 |
| 性质 | **非开发计划步骤**，属协作工具链问题处理（跨前后端） |
| 对应分支 | `backend`（改动涉及公共文件与 `frontend/` 的 `package.json`、`.npmrc`） |

### 背景

`frontend/package-lock.json` 在两分支间分叉：`backend` 侧 1 个 `"dev": true`，`frontend` 侧 28 个 `"dev": true` + 8 个 `"peer": true`。此前曾归因为"npm 10 与 npm 11 的代际差异"，**该判断有误**——两版 `lockfileVersion` 同为 3，非代际问题。

### 定位过程

在临时目录用 `npx -y npm@<版本> install --package-lock-only` 逐版本复现（不安装依赖、不触碰工程文件）：

| 版本 | `dev` 标记 | `peer` 标记 | 与 `backend` 侧锁文件对比 |
|---|---|---|---|
| 11.6.1（前端侧实际版本） | 28 | 8 | **分叉来源**，逐行吻合 |
| 11.12.1（后端侧实际版本） | 1 | 0 | 基准 |
| 12.1.0（当前 latest） | 1 | 0 | 除 `engines` 字段外**零差异** |

结论：分界线落在 **11.6.1 ~ 11.12.1 之间**，是 npm 11.x 内部小版本对 optional 平台包标记计算的行为变化。原 `engines` 门槛 `>=11` 拦不住 11.6.1，等于未设。

### 产出

| 项 | 位置 | 变化 |
|---|---|---|
| 版本门槛 | `frontend/package.json` | `engines.npm`：`>=11` → `>=11.12.1` |
| 归因注释 | `frontend/.npmrc` | 修正为"11.6.1 写标记、11.12.1 与 12.1.0 不写" |
| 公共文件 | `README.md` | 「前端」节版本要求与说明同步；顺带修正滞后的项目状态（步骤 1 → 步骤 3）与目录清单（补 `07-工作日志/`） |
| 公共文件 | `docs/02-设计文档/项目结构.md` | 第 3 节口径同步，升 **v1.7** |
| 问题记录 | `docs/07-工作日志/问题记录.md` | 新增 **IS-14**，状态统计更新为 10 / 3 / 1 |

### 验证

| # | 验证项 | 方式 | 结果 |
|---|---|---|---|
| 1 | 新门槛放行后端侧 | `npm install`（本机 11.12.1） | 通过，无 `EBADENGINE` |
| 2 | 锁文件幂等 | 连跑两次 `npm install` 比对 hash | `9c7fbaff` → `9c7fbaff`，**零变动** |

### 决策与遗留

### 工作内容

需求：模拟面试要支持**长时间语音交互**，且 TTS 播报音色要**鲜活灵动**。原方案两项均不达标——讯飞「语音听写」**单次 ≤60 秒**（做不了长时长）、浏览器 `speechSynthesis` 中文音色塑料感重。

调研对比后用户拍板 **FunASR（本地流式转写）+ edge-tts（合成播报）**，关键决策：

| # | 决策 | 结论与理由 |
|---|---|---|
| 1 | ASR 方案 | **FunASR `paraformer-zh-streaming`**（阿里开源）——进程内运行、CPU 可跑、**不限时长**、零费用、**不出网**（断网可演示）；首次需联网从 ModelScope 下载模型（数百 MB），之后本地可用 |
| 2 | TTS 方案 | **edge-tts**（微软 Edge 在线语音的 Python 封装）——免费无需注册、中文音色 20+（晓晓 / 云希 / 云扬）、自然度远超 `speechSynthesis` |
| 3 | 长时长怎么实现 | **不缓冲整场录音**：前端 VAD 检测约 1.2s 静音即切出 3~15s 片段，逐句上传转写、**累积回填**作答框；整场不限轮次与总时长（不做 WebSocket，避免复杂度） |
| 4 | TTS 链路归属 | edge-tts 是 Python 包，**必须走后端**：`POST /tts/synthesize` 返回音频流，前端 `<audio>` 播放可打断；按 `sha1(text+voice)` 文件缓存 |
| 5 | 供应商关系 | 讯飞由「唯一实现」降为**可选备选**（`asr_provider=xunfei`），其 Key 仅此时才填；豆包 TTS 预留 |
