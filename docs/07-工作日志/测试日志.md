### 工作内容

**① 修复步骤 1 遗留：测试库未隔离**

原 `conftest.py` 的 `client` fixture 直接使用生产 engine（`sqlite:///./app.db`），任何触发 `lifespan` 的测试都会写进**开发库**（建表、导入 120+ 道种子题、插入初始行），违反测试计划 §1.1「不碰开发库」。

改为：`conftest.py` **模块级**（早于任何 `app.*` 导入）把 `DATABASE_URL` 指向临时目录下的独立 SQLite 文件——`app/config.py` 的 `Settings` 在模块导入时即读取环境变量，晚一行就固定成开发库。会话结束先 `engine.dispose()` 再删临时目录（Windows 下未释放句柄会删除失败）。

**② 新增 `tests/expected_schema.py`：把设计文档固化为期望值**

15 表 / 116 字段 / 14 索引 / 7 外键 / 3 唯一约束，外加 10 个枚举类取值、种子题库数量要求、8 个配置默认项。**选择硬编码文档清单而非 ORM 元数据自查**——后者只能证明「库与模型一致」，抓不出「模型写错但自洽」，而验收口径是「字段符合**设计文档**」。

**③ 新增 `tests/test_database_init.py`：15 条建表冒烟用例**

| 类别 | 用例 | 检查内容 |
|---|---|---|
| 结构 | 1~6 | 15 表齐全；列名 / 类型 / 可空 / 主键逐字段相符；14 个索引；3 处唯一约束；7 处外键；WAL 与外键 PRAGMA 开启 |
| 行为 | 7~11 | 外键与 3 处唯一约束**真生效**（插非法数据被拒）；11 处枚举默认值 + 整型 / 文本默认值；初始行正确 |
| 数据 | 12~14 | 种子题库 ≥120 题且四方向各 ≥30；题干无重复、字段合法；`init_db()` 幂等 |
| 口径 | 15 | 10 个枚举类取值与设计文档 §5 逐值一致 |

**关键设计点**：SQLAlchemy 的 `default=` 是 **Python 侧默认值，DDL 中不产生 `DEFAULT` 子句**，因此「默认值正确」无法通过查表结构验证，只能**插入一行后读回**——用例 9 / 10 依此设计。同理，「约束声明了」不等于「约束生效」，用例 7 / 11 用真实插入验证。

### 工作内容

**一、背景：这不是「加一条边」，而是修正一条规则的表述**

试用中提出「已投递应该也要支持直接拖入面试中，有些公司是没有笔试的」。查证发现 SRS FR-004 原文写的是「流转只能**沿链前进**或终止」，而当前实现把「沿链前进」收窄成了「**逐跳**前进」，跨环节一律判为跳级拒绝。故本次是**规则的澄清**——改为「可前进到链上任意更靠后的状态」，而非开特例。

一并放开 `WRITTEN → OFFER`：只放开 `APPLIED → INTERVIEW` 会让规则变成「可以跳过笔试、不能跳过面试」，这条区分本身没有依据支撑。「不可回退」维持不变。

**二、TC-02 用例改造（三处）**

| # | 用例 | 改动 |
|---|---|---|
| 1 | `test_change_status_illegal_rejected` | 原 4 条参数中两条跳级组合（`APPLIED→INTERVIEW`、`APPLIED→OFFER`）**移出**（现已合法）；补入 4 条**回退**组合，共 6 条 |
| 2 | `test_change_status_skip_legal`（新增） | 3 条跳级路径：`APPLIED→INTERVIEW`（无笔试）、`APPLIED→OFFER`、`WRITTEN→OFFER` |
| 3 | `test_change_status_legal_chain` | 保留不动（逐跳路径须仍可用） |

**为什么补回退覆盖**：原非法参数只有 `CLOSED → WRITTEN` 一条回退路径。跳级放开后「非法」的语义收窄为**回退 / 原地 / 终态**三类，覆盖应随语义调整而补齐——否则「非法流转被拒」这项验收实际上只测了终态一种。

### 工作内容

**一、新增 `tests/test_sse.py`（18 条，TC-99~104）**

靶子是 `app/utils/sse.py` 的**协议层**，**不经 HTTP**——手写 `work` 生成器直接喂 `_drive`。这条路是后端「不继承 `StreamingResponse`」的决策换来的：协议层与 HTTP 解耦，断言事件序列比经 TestClient 读流更精确，也不必起服务。

| 组 | 条数 | 覆盖 |
|---|---|---|
| A 报文格式 | 4 | `event:` / `data:` 逐字节、中文不转义、`section` 可选、`tool_call` 载荷 |
| B 顺序与 start 首发 | 3 | `start` → `delta`×N → `done`；`work` 首行抛异常时 `start` 仍已发出；`start` 文案由调用方指定 |
| C done 载荷 | 2 | 取自 `work` 的 `return`；无 `return` 时两项均为 `null` |
| D 异常分派 | 4 | `BizException` → 其 code 与 message；未知异常 → 记堆栈 + `10000`（细节不进响应）；**delta 不撤回且不再发 done** |
| E 断连 | 3 | `GeneratorExit` 传播到 `work` 的 `finally`；协议层**不吞**该异常（用 `throw` 而非 `close` 才能区分）；断连后不再产事件 |
| F 独立会话 | 2 | Spy 替换 `SessionLocal`，断言创建一次、正常与异常路径均关闭 |

> **E 组第 2 条的测法值得记一笔**：`gen.close()` 对「重新抛出」与「吞掉 `GeneratorExit`」两种写法的表现**一样**（都是正常返回），分不出来。改用 `gen.throw(GeneratorExit)`——重新抛出时异常传给调用方，吞掉则只得到 `StopIteration`，这才有区分度。
