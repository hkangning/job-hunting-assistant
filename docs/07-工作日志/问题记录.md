## 维护约定

1. 每个问题一条记录，分配**唯一编号 `IS-XX`**，按发现顺序递增，编号**不复用、不跳号**；
2. **不改写历史条目**——问题状态变化时只更新「处理」「结论」「状态」三栏，原始描述保持原样；
3. 状态取值仅三种：

   | 状态 | 含义 |
   |---|---|
   | ✅ 已解决 | 已处理完毕并经验证 |
   | ⏳ 待处理 | 尚未处理，或部分完成、剩余部分依赖后续步骤 |
   | 🚫 不处理 | **必须写明理由**——分两类：经双方商讨后忽略，或属设计内的已知行为 |

4. 「不处理」最需要写明理由（谁定的、依据哪份文档的哪一条）。本表存在的意义就是让**当时的判断可追溯**，避免日后重复讨论同一个问题；
5. 范围不限于前端/测试：发现的文档问题、后端实现问题、协作流程问题一律记入；
6. 本文件位于 `docs/07-工作日志/`，属**公共文件**，改后需与 `backend` 分支互相拉取同步。
7. **本文件由测试负责人（卢世君）统一维护，后端侧不主动修改**——后端发现问题时先记入[后端工作日志](后端工作日志.md)并知会测试负责人，由其分配编号登记入本表；后端侧引用本表时**只读**。

| 项 | 内容 |
|---|---|
| 发现日期 | 2026-09-24（步骤 2 测试，准备编写建表冒烟时） |
| 类别 | 测试基础设施 |
| **问题** | `tests/conftest.py` 的 `client` fixture 直接使用生产 engine（`sqlite:///./app.db`）。任何触发应用 `lifespan` 的测试都会在**开发库**上建表、导入 120+ 道种子题、插入初始行 |
| **影响** | 违反测试计划 §1.1「测试数据库不碰开发库」；本步的建表冒烟需反复执行初始化，不修复则无法安全编写 |
| **处理** | 改为在 `conftest.py` **模块级**（早于任何 `app.*` 导入）把 `DATABASE_URL` 指向临时目录下的独立 SQLite 文件——`app/config.py` 的 `Settings` 在模块导入时即读取环境变量，晚一行就固定成开发库；会话结束先 `engine.dispose()` 再删目录 |
| **结论** | 修复后开发库全程零污染（5 个任务期间 `app.db` 始终未被创建），临时目录无 `jobpilot-test-*` 残留 |
| **状态** | ✅ 已解决 |

## IS-03 · 默认值无法通过查表结构验证

| 项 | 内容 |
|---|---|
| 发现日期 | 2026-09-24（步骤 2 测试设计阶段） |
| 类别 | 技术陷阱 |
| **问题** | SQLAlchemy 的 `default=` 是 **Python 侧默认值**，在 DDL 中**不产生 `DEFAULT` 子句**。若按常规思路查 `PRAGMA table_info` 的 `dflt_value` 来验证默认值，会得到全 `NULL` |
| **影响** | 会导致误判「枚举默认值未设置」，或写出永远通过（永远为空、断言不到东西）的假测试 |
| **处理** | 改为**行为验证**：插入一行**不指定**该列，再读回断言（如 `application.status` 读回应为 `"APPLIED"`） |
| **结论** | 用例 9 / 10 依此设计，11 处枚举默认值 + 整型 / 文本默认值全部验证通过 |
| **状态** | ✅ 已解决 |

## IS-09 · conftest 两套隔离方案被手工合并，测试全线不可用

| 项 | 内容 |
|---|---|
| 发现日期 | 2026-09-24（步骤 3 提交后、合入 `origin/frontend` 时） |
| 类别 | 流程 / 合并冲突解决 |
| **问题** | `tests/conftest.py` 被拼进**两套测试库隔离方案**：测试侧步骤 2 交付的**模块级 `DATABASE_URL` 环境变量**方案，与步骤 3 改造的**逐用例替换全局 engine** 方案；拼接时 `create_engine` / `sessionmaker` / `Session` / `Generator` 等 import 一并丢失 |
| **影响** | `pytest` 直接收集失败（`NameError: name 'Engine' is not defined`），43 条用例一条也跑不了。**更隐蔽的风险**：若只补 import 了事，`tests/test_database_init.py` 用的是模块级 `from app.database import engine`——替换方案对它无效（只改模块属性，改不掉用例里已绑定的名字），那 15 条建表冒烟会**真实打在开发库上** |
| **处理** | 以**模块级 `DATABASE_URL` 为唯一隔离底座**（对全部用例一视同仁，且是 test_database_init 的依赖），三个 fixture 改为基于全局 `engine` / `SessionLocal`；另加每例 `_reset_database()`（`drop_all` + `create_all`）保证用例间互不干扰；临时目录清理加三次重试（Windows 句柄释放有延迟，一次 `rmtree` 会出现「文件删掉、空目录留下」） |
