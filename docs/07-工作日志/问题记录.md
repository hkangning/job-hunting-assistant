## 维护约定

1. 每个问题一条记录，分配**唯一编号 `IS-XX`**，按发现顺序递增，编号**不复用、不跳号**；
2. **不改写历史条目**——问题状态变化时只更新「处理」「结论」「状态」三栏，原始描述保持原样；
3. 状态取值仅三种：

   | 状态 | 含义 |
   |---|---|
   | ✅ 已解决 | 已处理完毕并经验证 |
   | ⏳ 待处理 | 尚未处理，或部分完成、剩余部分依赖后续步骤 |
   | 🚫 不处理 | **必须写明理由**——分两类：经双方商讨后忽略，或属设计内的已知行为 |

4. 「不处理」最需要写明理由（谁定的、依据哪份文档的哪一条）。本表存在的意义就是让**当时的判断可追溯**，避免日后重复讨论同一个问题；
5. 范围不限于前端/测试：发现的文档问题、后端实现问题、协作流程问题一律记入；
6. 本文件位于 `docs/07-工作日志/`，属**公共文件**，改后需与 `backend` 分支互相拉取同步。
7. **本文件由测试负责人（卢世君）主导维护**（编号分配、表结构、新条目登记）——后端发现问题时先记入[后端工作日志](后端工作日志.md)并知会测试负责人，由其分配编号登记入本表；后端侧**新增条目与结构只读**。
8. **谁处理谁标注（2026-09-26 起）**：条目处理完毕后，由**实际处理方**直接更新「处理」「结论」「状态」三栏，并同步文末「状态统计」——后端侧闭环的条目由**后端侧自行标注** ✅ 已解决 并写明依据（文件 / 版本号 / 命令结果），不再等测试侧结案；前端 / 测试侧闭环的条目由测试侧标注。标注只动上述三栏 + 状态统计，原始「问题」「影响」描述保持原样（见第 2 条）。

## IS-03 · 默认值无法通过查表结构验证

| 项 | 内容 |
|---|---|
| 发现日期 | 2026-09-24（步骤 2 测试设计阶段） |
| 类别 | 技术陷阱 |
| **问题** | SQLAlchemy 的 `default=` 是 **Python 侧默认值**，在 DDL 中**不产生 `DEFAULT` 子句**。若按常规思路查 `PRAGMA table_info` 的 `dflt_value` 来验证默认值，会得到全 `NULL` |
| **影响** | 会导致误判「枚举默认值未设置」，或写出永远通过（永远为空、断言不到东西）的假测试 |
| **处理** | 改为**行为验证**：插入一行**不指定**该列，再读回断言（如 `application.status` 读回应为 `"APPLIED"`） |
| **结论** | 用例 9 / 10 依此设计，11 处枚举默认值 + 整型 / 文本默认值全部验证通过 |
| **状态** | ✅ 已解决 |

## IS-17 · `<script setup>` 顶层变量不是模块级，「会话内只播一次」失效

| 项 | 内容 |
|---|---|
| 发现日期 | 2026-09-25（步骤 7 前端，CDP 驱动真实交互时暴露） |
| 类别 | 前端缺陷（框架语义） |
| **问题** | `Welcome.vue` 把「会话内只播一次」的标记写成 `<script setup>` 顶层的 `let played = false`，期望它是模块级、跨组件实例共享。实际上 `<script setup>` 的顶层代码属于 `setup()` **函数体**，**每次组件实例化都会执行一遍**——标记每次进页面都被重置为 `false` |
| **影响** | 入场动画「同一浏览器会话内只播放一次」（SRS §3.13.3 第 3 条）失效：SPA 内每次进入 `/welcome` 都重播 |

| **处理** | 标记移入普通 `<script>` 块——与 `<script setup>` 并存时，普通块的内容处于模块作用域，只求值一次 |

| **状态** | ✅ 已解决 |

## IS-30 · 空态判定应看「是否真的什么都看不到」

| 项 | 内容 |
|---|---|
| 发现日期 | 2026-09-26（试用中追问：「那没数据的情况该显示什么呢」。此前已就空态提过一次：「没数据让我导入或者投递，我总得知道有啥能投的吧」） |
| 类别 | 交互设计 |
| **问题** | 当前空态引导卡的判定条件是 `stats.application_count === 0`（**零投递**）。但「没数据」不止一种：<br>① **零投递 + 校招情报有岗位**——用户**有东西可投**，而引导卡却说「还没有投递记录」并把「查看校招情报」做成一个**按钮**，等于让用户先跳出去找信息；此刻正确形态应是**直接把岗位 / 宣讲会显示出来**（它是本页唯一有内容的部分）；<br>② 零投递 + 校招也空——引导卡才是对的；<br>③ 有投递但今天没事——已按「一句说明 + 底部状态条」处理 ✓ |
| **影响** | **步骤 21/22 落地后，条件 ① 会变成常态**：用户注册后尚未投递、而系统已聚合了多校岗位——此时首页显示一张「还没有投递记录」的引导卡，**把唯一有信息的内容藏到了二级页面**，首页又变成"没东西可看"——正是此前两次讨论要避免的那个结果 |
| **处理** | **经讨论确定**：空态判定改为 **「是否真的什么都看不到」**——即 `application_count === 0` **且**校招情报（`campus_events` / `top_job_postings`）也为空时，才显示引导卡；任一侧有内容就正常渲染区块。**本步（步骤 9）不落地**：校招四项由后端按契约固定返空值（数据源属步骤 21~22），条件 ① 当前**不可达**，现在改是空改。**待步骤 22 落地后由前端调整**（一处 `isEmpty` 判定 + 引导卡文案需按场景区分：全空时说"还没有任何信息"，仅无投递时说"看看这些机会"） |
| **结论** | 前端已记录，随 **步骤 23**（校招情报前端）实现；**后端侧已闭环**（2026-09-26）：该口径已写入系统设计 **v1.17 §4.8**「空态口径」——判定以「是否真的什么都看不到」为准（零投递 **且**校招情报为空才显示引导卡），文案分「全空」/「仅无投递」两场景，实现时以该节为准 |

> **2026-09-26 补充（同一主题的另一面，前端自纠）**：做「有内容才显示」时**把校招情报区块也套了进去**，结果概览页只剩投递相关内容（待面试 / 跟进 / 投递统计），试用中当即指出「这样这个功能不还是跟投递管理冲突吗，我想要的是这个今日概览不只是提醒我今天干啥，还有能够获取一手招聘新闻啥的入口」。
>
> **结论：待办类区块与入口类区块的显隐规则不同**——**待办没内容时该收起，入口没内容时也该在**（入口本身就是内容，藏起来等于砍掉一条路径）。
>
> **已修正**（前端侧）：校招情报**始终显示**，无内容时以一句说明 +「去发现机会」承担讲清用途的职责；「今天没事」的判定**排除校招**（它是常驻入口，不算待办）。**请后端一并补进系统设计 v1.17 §4.8**（该节已含空态口径，本条是它的姊妹条款：「区块显隐——待办类有内容才显示，入口类始终显示」）。
| **状态** | ⏳ 待处理（后端侧口径已落系统设计 §4.8；前端实现待步骤 23） |

## IS-32 · 断连半成品无完成标记，前端识别可能漏判

| 项 | 内容 |
|---|---|
| 发现日期 | 2026-09-26（步骤 12 断连冒烟） |
| 类别 | 设计 / 口径 |
| **问题** | 客户端断开时已生成内容会**照常落库**（接口文档 §3.6 明确为预期行为，与「中途失败不落库」相反），但库表**无独立「未完成」标记字段**，文档给的判据是「`score` 为空**且**文本明显偏短」。步骤 12 实测：断点落在分数行之后时 `score` 有值（**89**）、而文本仅 **115 字**（完整报告 1200+ 字）——前端只按 `score === null` 判断，**不会**标出这条半成品 |
