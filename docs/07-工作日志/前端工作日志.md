### 工作内容

按开发计划步骤 1 分给前端的清单执行：

- 初始化 Vite + Vue 3 工程（**JavaScript 而非 TypeScript**，依据项目结构文档第 3 节全部标注 `.js`）；
- `vite.config.js`：端口 5173（与后端 CORS 白名单一致），`/api` 代理至 `http://localhost:8000`，**不做 rewrite**（后端路径本身即 `/api/v1/*`）；
- 路由表 9 条：8 个菜单页 + 1 个隐藏页（`/interview/:sessionId`，不进菜单）；
- 布局三件套：`App.vue`（容器骨架 + 折叠状态）、`components/SideNav.vue`（菜单渲染 + 路由高亮）、`components/AppHeader.vue`（折叠按钮 + 页面标题 + `actions` 插槽）；

- 9 个占位页 `src/views/*.vue`，统一 `el-empty` 占位并标注对应开发步骤；
- `main.js` 挂载顺序：Pinia → Router → Element Plus（全量引入 + `zh-cn` locale）。

### 工作内容

**一、拖拽失效（功能缺陷）**

根因：`canDropTo` 读 `to.el.dataset.status`，而 `to.el` 是 sortablejs 挂载的**列表元素** `.kanban__list`，`data-status` 却绑在父级列容器 `.kanban__col` 上 → 取到 `undefined` → `canTransit(状态, undefined)` **恒为 false** → 所有落点被静默拒绝。修复：属性改绑 draggable 根元素，并以 `closest('[data-status]')` 兜底。

**二、页面改版（布局与信息密度）**

试用反馈"不能一眼看全""一半多页面是空白"。实测取证：看板 `scrollWidth 1336 > clientWidth 1136`（第 5 列被截断）、看板底部距内容区底 **362px 全空**、列宽固定 256px × 5 排不下。改版：

- 列宽等分自适应（`flex: 1 1 0`），**消除横向滚动**；看板 `flex: 1` 撑满剩余高度，列内滚动；
- 新增**统计条**：总数 / 本周新增 + 状态占比堆叠条 + 计数图例（指标全部由已拉取数据现算，不新增接口）；
- 卡片改高密度排版，删除图标改 hover 显示，空列改矮虚线框；
- 数据量策略：**循环翻页拉全**（接口 `page_size` 上限 50，封顶 500 条并提示），列内滚动。

**三、配色调整（全站）**

试用反馈"不优美、太严肃"。定位：原配色（品牌紫 `#6B4E9E` + 深蓝 / 暗琥珀 / 墨绿）是"作战面板"调性，而**求职本身是压力源，界面不该加重紧张感**。改为提亮降饱和的清爽蓝紫：品牌 `#7A6BC4`、已投递 `#5B8DD9`、面试中 `#E0A030`、offer `#4CB782`、页面底 `#F7F8FC`。**不改色相**——蓝=起点、紫=笔试、琥珀=进行中、绿=成功、灰=结束这套语义本身是对的。

**四、卡片精简（消除截断）**

试用反馈"卡片信息显示不完整"。根因：**三个字段挤在一行**（"Java 后端开发 · 南京 · BO⋯"）——既没显示全、又占地方，是最糟的组合。改为一行一个信息：公司 / 岗位 / 投递天数 + 排期；城市 · 渠道 · 薪资 · 备注移到详情（点卡片）。卡片左侧色条改按**该列状态色**着色。

**六、状态机放开 + 结束原因（需求变更）**

- 试用实测"已获 offer 拖不到已结束"→ 根因是 SRS FR-004 把 `OFFER` 定为终态，业务上拒 offer / offer 撤回 / 谈崩都无法标记。经讨论**放开**（SRS v1.3）；

**七、过程中修掉的两个真 bug**

1. **文字竖排**（试用中发现"有些卡片竖着写"）：`.kanban-card__days` 缺 `white-space: nowrap`，作为 flex 子项默认可收缩，在"有排期 + 列宽偏窄"时被压到一字宽、中文逐字换行。多视口复现：1024 视口下被压成 20px、900 视口下 14px。修复：加 `nowrap + flex:none`，并给列设 `min-width: 168px`（实测出的下限），宽度不足时改为横向滚动而非压扁内容；
2. **确认结束的卡片被误还原**：`CloseReasonDialog` 的 `el-dialog` 关闭时一律触发 `@close`，我在那里无条件 `emit('cancel')`，导致**确认路径也被当成取消**、卡片被还原到原列。修复：加 `confirmed` 标志区分"确认后关闭"与"用户取消"。

**八、城市筛选改造：级联选择（试用中提出并迭代一次）**

原为纯文本输入框，讨论中提出"输入或自主寻找，按省份然后城市"，进一步明确为"**先出省份、点省份再出城市**"的级联交互。最终用 `el-cascader`（`show-all-levels=false` + `filterable`）实现，**未新增运行时依赖**。

配套新增 `src/constants/regions.js`（34 省级 / **747 城市** / 37.7 KB）。数据自 `element-china-area-data@6.1.0` 的 `regionData` **构建期提取一次**后内嵌，**运行时不含该依赖**（`npm install --no-save` 装、用完即删）。三条口径：

- **value 去掉尾部「市」字**——库内既有数据存的是「南京」而非「南京市」，不去后缀会让选择结果与历史数据分裂成两个筛选条件（显示仍为「南京市」，只 value 去后缀）；
- **第二级 = 地级市 + 该省下辖的县级市**（昆山、常熟、江阴等）——否则「投递到县级市」就筛不到，只能用公司关键字捞；实测 747 个可选城市；
- **直辖市不设第二级**（其下辖是「区」，市一级就是它自己），列表中直接选中；数据包只含大陆 31 个省级行政区，港澳台手工补齐。

**筛选与表单共用同一份数据**（表单的城市字段一并换成同一选择器）：否则录入时手写「昆山市」、筛选选「昆山」，两种写法在精确匹配下会分裂成两批。表单对**列表外的历史自由文本**做了兜底——若记录的城市不在省市列表中，则临时补一个「（原值，不在省市列表中）」的一级选项，保证能回显、不被静默清空。

筛选语义未扩展（仍是按城市精确匹配，后端未改）。

### 工作内容

试用后提出三项反馈。三项均先实测取证再定方案。

**一、城市选项收敛到地级市**

`constants/regions.js` 整体重新生成：数据源由原来的混合口径改用 `element-china-area-data@6.1.0` 的 `pcaTextArr`（省-市-区三级）**第二级**——该级本身即纯地级市（江苏 13 项），无需按行政区划代码推断；另排除 label 含「直辖县级行政区划」的占位项（河南 / 湖北 / 海南 / 新疆各 1 项）。可选中城市 **747 → 346**（二级选项 741 → 340，一级直达 6 项不变）。筛选栏与表单同源导入，改数据即两处生效。

**二、边框可见性**

试用反馈"卡片边框看不见，趋势图的边界也是"。实测：看板列 / 卡片 / 统计条 / 趋势图容器边框均为 `1px #ECEBF5`，对白色卡片**对比度仅 1.18:1**——不是"偏淡"，是实际不可辨。

- `--c-border` `#ECEBF5` → `#CFCBDD`（1.18:1 → **1.59:1**），一处 token 全站生效；
- `--c-divider` `#F3F2FA` → `#EAE8F2`：趋势图水平网格线用的是这个 token，边框加深而网格线不动会让图内依旧发虚；两者仍保持"分隔线比边框弱一档"的层级关系；
- **顺带修根因**：`TrendChart.vue` 内 5 处色值是 token 的**硬编码副本**（ECharts 画在 canvas 上读不到 CSS 变量，当初只能写死），后果是"改 token 图表不跟随"。改为 `buildOption()` 时经 `getComputedStyle` 取实值，回落值保留原色值。

**三、按钮尺寸与层级**

实测发现「查看趋势」**高 32px、热区 86×32**，与筛选输入框等高——**尺寸并不小，问题是 `border: 0px`**：它用的是 `text` 类型，在设计文档 §4.5.4 的三级体系里属「纯图标（工具性）」级，而它是有文案的次操作。按"放大尺寸"处理会改不到病根，故改为**主题色描边按钮**。真正偏小的是顶栏两按钮与趋势图区间切换（24px / small 档），一并提到默认档。

### 工作内容

**一、布局分两套壳（`meta.layout`）**

账号页（`/welcome`、`/login`、`/register`）需全屏无侧栏顶栏，业务页沿用现有布局。做法：路由加 `meta.layout: 'blank'`，`App.vue` 按 `route.meta.layout` 条件渲染。**未采用嵌套路由**——账号页是少数派（3 vs 10），把多数派降为 children 意味着重写 `SideNav` 的菜单派生与守卫逻辑，而步骤 4 刚验收的 9 个页面全部受影响；标记"例外"的回归面最小。

**二、dev-only mock 层（本步关键取舍）**

`frontend/mock/` 五个文件 + Vite 插件中间件。`VITE_USE_MOCK=true` 时接管全部 `/api/v1/*`，**同时不注册 `/api` 代理**（二者互斥，避免"谁先命中看实现细节"的脆弱依赖）。

- **全量自洽**，而非"只 mock 账号接口 + 业务接口透传真后端"：后者在两种时刻翻车——后端未做鉴权时能跑通（假象）；一旦后端推上步骤 5 鉴权，mock 签发的假 Token 立刻被判 401、触发全局登出、界面全崩。"验收时好跑、联调时崩"远比"离线自洽"危险；
- mock 实现**真实业务逻辑**而非固定桩：用户名唯一（不区分大小写）、首个账号 `ADMIN`、连续失败 5 次锁 5 分钟、改密作废旧 Token（`password_changed_at` 比对 `iat`）、头像 multipart 字节存取与静态返回；
- 额外提供 `POST /__mock__/reset`（清内存库），使断言脚本可重复执行——否则"首个账号应为 ADMIN"这类断言跑第二次必失败。

**三、账号状态与请求层**

- `useUserStore`：Token 持久化 localStorage（key `jobpilot_token`）、用户信息、`displayName` / `avatarImg` / `fallbackAvatar`（首字 + 哈希底色，纯前端生成）；
- **`reset()` 与 `logout()` 分离**：`reset()` 只清本 store（供 401 拦截器调用，跳转由拦截器统一控制，避免 store 反向依赖 router）；`logout()` 额外 reset 其余 store（对应 TC-66 账号切换无数据残留）；
- `request.js`：请求拦截器注入 `Authorization: Bearer`；响应拦截器识别 `80001/80002` → 清状态 + 提示 + 跳登录页，**带 `silent` 的请求只清状态不跳转**（`/welcome` 的 Token 预检用它）；
- 路由守卫**读 localStorage 而非 store**，避免"路由模块 ↔ store 模块"循环依赖；免登录页用**显式白名单**而非反向推断，避免新增页面时漏判。

**四、入场动画（按系统设计 §4.6 时间轴）**

纯 CSS `@keyframes`，零第三方库：logo 0.5s `scale .8→1` + 淡入、主标题逐字浮现（500ms 起、每字 80ms 交错）、副标题 1.6s 淡入、进度条 2.5s 走完、2.1s 后整体淡出。Token 预检与动画**并行**（不阻塞播放，失败只改跳转目标）；点击任意处 / 按任意键跳过；`prefers-reduced-motion: reduce` 时直接跳转。

**「会话内只播一次」的载体选择**：用**模块级内存标记**而非 `sessionStorage`，由此三方口径同时满足——SPA 内跳转不重播（SRS §3.13.3 第 3 条）、刷新 `/welcome` 重播（设计文档 §4.6 + TC-62）、已登录用户刷新业务页根本不经过 `/welcome`（SRS 第 4 条）。SRS 与设计文档在此处的表述差异因此无需改文档即可自洽。

**五、登录页与注册页**

共用 `AuthShell`（深紫渐变全屏 + 居中白卡片）。登录：用户名 / 密码 /「30 天免登录」勾选（`remember_me` 决定 1 天或 30 天 Token）；错误在**表单内**提示（调用带 `silent`，不弹全局 toast——接口文档规定 80004 的前端动作是"登录表单整体提示"）。注册：密码强度**只提示、不拦截提交**（SRS 明确"给出强度提示但不拦截"），仅"两次密码不一致"这类填错才拦截；80003 回传后用户名输入框标红；注册成功即自动登录进首页。

**六、用户菜单与侧栏调整**

`UserMenu`（头像 + 用户名 + 下拉：个人中心 / 设置 / AI 配置 ｜ 退出登录末位分隔），挂顶栏最右。侧栏**摘掉「系统」组**（`/settings` 加 `hidden`）——设置迁入用户菜单后若侧栏保留会出现两个入口。`/ai-config` 建占位页（步骤 8 填充）。

**七、个人中心**

账号信息卡（128px 大头像 + 可编辑昵称/邮箱 + 角色标签 + 只读 meta）/ 数据概览 3 小卡 / 修改密码 / 求职画像 12 字段。头像走 **canvas 居中裁切压 256×256**（jpeg 0.9）后上传，渲染路径统一为 `/static/avatars/<文件名>`（后端存 `uploads/avatars/x.png`，故取文件名再拼）。改密成功后清 Token 跳登录页。

**八、过程中修掉的两个真 bug**

1. **"会话内只播一次"失效**：`<script setup>` 的顶层代码属于 `setup()` 函数体，**每次组件实例化都会执行**，`let played = false` 写在那里等于每次进页面都重置。CDP 复现：SPA 内第二次进 `/welcome` 仍播动画。修复：移到普通 `<script>` 块（模块作用域）。已记入 IS-17；
2. **刷新业务页时顶栏用户名/头像空一截**：store 随页面重建后 `user` 为 `null`，而顶栏依赖它渲染。修复：`AppHeader.onMounted` 在"有 Token 且无 user"时补拉一次 `fetchMe`（非 silent，Token 已失效时由拦截器统一跳登录页）。

**九、交付后即时修订：入场动画时长（试用反馈）**

试用反馈："动画时长再缩短一些，感觉改成当前时间的四分之三或者三分之二比较好"。取**四分之三档 → 1.8s**，并**顺带修正一处实现偏差**：

| 项 | 原 | 现 |
|---|---|---|
| 动画主体 | 2.5s | 1.4s（计时到 `TOTAL_MS - LEAVE_MS` 即开始收尾） |
| 末段整体淡出 | 在 2.5s **之外**再加 0.4s | **含在 1.8s 之内** |
| **实测「进入到跳转」** | **约 2.9s** | **1718ms** |

原实现把「总时长约 2.5s（末段 0.4s 淡出）」读成了「2.5s 播完**再**淡出 0.4s」，实际比口径长了整整 0.4s——用户感受到的"偏长"里有一半来自这处偏差。本次一并纠正：**1.8s 即"进入到跳转"的总时长**。

逐字节奏同步加密（间隔 80ms → 60ms、起始 500ms → 400ms）；进度条时长改读 CSS 变量 `--welcome-duration`（由 JS 的 `TOTAL_MS` 下发）——**时长参数由此收敛为单一出处**，下次再调只需改 `TOTAL_MS` 一个数，不会再出现"JS 计时器与 CSS 动画各写一个数"的漂移。

### 工作内容

**一、两项形态决策（开工前经讨论拍板）**

| 决策点 | 选定 | 理由 |
|---|---|---|
| 12 张卡片 | **折叠卡片，点击展开编辑** | 每张卡要容纳 Key + base_url + 模型 + 四个按钮，全展开页面长达 2500px+ 且 12 个 Key 输入框同屏很吵；折叠后每张约 60px，状态一屏半看全 |
| 设置页保存 | **统一「保存设置」按钮** | 与个人中心画像表单一致；含讯飞凭据这类敏感输入，显式提交语义更清晰；实现上是「快照 diff → 一次 PUT」，不产生半保存状态 |

**二、AI 配置页 `/ai-config`**

- 页面持有 `providers` 列表为唯一数据源，按后端返回的 `group` 分组（国内/国外/聚合/本地/自定义，5/4/1/1/1）；卡片动作完成后 emit `changed` 由页面**整体重拉**——`is_active` 是互斥关系，局部更新会在切换后留下两个「当前使用中」；
- **卡片与页面的职责线**：改变持久化状态的动作（保存/激活/删除）与只读探测（拉模型列表/测连通性）都由卡片发起，前者完成后通知页面刷新全局数据，后者结果**就地展示**（`silent`，不弹全局 toast）；
- 状态标签严格取 SRS 三态，形态用**色点 + 文字**（系统设计 §4.5.4：一屏 12 张卡片若都是彩色胶囊会互相叫喊）；
- 模型列表**展开时才拉取**（否则进页面就打 12 个请求），同一次页面停留内不重复请求，「刷新」按钮带 `refresh=true` 强制重拉；`source=builtin` 时标注「内置列表（上次拉取失败）」；
- 页面级三态：加载失败给「重试」按钮；`active=null` 时顶部提示「尚未配置可用的 AI 供应商，AI 功能暂不可用」。

**三、实现中发现的一处设计缺陷（本步最有价值的发现）**

首轮联调断言暴露：`custom` 卡片点「测试连通性」报**「请先选择模型」**，链路根本走不通。根因是三方约束叠加——① `custom` 在注册表里 `default_model=None`；② 后端 `test_connection` 无模型可用时直接拒绝；③ 模型列表接口**只认已保存的 Key**（未保存则 10012）。于是形成死结：**测试连通性要选模型 → 选模型要先保存 Key → 保存 Key 前又拉不到模型列表**。

修复：模型下拉加 `allow-create`，**支持直接手输模型 ID**。这既解开了死结，也顺带覆盖「断网回退内置表不含新模型」「列表外模型」等场景——自定义端点上的模型 ID 本就不可预知，只给下拉选择是不完整的。设计文档已同步该调整。

**四、设置页 `/settings`**

- 三组：语音交互 / 模拟面试 / 就业网抓取；**LLM 相关字段全部移除**（本步验收项）；
- 统一保存 + 快照 diff：只提交变更字段（接口为部分更新语义），布尔严格传布尔（接口对非布尔值一律 10001，不做隐式转换），讯飞凭据留空 = 不修改；
- 联动：`asr_provider=xunfei` 时才显示讯飞凭据；`tts_enabled=false` 时音色禁用；`crawl_enabled=false` 时目标地址禁用；就业网抓取组标注「系统级配置：任一账号修改后对全部账号生效」；
- 加载后写入 `useAppStore`，供后续步骤（13 陪练题量、22 语音开关）取用——`stores/app.js` 无需改动，现有 `setSettings` 即可。

| 对应分支 | `frontend` |
| 上游依据 | 试用反馈 / 接口文档 §3.3 / 问题记录 **IS-27** |

### 工作内容

**一、模型列表为什么非要 Key（对设计的疑问，先查证）**

**不是前端加的锁，是接口契约**：`GET /llm-providers/{provider}/models` 的 Key 只取当前账号**已存配置**（`get_models` 里 `decrypt_text(row.api_key)`），不接受传入；而**同组的** `POST /llm-providers/test` 是接受传入的——同一页面两个探测接口口径不一，容易被读成前端限制。技术上模型列表也确需认证：供应商的 OpenAI 兼容 `GET /models` 要 Bearer Key（`ollama` 本地不需要、OpenRouter 列表公开，属少数派）。

**处置**：前端能做的先做（保存后自动拉取，见下），**根治转后端**——登记 **IS-27**，请后端给该接口加可选 `api_key`（与 `/test` 同口径），具体形式（query 参数 / 改 POST）由后端定，前端不猜实现。

**二、保存后自动探测（本次核心改动）**

原先要手动点「测试连通性」，现在**保存成功后自动拉模型列表 + 自动测连通性**，结果就地展示——用户填完 Key 点一次保存就能看到「连通正常（模型：xxx）」和可选模型，不必再点两下。

两处实现细节：

- **不把测试合并进保存请求**：保存应当只负责"存"（快速返回）。合并的话，测试超时会拖累保存，且测试失败会让人误以为配置没存上。现在是保存成功后**并行**触发两个探测，各自更新各自的状态；
- **`loadModels` 加 `force` 参数**：保存成功那一刻 Key 刚落库、但 `props` 还没随页面重拉刷新，照常检查 `key_set` 会被误拦——`force=true` 跳过该前置检查。

**三、删除提示补全**

原文案只说「删除后 AI 功能将不可用」——反过来说，**没说删掉什么、能否恢复**。改为两段式：

- 固定段：将一并删除该供应商的 **API Key、所选模型、自定义端点与模型列表缓存**；
- 后果段：激活项 →「该供应商当前正在使用，删除后 AI 功能将不可用」；非激活项 →「删除后需重新填写才能使用」。

多行提示用 `dangerouslyUseHTMLString` 渲染，但 **HTML 内不含任何动态内容**（供应商名只出现在纯文本标题里），无注入面。

### 工作内容

**一、问题定位**

截图确认：新账号（零投递）打开首页时，5 张统计卡全是 `0`、两个列表各剩一行灰字、快捷入口被挤在右下角——**唯一的"可用入口"面积最小，而没有信息量的部分占据了首屏最显眼的位置**。

根因是布局照「有数据」的情形设计：统计卡的设计前提是"一屏看到各状态分布"，无数据时这个前提不成立。

**二、方案（经讨论确定：空态引导卡）**

| 项 | 设计 |
|---|---|
| 触发条件 | `stats.application_count === 0`——**不是**「统计卡恰好全 0」（那可能只是各状态暂无记录） |
| 替换范围 | 统计卡 + 待面试 + 跟进列表 → **一张引导卡**；快捷入口也省去（引导卡里已是主要入口） |

| 恢复 | 有投递后自动回到常规布局（同一份数据驱动，无额外状态） |

**三、过程中的一处实测发现**

首版引导卡下方留白仍大，加大 `min-height` 撑满内容区后反而**整页出现滚动**（卡片底部溢出到视口外）。凭肉眼只看到"内容偏下"，**实测几何**才定位到真因：`box-sizing` 默认 `content-box`，`min-height` 只管内容区，加上上下 padding 80px 后总高变成 860 > 视口 900 的内容区高度。

修复：显式 `box-sizing: border-box` + `min-height: calc(100vh - 100px)`（视口 − 顶栏 56 − 内容区上下 padding 40，留 4px 余量）。复测：卡片高 800、底部 876（视口 900 内）、上下留白各 312（完全对称）。

**二、五处调整**（经讨论确定）

1. **移除首屏 5 张大统计卡**——它是现状而非行动，且占了最显眼的位置；
2. **移除「快捷入口」区块**——其中 JD 分析 / 模拟面试 / 八股陪练 / 错题抽问**侧栏已有**，而侧栏是常驻的，再放一遍没有信息增量；唯一有独立价值的「新增投递」顶栏本就有按钮；
3. **新增底部状态条**（紧凑一行：错题到期 + 投递各状态计数）——投递进度**不能删**（"今天没事可做"是常态，总得有东西看），但正确的位置是**兜底内容**而非首屏主角；
4. **各内容区块改为「有内容才显示」**——概览页每天都要打开，空区块（「暂无到期错题」之类）就是噪音；
5. 新增一句「今天没有需要处理的事，安心准备下一场面试吧」作为全空的兜底文案。

**调整后的形态**：待面试（明日置顶）→ 该跟进 → 校招情报 → 底部状态条。呈现的是"**今天有几件事**"，而不是"一堆面板 + 几行 0"。

| 项 | 内容 |

| 设计文档 | 设计稿与实现计划（过程文档，不入库） |

### 工作内容

**一、`utils/sse.js`：回调式 API**

```js
const { abort } = streamSSE('/stream/demo', { message }, { onStart, onDelta, onDone, onError })
```

选回调式而非 async generator：后续四条链路的用法都是「`delta` 累积到某个 ref、`done` 后刷新列表、`error` 后显示重试」这种分散更新，回调最直接；中止只需调 `abort()`，不必把 `AbortSignal` 一路透传给调用方。`onToolCall` 一并预留（步骤 19 的确认卡片用）。

**二、跨 chunk 边界是唯一的真坑**

SSE 的事件块可能被 TCP 拆到两个 chunk 里，按 chunk 边界解析就会把半截 JSON 喂给 `JSON.parse`。实现维护一个缓冲区，**只在 `\n\n` 处切分**：

```js
buffer += decoder.decode(chunk, { stream: true })
while ((idx = buffer.indexOf('\n\n')) !== -1) {
  emit(parseEvent(buffer.slice(0, idx)))
  buffer = buffer.slice(idx + 2)
}
```

非 SSE 响应单独给提示——`vite.config.js` 的 mock 与代理互斥，开着 mock 时 `/stream/demo` 无人应答，提示里直接点明「关闭 mock」。

**三、`StreamText.vue`：三档吐字**

纯展示组件（只收 `text` + `streaming`），用 rAF 追赶目标文本。吐字速度分三档：落后 ≤60 字每帧 1 字（60 字/秒，与 LLM 常见速率相当）、≤240 字每帧 2 字、更多每帧 5 字（长报告不至于永远追不上）。

**首版写的是 `lag / 8` 无上限提速，被联调证伪**：91 字时每帧吐 12 字、0.13 秒追平——打字机等于没做。无上限的「追赶」在短文本上退化成瞬移。

**四、`views/DevStream.vue`：不进导航的调试页**

路由 `/dev/stream` 带 `meta.hidden`（与 `/settings` 同款标记），侧栏不显示、只能手输 URL 访问。保留而非用完即删：步骤 12 起每条 AI 链路联调都要靶子，后端也已把 `/stream/demo` 定为常驻端点。页面内含事件日志（`start` / 首个 `delta` / `done` 的时间戳与载荷），核对首字延迟与事件顺序时不必开 DevTools。

### 验证

CDP 驱动 Edge + 真后端，三项实测：

| 场景 | 结果 |
|---|---|
| 打字机 | 页面内按帧记录：**895 帧有文本、86 种不同长度**，前 40 帧 `[1,2,2,2,3,4,5,…]` 逐字递增，最终 86 字与后端 `chars: 86` 一致；首字 1244ms |
| 中止 | 状态条「已中止（客户端主动断开）」、**无错误提示**、事件日志追加 `abort`、中止按钮转禁用 |
| 错误路径 | 未配供应商的临时账号：`start` 文案先出 → `error 10012`，事件序列 start → error |

另有 `npm run build` 通过、后端全量 **219 passed / 0 failed**。

> 首轮判「未通过」是**验证方法**的问题：CDP 每 0.2 秒采样一次正文长度，采到 `[0,0,0,0,0,24,91,91,…]`，看着像一步到位。改成页面内 rAF 逐帧记录才看清真实节奏——批量采样对「逐帧变化」这类现象本就无能为力。

### 结论与遗留

- 前端流式出口就绪，步骤 12 起四条 AI 链路直接复用 `streamSSE` + `StreamText`（`section` 分段由各链路在调用方处理，组件不用改）；

- **遗留**：无。

### 工作内容

**一、页面结构：左窄栏 + 右宽区**

左栏（320px）放输入与历史列表，右宽区留给报告——五段报告是长文本，需要横向空间；历史列表项只需显示「公司 · 分数 · 时间」，窄栏够用。后续三条链路（陪练 / 面试 / 面经）的页面结构可照此复刻。

## 全站字号与控件提档（试用反馈）

### 触发

用户试用后反馈：「主页左下角这个今日待办是不是太小了，还有很多按钮是不是也设计的比较小」。

### 诊断：不是单个组件的问题

代码级盘点：全站 `font-size` 声明 **95 处 / 21 个文件**，其中 85 处是 17px 以下的文字类字号，散落在 **11 / 11.5 / 12 / 12.5 / 13 / 14 / 15 / 15.5px 八种取值**上；`tokens.css` 未覆盖任何 Element Plus 尺寸或字号变量，控件全走库默认（按钮与输入框 32px、`size="small"` 24px）。

三条成因并存：

1. **字号阶梯照英文界面惯例定**——13px 对拉丁字母尚可，汉字笔画密度高得多，同字号下辨识成本明显更高；「今日待办」的 11px 标题 + 11.5px 条目是全站最小值；
2. **两套字号体系在打架**——Element 组件文字走库默认 14px，比项目自有的 13px 正文**还大 1px**，于是侧栏出现「菜单项 14px 紧挨着待办标题 11px」的 3px 落差；
3. **控件未做尺寸覆盖**——32px 是 Element 的桌面默认值，宽屏高 DPI 下偏紧。

故本轮处理的是整套尺寸体系，不是那一个组件：只放大待办卡，它与紧挨着的菜单项的比例关系仍然是错的。

### 改动

**一、字号阶梯收敛为 CSS 变量**（`tokens.css` 为唯一出处，21 个文件 85 处改为引用）：

| 变量 | 值 | 承接旧值 |
|---|---|---|
| `--fs-xs` | 12.5px | 11 / 11.5px |
| `--fs-sm` | 13.5px | 12 / 12.5px |
| `--fs-body` | 14.5px | 13px（正文） |
| `--fs-title` | 15px | 13px(700) 标题 / 14 / 15px |
| `--fs-h1` | 17px | 15.5px |

其中 13px 有 26 处，**正文与卡片标题混用**，需逐处判别：区块 / 卡片标题归 `--fs-title`，其余归 `--fs-body`。原口径「卡片标题靠字重不靠字号」随之改为字号 + 字重双通道——正文提到 14.5px 后，标题若原地不动会比正文还小。

**二、Element Plus 控件尺寸**：`--el-component-size` 32 → 36px（小号 24 → 30、大号 40 → 44）；`--el-font-size-base` 改为引用 `var(--fs-body)`（14.5px），使 Element 组件文字与自有文字同源。

**三、按钮需单独覆盖**（本轮最反直觉的一处）：`--el-component-size` 系列**只管输入框**——全库仅 `.el-input` / `.el-date-editor` / `.el-input-tag` 三个选择器引用它。`.el-button` 的规则里没有 `height`，32px 是 `padding 8px×2 + 行高` 凑出来的；`--el-button-size` 的 24 / 40px 又是**规则内硬编码**。照直觉只改尺寸变量会得到「输入框变大、按钮纹丝不动」，故三档按钮另行覆盖（用 `min-height` 而非 `height`，长文案按钮可自动撑高）。

**四、布局**：侧栏 230 → 248px、顶栏 56 → 62px；折叠态维持 64px（只显示色点、不承载文字，且其宽度是 `.el-menu--collapse` 的计算值）。

**五、消除两处硬编码**（执行中发现，原计划遗漏）：`App.vue` 的 `el-aside` 用 `:width` 内联传值、`el-header` 用 `height="56px"`，与 `tokens.css` 的 `--sidebar-w` / `--header-h` **各写了一遍**——只改变量会得到「品牌区 62px、顶栏 56px」的错位。两处均改为 CSS 读变量（二者 prop 默认值皆为 `null`，为 null 时不生成内联样式）。**教训：变量定义了 ≠ 有组件在读它。**

### 验证

`npm run build` 通过；静态扫描确认 85 处文字类字号**全部**改为变量引用，仅剩 9 处 17px 以上的图标 / 展示型值与 1 处 `font-size: 0`。

CDP 无头走查（Edge + Node 自带全局 WebSocket，零新增依赖），1440×900 视口、15 条路由：

| 项 | 改前 → 改后 |

| 顶栏高 | 56 → 62 |
| 「今日待办」标题 / 条目 | 11px / 11.5px → 12.5px / 13.5px |
| 「今日待办」卡内边距 | 11px → 14px |
| 侧栏菜单项 | 14px → 14.5px |
| 卡片标题 / 列表正文 | 13px / 13px → 15px / 14.5px |
| 默认按钮高 / 字号 | 32px / 14px → 36px / 14.5px |

全部断言 PASS；15 条路由横向溢出均为 0；层级关系（弱化 < 次要 < 正文 < 标题）无一处反转。

验证过程中修掉了脚本自身两处会造假的问题，一并记录：**视口未锁死**（`--window-size` 在 Edge 实例被转交时失效，实测视口只有 500px 宽，导致 15 页全报「横向溢出 100px」的假警报；改用 CDP `Emulation.setDeviceMetricsOverride` 锁定）；**登录态未按页切换**（已登录时访问 `/login`、`/register` 会被路由守卫重定向到首页，截到的其实是概览页；改为按页切换 token 并加「实际停留路由必须等于目标路由」的自检）。

## 按钮 loading 跳动修复（试用反馈）

### 现象

用户反馈：个人中心「保存画像」点击保存后按钮位置突然偏移、一闪后恢复，功能正常。

### 根因

Element Plus 的 `.el-button` 在 `loading` 状态会**真实插入一个图标节点**（见 button 组件的渲染分支 `loading ? createBlock(ElIcon, ...)`），它参与布局并把按钮撑宽：

| 状态 | 按钮宽 | 图标数 | 文字 x |
|---|---|---|---|
| 正常 | 90px | 0 | 307 |
| loading | 110.5px | 1 | 327.5 |

按钮左边缘恒定（x = 291），是**宽度被撑开**、文字跟着右移。撑宽量 = 图标 `1em`（14.5px）加上库内 `.el-button [class*=el-icon]+span { margin-left: 6px }` = **20.5px**，与实测分毫不差。库内只有 `:before` 遮罩是绝对定位的，图标不是。

**非本次字号提档引入**：改动前字号 14px，图标 14px + 6px = 原本就跳 20px，本次只是把它变成了 20.5px。

**波及范围**：全站 **14 处**带 `:loading` 的按钮（9 个文件）——登录 / 注册 / 保存设置 / 保存修改 / 修改密码 / 导入对话框 / 供应商弹窗…，不止「保存画像」。

### 修复

`tokens.css` 加一条全局规则（一处生效，14 处全受益）：loading 图标绝对定位居中、同时隐藏文字，按钮宽度恒定。

**第一版修复漏了一层**：把图标改为绝对定位后，跳动从 20.5px 只降到 **6px**——因为图标仍在 DOM 里当着 span 的前一个兄弟，`.el-button [class*=el-icon]+span` 这个**相邻兄弟选择器照样命中**、照样给文字加 6px 外边距。补上 `margin-left: 0` 之后才归零。根因比第一版判断更细一层。

### 验证

逐帧记录（CDP + `requestAnimationFrame` 逐帧采样；给 `PUT /profile` **注入 1500ms 延迟**——mock 是即时返回的，loading 态一帧都不渲染，不注入延迟根本复现不出来）：

| 阶段 | 记录帧数 | 变化帧 | 按钮宽度 |
|---|---|---|---|
| 修复前 | 798 | 365 | 90 → 110.5px |
| 第一版修复 | 795 | 360 | 90 → 96px |
| 最终修复 | 794 | **0** | 90px 恒定 |

回归：`npm run build` 通过；概览 / 个人中心 / 设置 / 登录四页的正常态尺寸与修复前**逐项一致（0 处差异）**——该规则只在 `.is-loading` 态生效，碰不到正常态。

### 边界

规则假定按钮正常态**不含图标**。若某按钮平时就是「图标 + 文字」，其 span 正常态本有 6px 且图标占位，loading 时会少掉这部分宽度、仍会跳动。当前 14 处均为纯文字按钮，无此类；将来引入时需另作处理（已在 `tokens.css` 注释中写明）。

## 侧栏「今日待办」刷新时机修复（试用反馈）

### 现象

用户反馈：在投递页临时新增一条记录（时间上应进入今日待办），侧栏「今日待办」没有更新，**刷新整个网页才更新**。

### 根因

侧栏待办的数据（`GET /overview` 的 `upcoming_events`）全站只有三处刷新点：

| 位置 | 条件 |
|---|---|
| `SideNav.vue` | **仅当 store 为空时**（首次进站） |
| `Overview.vue` | 概览页挂载时取一次 |
| `Overview.vue` | **全站唯一的轮询**（30s），且只在概览页挂载期间跑 |

**投递页一个都不占**——它那 5 处写操作（新增/编辑、删除、批量导入、状态流转、标记结束）每处只调本页的 `load()` 刷新自己的看板，从没通知过 overview store。而顶栏「＋ 新增投递」正是把人送到投递页的，用户加完记录停在投递页，侧栏自然停在旧数据。

实测取证（只观察请求，不写任何数据）：停留 35 秒期间 `/overview` 请求数——概览页 **1 次**、投递页 **0 次**、个人中心 **0 次**。

此为步骤 9 交付时的设计取舍留下的口子：轮询刻意只在本页跑（避免在别的页面持续请求没人看的接口），但没覆盖「数据变更后应立即反映」这一条。

### 修复

`Applications.vue` 新增 `syncOverview()`，在**改变投递数据的写操作成功后**调用。共 **5 处**，其中两处是排查时才发现需要补的：

| 操作 | 原先成功后的动作 |
|---|---|
| 新增/编辑保存、删除、批量导入（3 处） | 调 `load()`，顺带补 `syncOverview()` |
| **状态流转、标记结束（2 处）** | **只做本地乐观更新、根本不调 `load()`**——只改 `load()` 覆盖不到这两条 |

筛选（2 处）与写操作失败恢复（2 处）**不刷新**——数据未变，不必多发请求。

### 验证

CDP 驱动真实保存流程（mock 层没有投递接口，用 `Fetch.fulfillRequest` 把写请求伪造成成功，从而走通真实的前端代码路径）：

| 阶段 | 保存成功 | `/overview` 请求 | 结论 |
|---|---|---|---|
| 修复前 | ✓（页面提示「已新增」） | **0 次** | FAIL |
| 修复后 | ✓ | **1 次** | PASS |

回归：`npm run build` 通过；侧栏与概览页的尺寸、待办渲染逐项比对**无变化**。

### 遗留

`syncOverview()` 是**手工约定的刷新入口**——将来新增写操作、或别的模块（如步骤 23 校招情报「一键加入投递」）改变投递数据时，需自行调用，已在函数注释中写明该约定。若这类入口继续增多，可考虑改为在 store 层统一监听；本次未做——目前仅投递一处数据源，引入机制的成本大于收益。

用户就 AI 配置页提三点：①选完供应商不填 Key 也能看模型清单；②保存时自动测连接、连不通则保存失败并提示；③优化页面布局。

其中 **①已由台账 #58 交付**（2026-09-27），本轮**零改动**——在此备案，以免与本轮混记。

### 改动

**一、保存前自动测连接**（`ProviderFormDialog.vue`）

`onSave` 由「校验 → 直接 PUT」改为「校验 → **无变更则退出** → **POST /test** → 通过才 PUT」：

- 测试载荷抽为 `buildTestPayload()`，与既有「测试连通」按钮**共用同一份**（避免两处各写一遍），一律用**表单当前值**（未保存的 Key / 端点 / 模型）——后端按临时参数测、不读已存配置，故「改了 Key 想换一家」能先被验证；
- **测试失败即不落库**，弹窗保持打开、错误显示在弹窗内，用户可直接改完再存，不必重填；
- **无变更时不做测试**——先组装 payload 判断有无变更，有才进入测试环节；否则会出现「测了半天却提示没变更」的怪顺序；
- 「测试连通」按钮**保留**（用户明确要求，用于「先探一下、不一定存下来」的场景）；
- 保存按钮 loading 文案改为「验证并保存中…」。

**二、布局三项**（`AiConfig.vue`）

| 项 | 改动 |
|---|---|
| 容器 | `max-width` 820 → **1100px**（1440 视口下右侧留白由 350px 收到约 70px） |
| 当前使用中 | 由卡片外的独立一行，**并入卡片、作为列表上方首条**（带底色的 flex 条 + 品牌色圆点）——原本它的背景 `--c-bg` 与页面底色几乎同色，视觉上就是「一行浮在卡片外的小字」，而它是本页头等信息 |
| 列表行 | 去掉「国内大厂 / 本地部署」分组列（对「选哪个模型」无帮助、纯占宽度）；去掉「设为当前」按钮，**改为点击整行**（仅非激活行；行内按钮区 `stopPropagation` 防止误触发） |

### 验证

`npm run build` 通过。CDP 走查五个场景（mock 层无供应商接口，用 `Fetch.fulfillRequest` 伪造 `/api/v1/llm-providers*` 响应并记录请求序列）：

| B 测试失败 | `POST /test`（**到此为止**） | 全部 PASS：**未发 PUT**、弹窗仍开、显示「连接失败，未保存」 |

**走查抓到并修掉的三处真实缺陷**（假流的价值正在于此）：

1. **会话 id 取错字段**——前端读 `session.value.id`，而契约字段是 `session_id`，逐轮请求实际传 `undefined`（假后端因此每轮新建会话，真实后端会 404）；症状是追问进度永远停在「第 1 层」。改为取 `session_id`；
2. **`dimensions` 解析成功后不进 `blocks`**——渲染按 `blocks` 顺序遍历，四维分栏因此**永不出现**；改为解析成功也保留块（内容由 `turn.dimensions` 呈现，解析失败按纯文本降级）。**先改测试契约（单测由「不进文本块」改为「块仍在」）确认 RED，再改实现**；
3. **`StreamText` 缺 `immediate`**（**既有组件缺陷**，步骤 11 产物）——挂载时若文本已有内容（模型快、或同一 `section` 的多个 delta 成批到达），不会再有 `text` 变化来触发 watch，该段文字**永远空着**。加 `immediate: true` 修复；本轮走查的假流节奏下稳定复现，真实场景偶发。

### 工作内容

**一、消息序列纯函数（`utils/interviewStream.js`，本轮核心）**

进行页有三个数据来源——恢复用的 `qa_list`、流式 `delta`、本地提交的作答。三者揉进组件会让"恢复"与"流式"各写一套渲染，故收进纯函数模块，统一翻译成**消息序列**（`question` / `answer` / `review` 三种消息），渲染层只认 `messages`。

- `buildMessages` 由 `qa_list` 展开并标注**四种尾态**：`empty`（待请首题）/ `awaiting-answer`（等输入，刷新恢复的主路径）/ `midway`（已作答、下一题未生成，可继续）/ `finished`（满题量）；
- `applyDelta` 按 `section` 归段（`review` → 点评卡片、`next_question` → 提问气泡），对**缺段容忍**——跳过轮只有 `next_question`、满题量轮只有 `review`，都是正常路径；
- `appendAnswer` / `insertSkipped` / `sealStreaming` 负责本地插入与定稿。
- `midway` 的三种成因（下一题未生成 / 点评未完成 / 流中断）不区分——后端断连语义未写明（IS-45），前端一律按"可继续"呈现。

**二、列表页与发起弹窗**

- `InterviewList.vue`：卡片列表 + 状态筛选（全部/进行中/已结束）+ 分页；`ACTIVE` 显「继续面试」、`FINISHED` **只标状态不给入口**（tooltip 说明回看属下一步，不做假入口）；
- `InterviewCreateDialog.vue`：选投递（远程搜索下拉，选中自动带入公司岗位）或手填二选一；方向按技术栈分组（**取自 `GET /practice/meta`，未硬编码 19 项**——待改问题 #33）；题量 3~15 默认 8。

**三、进行页（`InterviewChat.vue`）**

页头（返回 / 公司岗位 / 方向 / 第 N/M 题）+ 消息流 + 作答区。进入即拉详情恢复（`qa_list` 为空则自动请首题）；作答/跳过/midway 继续走同一个流式出口，`done` 时读 `extra.session_finished` 决定完成态，并以后端 `seq` 校准本地题号；点评分数从点评正文解析（复用陪练的 `parseRoundScore`——契约的 `done` 不带分数）。

**四、方向选择扩容（待改问题 #33 闭环）**

`GENERAL`（不限方向）置顶 + `meta.stacks[].domains` 分组渲染，默认「通用」；列表页与进行页的方向中文名用同一份映射（`directionLabelMap` + `GENERAL` 补位）。

**五、后端用例（`backend/tests/test_interview.py`）**

1. **进行页高度计算失效**——`calc(100vh - var(--header-h) - var(--content-padding) * 2)` 中 `--content-padding` 是简写值（`20px 22px`），参与乘法无法解析、整条声明失效，卡片退化为内容高度（底部大片空白）。改为 `height: 100%`（el-main 为 flex 拉伸出的确定高度，百分比可解析）；
2. **历史消息也走打字机**——刷新恢复后整屏历史逐字重打一遍，像重播（截图里停在半截）。改为**打字机只给流式中的消息**（`m.streaming` 为真才走 `StreamText`），历史消息直接渲染纯文本。

### 决策与遗留

- **消息序列统一模型**是本轮的核心设计：恢复与流式两条路径共用一份渲染与一份判定，"刷新接着答"因此只是 `qa_list` 的另一种输入，不是专门写的一套恢复逻辑；
- **空提交禁用、跳过带轻确认**：陪练页允许交白卷是因为后端有 `STUCK` 断点语义，面试契约没有——「答不上来」由「跳过」承担；跳过不可撤回但代价低于未答完，故用轻确认而非重确认；
- **`FINISHED` 不给入口、完成态不留假按钮**：回看属步骤 16，此处只标状态；答满后显示「本场面试已完成 · 共 N 题」，总结入口留步骤 16 接线；
- **走查用构建产物而非 dev server**：零侵入的代价是走查对象为 `dist` 产物——与源码行为一致（Vite 仅打包），且更接近真实运行形态；
- **遗留**：
  1. **真联调待后端**——契约已冻结但服务层未实现；落地后需：跑 `test_interview.py` 摘 `xfail`、真 AI 冒烟（点评流式节奏、跳过、满题量、刷新恢复、跨账号 `10002`）；
  2. **4 个契约缺口已登记**：IS-43（SRS 有 6 类题源、接口无参数）、IS-44（列表响应字段未写明且无已答数字段）、IS-45（断连落库语义）、IS-46（非首题空 `answer` 语义）——随该步后端实现明确；
  3. **midway 的「继续下一题」请求形态**（`{session_id, answer: ''}`）按最合理假设实现，真联调时核对（IS-46）；
  4. 走查脚本、假后端与截图已按惯例清理（临时目录），`frontend/dist` 构建产物一并删除。

## 作答区按钮布局调整（用户反馈，2026-09-29）

### 背景

用户反馈：「选择题提交按钮和选项有点远了，要不就都放在退出按钮旁边，从用户人机交互体验出发」。

### 实测定位

跑一个真实的选择题训练量化：选项为**全宽长条**（鼠标落在左侧），而「退出」在左下、「结束本场 / 提交」被推到屏幕最右（x≈1368）——**从选项区到提交的横向动线近 1000px**。根因是按钮行的两端布局（`.runner__quit` 的 `margin-right: auto` 与 `.review__actions-main` 的 `margin-left: auto`）。

### 改动

**按钮行整体左对齐**（去掉两处 `margin: auto`），按钮顺序不变（退出 → 结束本场 → 提交）——选项与输入框本就是左对齐，主操作跟随其正下方，横向动线归零：

### 二、契约口径与实现要点

| 项 | 说明 |
|---|---|
| 保存与提取分离 | 契约 `POST /experiences` **只存原文不触发提取**，提取走 `POST /stream/experience-extract`（done 时条目已落库）——弹窗因此给两个动作：「保存并提取」/「仅保存原文」（提取消耗 AI 调用，格式太乱的原文可能只想存档） |
| 提取 UI 不是打字机 | 契约明确 `delta` 是**提取进度状态文字**（不逐字展示 JSON）——状态行 + 旋转图标，与点评 / 总结的打字机形态区分 |
| 失败降级 | 40002 提示「原文已保留，可重试」——保存成功后原文必在库，失败只丢条目不丢内容；重试入口就在原地 |
| 刷新不重复计费 | 自动提取发起后立即 `router.replace` 清掉 `?extract=1`——刷新时条目已落库自然不再渲染提取区；若仍无条目则回到手动入口，不会静默重跑 AI 调用 |
| 字数口径 | 10000 字上限按 **Unicode 码点**计数（`utils/text.js` 的 `textLength`）——JS `.length` 是 UTF-16 码元（emoji 算 2）、后端 Python `len` 是码点（算 1），用错会在 10000 字附近误判超限 |
| 检索交互 | 防抖 300ms 输入即搜（与投递页 / 错题本同形态）；结果项点击跳详情页 `?item=<id>`，滚动定位 + 2.4s 模块色高亮 |
| SRS 与契约的出入 | ①SRS「按公司 / 岗位 / 关键词检索」——契约只做关键词命中 `question`；②SRS「流式回显供确认后落库」——契约改为保存与提取分离。**均按契约实现**，出入项入「明确不做」 |

### 二、全站 loading 转圈不居中（修复）

**症状**：所有界面等待 AI 等场景的 loading 按钮，转圈图标偏右下、不在按钮中心。

**根因**（CDP 量化 + computed style 实测）：`.el-icon.is-loading` 挂着库内 `rotating` 动画，其 keyframes 只声明 `transform: rotate(...)`——**运行中的动画整体接管 transform**，此前用 `translate(-50%,-50%)` 做的居中位移被覆盖丢弃（实测图标中心偏右下 **7.25px**，computed transform 的平移分量为 0）。

**修复**：居中改用与动画互不干扰的属性——`inset: 0 + margin: auto`（图标尺寸固定 1em，绝对定位下四边归零 + auto 边距即几何居中），不再碰 transform。按钮宽度恒定（文字 visibility 隐藏保留占位）的原设计不变。

**验证**：CDP 量化两形态——普通按钮「保存画像」与图标按钮「上传简历」均 **dx=dy=0**；修复前复现值 7.25px。

### 决策与遗留

- **「重新提取」做成显式入口**（不自动重跑）：提取消耗 AI 调用，替不替由用户确认框拍板；
- **失败态的「关闭」只给重新提取场景**（`closable` prop）：初次提取失败时提取区本就常驻（页面就停在「还没提取」状态），无关闭可言；
- **图标按钮形态顺带验证**：「上传简历」正常态含图标，loading 后转圈同样居中（DOM 注入复刻验证）；
- **遗留**：公司自动提取（IS-54）与提取中删除的并发防御（IS-55）待后端；真 AI 冒烟待有效 Key。
