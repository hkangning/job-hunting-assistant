## 1. 设计约定

| 项 | 约定 |
|---|---|
| 数据库 | **MySQL 8.0**（InnoDB 引擎），单库 `job_hunter`；`pymysql` 驱动接入，引擎参数 `pool_pre_ping` + `pool_recycle=3600` 防空闲断连 |
| 字符集与排序规则 | 库与表统一 **`utf8mb4` / `utf8mb4_0900_ai_ci`**——大小写不敏感、支持 emoji 与生僻字；用户名/邮箱查重仍走应用层 `LOWER()`（见 3.16） |
| 命名 | 表名/字段名全小写下划线（snake_case）；表名单数；关联外键 `xxx_id` |
| 主键 | 除 config 表外全部 `id INT AUTO_INCREMENT PRIMARY KEY`；config 为 `(user_id, key)` 联合主键 |
| 类型映射 | 设计稿中的 `INTEGER` 一律落为 MySQL **`INT`**；**布尔语义字段**（各类开关、`is_active`）以 `INT` 存 `0/1`，与接口契约的 JSON 布尔在服务层转换 |
| **账号归属** | **账号私有表**均含 `user_id INTEGER NOT NULL, FK→user.id`，并建 `idx_<表名>_user` 索引；**子表**（interview_qa / experience_item / agent_message / drill_attempt）**不冗余存 `user_id`**，经父表间接隔离；**公共表**（question / campus_event / crawl_source）不含 `user_id`，全站共享；**混合表**（job_posting）含 `user_id` 但**可取值 `0`**——`0` 表示自动抓取的公共数据、账号 id 表示该账号投喂的私有数据，查询限定 `user_id IN (0, 当前账号)`。归属划分见 §2 |
| 时间字段 | 一律存**本地时间**（`DATETIME`，**精度到秒、无小数秒**——带微秒的值写入时由 MySQL 四舍五入到秒）；Python `datetime` 对象直存；日期判定用 `DATE()` 比较 |
| 时间戳字段 | 每张业务表含 `created_at`；可更新表含 `updated_at`（应用层维护，不用触发器）。**例外**：`campus_event` / `job_posting` 因需区分「首次入库」与「最近仍抓到」，以 **`first_seen_at`** 承载创建时间语义，不另设 `created_at`（两字段语义完全重合，并存只会造成不一致） |
| 枚举 | 以 VARCHAR 存**大写英文码**（如 `APPLIED`），Python 侧用 `enum.Enum` 映射，口径见第 5 章 |
| 软删除 | 不引入——删除即物理删除（本机使用场景，看板删除已有二次确认） |
| JSON 字段 | 少量动态结构（Agent 工具参数、模型列表缓存）以 TEXT 存 JSON 字符串，应用层序列化，不建 JSON 查询 |
| 索引 | 只建查询路径上的索引（见各表），不在全表数百行的规模上过度索引 |
| 加密字段 | `llm_provider_config.api_key`、`config` 中的讯飞 ASR 凭据（`asr_api_key`）以 **Fernet 对称加密**后存 TEXT（主密钥 `APP_SECRET_KEY` 在 .env）；**默认的 FunASR 本地模型与 edge-tts 不需要任何凭据，故无字段** |

```mermaid
    crawl_source ||--o{ campus_event : "抓取产出（按 source_site 标识）"
    crawl_source ||--o{ job_posting : "抓取产出（按 source_site 标识）"
```

文字版关系：

- **`user`（账号）是归属根**：账号私有数据均带 `user_id` 外键，删除账号即级联清理其全部私有数据（例外见 §3.14 `config`——该表含 `user_id=0` 的系统级行，不建外键）；
- `application`（投递）是业务中心实体：JD 分析、模拟面试、跟进提醒均围绕它，且**仅在所属账号内可见**；
- `question`（题库）为**公共资源**，被所有账号的陪练、错题本共用；`wrong_question` 对 `(user_id, question_id)` 建唯一约束——**同一题在不同账号的错题本中各存一条，互不影响**；
- `interview_session` 允许 `application_id` 为空（用户不选投递、手填公司岗位发起面试）；
- `llm_provider_config` 为**账号 × 供应商**配置表（`user_id + provider` 唯一），每账号至多一行 `is_active=1`；为**纯账号级**表，`user_id` 建外键（对照 §3.14 `config` 含系统级行、不建外键）；
- `config` 为 key-value 配置表，`user_id` 为 **0 表示系统级配置**（不建外键，见 §3.14）；
- `user_profile` 与账号 1:1（`user_id` 唯一）；
- `drill_topic`（我的题目）与 `drill_attempt`（一次练习）构成**练习模式**：题目归账号所有，尝试为子表（不冗余存 `user_id`，与 `interview_qa` 同口径），同一道题反复练、逐次留存；
- `crawl_source`（抓取源配置）为**公共表**——一行 = 一所学校的一个就业网站系统，任一账号修改全局生效；`campus_event` / `job_posting` 的自动抓取结果按 `source_site` 标识回指到源（**不建外键**：条目可由多个源合并产出、源删除后条目仍有效，见 §3.20）；
- `job_posting`（岗位）为**本库唯一的混合归属表**：`user_id=0` 为自动抓取的公共岗位、账号 id 为投喂的私有岗位，唯一约束 `UNIQUE(user_id, dedup_key)` 使两类数据各自去重、互不干扰（见 §3.21）；
- `subscription`（订阅规则）为账号私有表，命中后写 `reminder`（`reminder_type=INFO_MATCH` + `ref_type` 标识来源表）——**匹配范围限「公共信息 + 该账号自己的投喂记录」**，不得命中其他账号的投喂内容（见 §3.12）。

## 3. 表结构详述

**类型口径**：各表的「类型」列沿用设计语义写法，落到 MySQL 的实际类型对照——`INTEGER` → `INT`、`VARCHAR(n)` → `VARCHAR(n)`、`TEXT` → `TEXT`（上限 64KB，见 §6）、`DATETIME` → `DATETIME`（精度到秒）、布尔语义字段 → `INT` 存 `0/1`。**`TEXT` 列一律不设默认值**（MySQL 不允许 TEXT 带 `DEFAULT`），需要非空的 TEXT 字段由应用层保证写入。

**账号归属**：**公共表，不含 `user_id`**——就业网抓取结果为全站共享（每日抓一次入库，所有账号读到同一份数据）。

### 3.14 config —— 系统配置

对应需求：FR-015。

| 字段 | 类型 | 约束 | 说明 |
|---|---|---|---|
| user_id | INTEGER | 非空，联合主键之一 | 所属账号；**`0` 为保留值，表示系统级配置**（**不建外键**，0 非合法 user 行） |
| key | VARCHAR(50) | 非空，联合主键之一 | 配置键 |
| value | TEXT | 可空 | 配置值（开关、URL、Key 加密值） |
| updated_at | DATETIME | 非空 | 更新时间 |

**主键**：`(user_id, key)` 联合主键（多账号改造前为 `key` 单列主键）。

**为什么用 `0` 而不是 NULL 表示系统级**：SQL 语义下 **NULL 在 UNIQUE / 主键判定中互不相等**（MySQL 唯一索引同样允许多行 NULL），用 `user_id=NULL` 会导致同一 key 重复插入多行、唯一约束形同虚设；故以 NOT NULL + 保留值 `0` 表达。

**两级配置键清单**：

| 级别 | 键 | 说明 |
|---|---|---|
| 账号级 | `tts_enabled` / `voice_enabled` | TTS 播报、语音作答开关（默认 false） |
| 账号级 | `default_question_count` | 模拟面试默认题量（默认 8） |
| 账号级 | `asr_provider` | ASR 供应商：`funasr`（默认，本地模型）/ `xunfei`（云端备用） |
| 账号级 | `tts_voice` | TTS 音色 ID（edge-tts 音色名，默认 `zh-CN-XiaoxiaoNeural` 晓晓） |
| 账号级 | `asr_app_id` / `asr_api_key` | **仅 `asr_provider=xunfei` 时需要**；Key 以 **Fernet 加密**存 value（P2） |
| 账号级 | `guide_done` | 新手指引是否已读（`true`/`false`，默认 false）；注册后走完或跳过引导置 `true`，个人中心重看不回写（P2） |
| 系统级（`user_id=0`） | `crawl_enabled` | 校招信息采集总开关（面向整站公共数据，任一账号修改全局生效）；**具体抓哪些学校由 `crawl_source` 表维护**（见 3.20） |

**`crawl_url` 已废弃**（原设计为单站点抓取目标地址）：抓取目标升级为 `crawl_source` 表多行后，单值 URL 无法表达多源；建表与迁移均**不再预置该键**，源清单由设置页「信息源管理」维护。

**敏感策略**：讯飞语音 Key 由设置页填写后加密存本表 value；**不进入版本库、不写入日志、接口不回显明文**（接口仅返回 `asr_api_key_set` 布尔）。**默认的 FunASR 本地模型与 edge-tts 无需任何 Key**，仅 `asr_provider=xunfei` 时才涉及凭据。AI 供应商配置（Key / base_url / 模型 / 模型缓存）**不存本表**，见 3.17 `llm_provider_config`。

### 3.17 llm_provider_config —— AI 供应商配置

对应需求：FR-018。

| 字段 | 类型 | 约束 | 说明 |
|---|---|---|---|
| id | INTEGER | PK 自增 | 主键 |
| user_id | INTEGER | 非空，**FK→user.id（ON DELETE CASCADE）** | 所属账号（**配置按账号隔离**；账号删除时其配置行一并清理） |
| provider | VARCHAR(30) | 非空 | 供应商标识（注册表 12 项之一，见第 5 章） |
| base_url | VARCHAR(200) | 可空 | API 端点；**空 = 用注册表默认值**（覆盖场景：供应商端点变更、自建代理） |
| api_key | TEXT | 可空 | 密钥（**Fernet 加密后存**；接口只回 `key_set` 布尔，**永不回显明文或片段**）；`ollama` 本地无需 Key 故可空 |
| model | VARCHAR(100) | 可空 | 该供应商下所选模型（**每家各记一份**，空 = 用注册表默认模型） |
| models_cache | TEXT | 可空 | 模型列表缓存 JSON（含 `fetched_at`，24h 过期；**按本行 provider + base_url 维度**） |
| is_active | INTEGER | 非空，默认 0 | 是否当前激活（**每账号至多一行 =1**） |
| created_at | DATETIME | 非空 | 创建时间 |
| updated_at | DATETIME | 非空 | 更新时间 |

约束：`UNIQUE(user_id, provider)` 保证每账号每供应商一行（重复保存走更新）。索引：`idx_llm_cfg_user(user_id)`。

**为什么 `user_id` 建外键**：本表是**纯账号级**配置（每账号 × 每供应商一行，不存在平台级共享行），故与其余账号私有表同口径建 `FK→user.id` 并设 `ON DELETE CASCADE`——账号被删除时其 AI 配置一并清理，不留孤儿行。（对照 §3.14 `config`：该表含 `user_id=0` 的系统级键，不对应任何账号，故不建外键。）

**激活语义**：保存配置时若该账号尚无激活行，本次保存的供应商自动置 `is_active=1`；切换供应商 = 在同一事务内把旧激活行置 0、目标行置 1（保证至多一行激活）。运行时 Key 读取链见系统设计 5.4。

**平台不自备 Key**：本表**只存账号自己的供应商配置**，不存在平台级的共享 Key 行——平台不为账号代付任何 LLM 额度（FR-018 配置规则 1）。

**模型缓存为何挂在本表**：缓存内容（某 base_url 下有哪些模型）是供应商公开信息、与账号无关，但同一账号同一供应商天然只有一行，挂在行上无需额外表；代价是多账号各自拉一次（12 家供应商、单次 GET /models，可忽略）。

### 3.19 drill_attempt —— 一次练习（练习模式）

对应需求：FR-020、FR-014。

| 字段 | 类型 | 约束 | 说明 |
|---|---|---|---|
| id | INTEGER | PK 自增 | 主键 |
| topic_id | INTEGER | 非空，FK→drill_topic.id | 所属题目 |
| seq | INTEGER | 非空 | 第几遍（同一题目内从 1 递增，跨次对比按此排序） |
| answer | TEXT | 可空 | 本次作答文本（未答为空） |
| is_voice | INTEGER | 非空，默认 0 | 是否语音作答（0 文字 / 1 语音） |
| voice_metrics | TEXT | 可空 | 表达力指标快照（JSON，见下方结构）；非语音作答为空 |
| score | INTEGER | 可空 | 得分 0~10 |
| review | TEXT | 可空 | AI 点评（亮点/不足/参考要点） |
| duration_ms | INTEGER | 可空 | 作答耗时（毫秒） |
| created_at | DATETIME | 非空 | 提交时间 |

索引：`idx_attempt_topic(topic_id)`。

**账号归属**：子表，**不冗余存 `user_id`**——经 `topic_id → drill_topic.user_id` 归属到账号，服务层查询一律先校验题目归属（与 `interview_qa` 同口径）。

**`seq` 的生成**：服务层在同一题目内取当前最大 `seq` + 1；单账号单机场景不存在并发写同一题目的情况，故不建唯一约束。

**`voice_metrics` 结构**（与 `interview_qa.voice_metrics` 完全一致，由同一纯函数 `app/utils/speech_metrics.py` 产出）：

```json
{
  "version": 1,
  "quality": "OK",
  "total_ms": 95000,
  "speech_ms": 78000,
  "silence_ms": 17000,
  "char_count": 320,
  "speech_rate": 246,
  "speech_ratio": 0.82,
  "filler_count": 12,
  "filler_rate": 0.037,
  "filler_detail": { "然后": 6, "就是": 4, "嗯": 2 },
  "pauses": [
    { "after_seq": 3, "duration_ms": 3200, "context": "缓存雪崩", "level": "HIGH" }
  ],
  "longest_pause_ms": 3200,
  "fluency_trend": {
    "direction": "DECLINING",
    "segments": [
      { "seg": 1, "speech_rate": 262, "filler_count": 2 },
      { "seg": 2, "speech_rate": 241, "filler_count": 4 },
      { "seg": 3, "speech_rate": 198, "filler_count": 6 }
    ]
  }
}
```

- `version`：指标算法版本号。算法口径调整后旧数据能被识别（`quality` / `version` 枚举见第 5 章），**跨版本数据不在同一进步曲线中并列展示**；
- `quality`：`OK` 正常 / `TOO_SHORT` 作答不足 10 秒未分析 / `TEXT_ONLY` 纯文字作答（后两者不产出表达维度点评）；
- `pauses[].level`：`LOW`（1.5~3 秒）/ `HIGH`（3~5 秒）/ `SEVERE`（>5 秒）；`context` 为该停顿前一句的末尾若干字，供 LLM 判断是否构成知识点。

## 6. 容量与性能说明

- 预估总数据量 < 10 万行（见 SRS 4.2），**单库单表即可**，无需分库分表；
- **`TEXT` 单列上限 64KB**（MySQL `TEXT` 的字节上限，utf8mb4 下约 2 万汉字）——本题库最长字段为场景题参考答案（1~2KB），面经原文、AI 点评等大文本亦远低于上限；确需更长时改用 `MEDIUMTEXT`（16MB），本期无此需求；
- **时间精度到秒**（见 §1）：同秒内多条记录的顺序不确定，需要稳定排序的列表接口以主键 `id` 作次级排序键；
- 面经/报告等大 TEXT 字段总量 < 50MB，无性能压力；
- 前端列表全部服务端分页（page/page_size，默认 10 条），LIKE 检索限定在面经条目表且结果分页。
- **多账号影响**：数据量随账号数线性增长，但本机单机场景账号数在个位数量级，总量仍在上述量级内；账号级查询一律带 `user_id` 等值条件，各表已建 `idx_*_user` 索引，隔离不带来额外扫表成本。
- **头像文件不入库**：仅存相对路径于 `user.avatar`，实际文件在 `backend/uploads/avatars/`（每张压缩至 256×256，约 20~50KB，量级可忽略）；该目录**已入 `.gitignore`**（`backend/uploads/`）。
- **语音模型不入库**：FunASR 流式模型由 ModelScope 下载到本机缓存目录（约 200~300MB，INT8 量化后），**不在仓库、不在数据库**；TTS 合成结果按 `sha1(text+voice)` 缓存在 `backend/cache/tts/`（单条数秒音频约 10~50KB），该目录**已入 `.gitignore`**（`backend/cache/`），不占用数据库体积。
- **练习模式数据量**：练习记录逐次累积（每练一遍一行 `drill_attempt`），按每天练 10 遍估算一年约 3600 行，相对现有量级可忽略；`voice_metrics` 为单次作答的 JSON 快照（约 1~2KB），仅语音作答时写入。原始音频**不入库、不落盘**（分析完即弃，见 SRS 7 范围边界）。
- **校招情报数据量**：按 10 个源、每源每日新增 20 条估算，一年累计约 7 万行——**已含在首条的 10 万行总预估内**；过期数据由归档机制定期清理（`EXPIRED` 超 90 天物理删除），稳态行数远低于累计值。抓取条目**只存元数据与原文链接、不存正文**（NFR-016），无大 TEXT 增长。
- **信息源与订阅规则量级可忽略**：源为个位到十位数量级（一校一行）；订阅规则由用户自建，量级在几条到几十条。

## 7. 数据库初始化

### 7.1 建库（一次性，手工执行）

MySQL 实例需先建好库与账号，服务不会自动建库。以管理员身份执行：

> **注意**：下面命令里的 `<密码>` 是**占位符，必须替换成真实密码再执行**（含尖括号一并替换掉），`backend/.env` 的连接串里填同一个。原样执行会把密码设成中文字面量 `<密码>`——Python 客户端发不出中文密码，后端只会报 `1045 Access denied`，从报错看不出根因。

```sql
CREATE DATABASE IF NOT EXISTS job_hunter DEFAULT CHARACTER SET utf8mb4 COLLATE utf8mb4_0900_ai_ci;
CREATE DATABASE IF NOT EXISTS job_hunter_test DEFAULT CHARACTER SET utf8mb4 COLLATE utf8mb4_0900_ai_ci;
CREATE USER IF NOT EXISTS 'jobhunter'@'localhost' IDENTIFIED BY '<密码>';
GRANT ALL PRIVILEGES ON job_hunter.* TO 'jobhunter'@'localhost';
GRANT ALL PRIVILEGES ON job_hunter_test.* TO 'jobhunter'@'localhost';
FLUSH PRIVILEGES;
```

PowerShell 一行版（MySQL 装在默认路径时，`-p` 后回车输入 root 密码）：

```powershell
& "C:\Program Files\MySQL\MySQL Server 8.0\bin\mysql.exe" -u root -p -e "CREATE DATABASE IF NOT EXISTS job_hunter DEFAULT CHARACTER SET utf8mb4 COLLATE utf8mb4_0900_ai_ci; CREATE DATABASE IF NOT EXISTS job_hunter_test DEFAULT CHARACTER SET utf8mb4 COLLATE utf8mb4_0900_ai_ci; CREATE USER IF NOT EXISTS 'jobhunter'@'localhost' IDENTIFIED BY '<密码>'; GRANT ALL PRIVILEGES ON job_hunter.* TO 'jobhunter'@'localhost'; GRANT ALL PRIVILEGES ON job_hunter_test.* TO 'jobhunter'@'localhost'; FLUSH PRIVILEGES;"
```

**建完自检**（用刚设的账号连一次，能列出两个库即成功；密码即上面设的那个）：

```powershell
& "C:\Program Files\MySQL\MySQL Server 8.0\bin\mysql.exe" -u jobhunter -p -e "SHOW DATABASES LIKE 'job_hunter%';"
```

**报 `1045 Access denied for user 'jobhunter'@'localhost'` 时**（密码设错、或磁盘上已有旧账号）：先以 root 看账号实际状态——`password_last_changed` 能指示密码是什么时候设的、与哪个时刻对得上；再用同一条命令重置密码（`<你的密码>` 与 `backend/.env` 保持一致）：

```powershell
& "C:\Program Files\MySQL\MySQL Server 8.0\bin\mysql.exe" -u root -p -e "SELECT user, host, plugin, password_last_changed FROM mysql.user WHERE user='jobhunter'; ALTER USER 'jobhunter'@'localhost' IDENTIFIED BY '<你的密码>'; FLUSH PRIVILEGES;"
```

**两个库**：`job_hunter` 为开发库，`job_hunter_test` 供 pytest 使用（与开发库物理隔离，口径见测试计划 §1.1），上面两条命令已一并创建。

连接串写入 `backend/.env`（模板见 `backend/.env.example`；`.env` 已 gitignore，严禁提交）：

```
DATABASE_URL=mysql+pymysql://jobhunter:<密码>@127.0.0.1:3306/job_hunter?charset=utf8mb4
```

### 7.2 建表与种子导入（自动）

服务启动时 `init_db()` 自动完成，无需手工执行 DDL：

1. **建表**——`Base.metadata.create_all(engine)` 按 ORM 模型建 **22 张表**（`CREATE TABLE IF NOT EXISTS` 语义，已存在则跳过；**不会给已存在的表补列或改约束**，故表结构变更须走 7.3）；
2. **系统级配置**——插入 `config` 的 `user_id=0` 默认行（幂等）；
3. **题库种子**——导入 `backend/seed/questions.json`（**585 题**，upsert 语义见 §4）。

### 7.3 表结构变更约定

开发库业务数据为空，**改表结构一律"改 ORM 模型 → 删库重建"**，不写增量升级 SQL：

```powershell
& "C:\Program Files\MySQL\MySQL Server 8.0\bin\mysql.exe" -u root -p -e "DROP DATABASE job_hunter; CREATE DATABASE job_hunter DEFAULT CHARACTER SET utf8mb4 COLLATE utf8mb4_0900_ai_ci;"
```

重建后重启服务即自动建表并导入种子。本约定成立的前提是"库内数据可弃"；待开发库出现需保留的数据后，改用迁移工具，届时另行定稿。

**库内已有需保留的数据时**（如已注册账号、已录入投递），改用手工 `ALTER`——MySQL 支持直接增删列与约束，比四步重建省事得多；改完与 ORM 模型对齐即可。本文件 v1.13 的 `llm_provider_config` 变更（随免费档摘除还原表结构）即走此路径，两条语句同步作用于开发库与测试库：

```sql
DELETE FROM llm_provider_config WHERE user_id = 0;   -- 先清平台行，否则下一条外键建不上
ALTER TABLE llm_provider_config
  DROP COLUMN use_shared,
  ADD CONSTRAINT llm_provider_config_ibfk_1 FOREIGN KEY (user_id) REFERENCES `user` (id) ON DELETE CASCADE;
```

`use_shared` 为免费档专用列，摘除后无数据需保留（存量行一律是自配 Key 档）；外键随平台行消失而恢复（见 §3.17），原有 `idx_llm_cfg_user` 索引保留，与 ORM 声明一致。**（历史：v1.10 曾以同一路径为该表加上 `use_shared` 列并去掉外键，本次反向还原。）**

> **历史说明**：本章此前是按版本递进的增量升级 SQL（v1.2 → v1.8 共 9 节、约 270 行）。其存在理由是 SQLite 的 `ALTER TABLE` **不支持新增主键 / 唯一约束**，多账号改造与校招情报改造中的 `config` / `wrong_question` / `reminder` / `user_profile` / `campus_event` 五张表必须走"建新表 → 搬数据 → 删旧表 → 改名"四步重建。改用 MySQL 后约束变更可直接 `ALTER`，且开发库本就以删库重建为路径，这批脚本已无使用场景，随本次数据库切换一并废止（历史内容见 v1.8 版本的本文件）。
