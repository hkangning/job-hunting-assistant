## 1. 引言

### 1.1 编写目的

本文档承接需求规格说明书（SRS），给出系统的技术架构与核心机制设计。开发人员按本文档 + 接口文档 + 数据库设计文档实现代码，不得偏离。

### 1.2 设计原则

| 原则 | 落地方式 |
|---|---|
| 低延迟优先 | 所有 LLM 输出 SSE 流式；prompt 精简；定时任务不阻塞请求（NFR-001~004） |
| LLM 失败不致命 | LLM 封装层统一重试/降级；纯数据功能与 LLM 功能完全解耦（NFR-005/006） |
| **账号即边界** | 账号私有数据的归属**只由登录态决定**（服务层参数强制），不由前端传入；跨账号一律按"不存在"处理（NFR-014） |
| **配置与代码分离** | 供应商注册表、Key、模型均运行时读取，切换即时生效；新增供应商只加配置不改业务代码 |
| 可测试 | LLM 调用全部收敛到单一封装层，测试时注入 mock；鉴权经依赖注入可替换（NFR-012） |
| 最小依赖 | Agent 手写；数据库 MySQL；除 LLM/STT 外无外部服务 |
| 文档一致 | 本文档引用的表名/接口路径/枚举与数据库设计文档、接口文档严格一致 |

## 3. 后端设计

### 3.1 分层架构

```
routers/（API 层）：路由、参数校验、鉴权（依赖注入取当前账号）、异常捕获 → 只做协议转换
services/（服务层）：业务逻辑、事务边界、LLM 调用编排 → 不做协议细节
models/（数据层）：ORM 模型、枚举、DDL 映射
schemas/（传输层）：Pydantic 请求/响应模型（DTO）
```

**规则**：routers 禁止直接访问 ORM；services 禁止返回 ORM 对象给 router（必须转 DTO）；所有 LLM 调用必须经 `llm_client`，任何地方不得直接 new 一个 openai 客户端；**业务服务的每个读写方法都必须接收 `user_id` 参数**（由路由层从登录态传入，服务层不得自行推断归属）。

**采集与处理分层（校招情报，见 5.9）**：采集适配器只负责「把页面变成统一结构的原始条目」（网络、解析、异常、限频归它管），**不产生业务状态与指纹**；处理层是**纯函数模块**（归一化 / 去重指纹 / 变更检测 / 过期归档 / 匹配打分），零 IO、可离线单测；服务层负责调度采集、调用处理层、落库与消费编排。这样目标站点改版时只换适配器，处理逻辑零改动。

### 3.2 统一响应体

```json
{ "code": 0, "message": "ok", "data": {} }
```

- `code=0` 成功；非 0 为错误码（完整错误码表见接口文档）；
- 列表类 `data` 统一为 `{ "total": n, "items": [...] }`（分页规范见接口文档）；
- SSE 流式端点不走此格式（事件协议见 5.1）。

### 3.3 全局异常处理

| 异常 | 响应 |
|---|---|
| 参数校验失败（Pydantic/RequestValidationError） | 400 + 错误码 10001，message 列出首个字段错误 |
| 资源不存在 | 404 + 错误码 10002 |
| **未登录 / Token 无效** | 401 + 错误码 80001，message"登录状态已失效，请重新登录"（前端清本地 Token 并跳登录页） |
| **Token 已过期** | 401 + 错误码 80002（前端处理同 80001） |
| **账号锁定** | 403 + 错误码 80005，message 含剩余锁定时间 |
| **跨账号访问资源** | 404 + 错误码 10002（**与"资源不存在"完全一致，不暴露资源存在性**，见 3.6） |
| **原密码错误 / 密码强度不足** | 400 + 错误码 80007 / 80006 |
| LLM 调用失败（llm_client 抛出 LLMError） | 502 + 错误码 10010，message 提示"AI 服务暂不可用，请重试或检查设置" |
| **信息源解析失败**（针对单个源的手动抓取） | 502 + 错误码 70002，message 含源名称与失败原因；**全量抓取不整体报错**，逐源结果计入返回摘要（见 5.9） |
| **投喂内容解析失败** | 400 + 错误码 70003，message 区分"AI 抽取失败"与"链接需登录 / 被拒绝"，前端提示并降级为手动填表 |
| 未捕获异常 | 500 + 错误码 10000，记录日志（logging），响应不含堆栈 |

### 3.4 事务边界

- 写事务最小化：单条 SQL 的简单写入由 ORM 自动提交；跨表写入（如"面经主记录 + 结构化条目"）在服务层显式 `with Session.begin()`；
- LLM 调用**不在事务内**：先完成 LLM 获取结果，再开事务落库，避免长事务占用锁。

### 3.5 账号与鉴权设计（FR-016）

**密码存储**：bcrypt 哈希（自带盐值），`user.password_hash` 存哈希串；明文密码只在注册/登录请求体内短暂存在，**不写日志、不入库**。

**JWT 签发与校验**：

```
签发（登录/注册成功）：
  payload = { sub: user_id, username, iat: 签发时间, exp: 过期时间, pwd_ver: 密码版本 }
  算法 HS256，密钥 APP_SECRET_KEY（.env）
  有效期：勾选「30 天免登录」= 30 天；未勾选 = 1 天

校验（每个受保护请求）：
  Authorization: Bearer <token>
    → 验签 + 验 exp → 失败：401 + 80001/80002
    → 取 sub 查 user → 用户不存在/已停用：401 + 80001
    → 校验 pwd_ver == 当前密码版本 → 不等：401 + 80002（密码已改，旧 Token 作废）
    → 通过：把 user 对象注入请求上下文（get_current_user 依赖）
```

- **密钥持久化**：`APP_SECRET_KEY` 由 .env 提供；若缺失，服务首次启动时生成随机值并**写回 .env**（避免每次重启都使已签发 Token 失效）；
- **无需服务端会话表**：JWT 无状态，登出由前端清除本地 Token 完成；"改密后旧 Token 作废"通过 Token 载荷中的 `pwd_ver` 与库中当前值比对实现（`pwd_ver` = `password_changed_at` 的秒级时间戳，从未改密则为 0），不引入黑名单。**不用 `iat < password_changed_at` 的原因**：`iat` 为秒级截断，同一秒内登录再改密会误判为"未过期"；改用签发时固化的 `pwd_ver` 与该字段直接比对，语义等价且边界精确；
- **白名单**：`/health`、`/auth/register`、`/auth/login` 免鉴权，其余全部端点挂 `Depends(get_current_user)`；**SSE 端点同样鉴权**（前端 `fetch` 可带自定义头，不受 EventSource 限制）。

**登录失败锁定**：`user.login_fail_count` 与 `user.locked_until` 两字段实现——失败累加，达 5 次写入 `locked_until = now + 5min`；锁定期间即使密码正确也返回 80005；登录成功清零两字段。失败提示统一为"用户名或密码错误"（80004），**不区分**用户名是否存在。

**头像文件存储**：

```
上传：前端 canvas 压缩至 256×256 → multipart 上传
  → 后端校验类型（jpg/jpeg/png/webp）与体积（≤2MB），Pillow 验真
  → 服务端兜底处理：最长边 > 256 时等比缩至 256（只缩不放）；jpg/jpeg 且图像模式非 RGB/L 时 `convert("RGB")`（JPEG 不支持透明通道）
  → 服务端重命名：uploads/avatars/{user_id}_{uuid8}.{ext}（不使用用户原始文件名）
  → user.avatar 存相对路径；旧头像文件同步删除（同一次请求内完成，不引入异步任务）
删除（恢复默认）：删除文件 + user.avatar 置空（默认头像由前端按用户名生成，不占存储）
静态访问：FastAPI StaticFiles 挂载 /uploads → uploads/（仅本机访问）；库中存的相对路径 `uploads/avatars/x.png` 前端拼后端地址即可直接访问，无需路径改写
```

### 3.6 多账号数据隔离设计（FR-016）

**隔离原则**：账号私有数据在**服务层**统一按 `user_id` 过滤，路由层从 `get_current_user()` 取得归属，**前端无法指定归属**（不接受请求体/查询参数里的 user_id）。

| 层级 | 措施 |
|---|---|
| 数据模型 | 账号私有表含 `user_id` 外键（见数据库设计文档）；子表（问答条目/消息/面经条目）不冗余存 `user_id`，经父表间接隔离 |
| 服务层 | 所有按 id 查询的方法签名强制为 `get_xxx(db, user_id, xxx_id)`，查询条件同时含 `id == xxx_id` 与 `user_id == user_id`；查不到一律按"资源不存在"处理 |
| 路由层 | 每个受保护端点声明 `current_user: User = Depends(get_current_user)`，把 `current_user.id` 传入服务层 |
| 越权响应 | 跨账号访问返回 **404 + 10002**，与正常"不存在"完全一致（不泄露资源是否存在，见 4.1 数据归属） |
| 公共数据 | `question`（题库）、`campus_event`（宣讲会/双选会）、`crawl_source`（抓取源配置）无 `user_id`，全站共享；写操作（AI 生成入库、抓取、源管理）不限账号 |
| 混合表 | `job_posting`（岗位）含 `user_id`：`0` = 自动抓取的公共岗位，其余 = 该账号投喂的私有岗位。**查询一律限定 `user_id IN (0, 当前账号)`**——公共记录人人可见、私有记录仅归属账号可见；订阅匹配受同一约束（见 5.9） |
| 定时任务 | 逐账号遍历执行（遍历 `user` 表），提醒记录归属对应账号；**校招信息采集为公共任务，全站执行一次**，抓取完成后对每个账号跑一遍订阅匹配（只匹配公共信息与该账号自己的投喂记录） |

**越权防护为测试必测项**：每个业务模块至少一条「A 账号 Token 访问 B 账号资源 id → 404」用例（见测试计划）。

页面内短生命周期状态（看板数据、面试会话）用组件局部 state，不滥用 Pinia。

### 4.3 前端工程约定

- 请求统一走 `src/api/` 封装（axios 实例，统一拦截 code≠0 弹错）；**请求拦截器统一注入 `Authorization: Bearer <token>`**，响应拦截器识别 80001/80002 触发全局登出（见 4.1）；
- 组件按页面分目录：`src/views/<page>/`；
- LLM 流式文本一律渲染为纯文本（`{{ }}`），**不用 v-html 渲染 LLM 输出**（NFR-010）；
- Element Plus 全量引入（项目规模下按需引入收益低，控制构建复杂度）；
- **Element Plus 主题定制**：覆盖其 CSS 变量，把默认蓝 `#409EFF` 换成品牌紫，并统一圆角与字体。只改视觉变量，不改组件行为与 API，升级 Element Plus 不受影响；
- **设计 token 单一出处**：`src/styles/tokens.css` 用 CSS 自定义属性定义全部色彩、间距、圆角，在 `main.js` 中于 Element Plus 样式之后引入使其生效。页面与组件一律引用变量，不写死色值。

#### 4.5.2 字体与排版

- 字体族用**系统字体栈**，不引入 webfont：`-apple-system, BlinkMacSystemFont, "Segoe UI", "Microsoft YaHei", "PingFang SC", sans-serif`。中文环境下系统字体（苹方 / 微软雅黑）质量已足够，而一个中文字体包动辄数百 KB，会让首屏白等——收益不抵成本；
- 数字一律 `font-variant-numeric: tabular-nums`，使表格与指标纵向对齐；
- 字号阶梯：

| 用途 | 字号 / 字重 |
|---|---|
| 顶栏页面标题 | 15.5px / 700 |
| 卡片标题 | 13px / 700 |
| 正文 | 13px / 400 |
| 次要信息 | 12px / 400 |
| 弱化信息 | 11.5px / 400 |
| 指标数字 | 13–15px / 700 |

#### 4.5.3 间距与圆角

- 间距基础单位 4px；内容区 `padding: 20px 22px`；卡片内 `padding: 16px 18px`；卡片间距 14px；
- **圆角按层级区分，不统一**：

| 元素 | 圆角 | 理由 |
|---|---|---|
| 卡片 | 8px | 大块面，稍大圆角更柔和 |
| 按钮、输入框 | 6px | 可点击元素的触感 |
| 菜单项 | 5px | 可点击 |
| 需强调的标记 | 4px | 小面积色块 |
| 数据条 | 2px | **不可点击**，故接近直角——圆角是"这里可以点"的信号 |
| 状态色点 | 50% | 圆点本身 |

#### 4.5.4 组件形态原则

| 场景 | 形态 | 理由 |
|---|---|---|
| 列表中的状态（默认） | 色点 + 文字 | 一屏常同时出现五种以上状态；若全做成彩色胶囊，界面会布满色块、每个都在喊"看我" |
| 需警示/强调的状态 | 带底色标记 | 强调必须稀缺才成立，只给「明天截止」这类真正需要注意的用 |
| 表示量级 / 占比 | 直角长度条 | 长度本身表达大小；套上圆角矩形反而模糊了"量"的语义 |
| 操作按钮 | 三级：实心（主操作）/ 描边（次操作）/ 纯图标（工具性） | 按重要性分级，避免所有按钮长成同一个样 |
| 菜单选中态 | 左侧竖色条 + 浅底 | 色条直接回答"我在哪儿"，比整块圆角矩形定位更准 |
| 列表项 | 下边框分隔 | 不必把每一项都做成卡片；卡片只用于内容确实独立成块处 |

**明确禁止**：

- 全站共用一个圆角值；
- 所有卡片压同一层柔和灰阴影（阴影只用于真正需要"浮起"的元素，如悬浮层、下拉层）；
- 每个区块标题上方加全大写小标签；
- 用渐变作为装饰。

#### 4.5.5 暗色模式

**本期不做**。SRS 未要求，且会使样式量与回归成本翻倍。但全部色值已通过 CSS 变量收敛在 `src/styles/tokens.css`，将来新增暗色只需补一套变量值，无需改动任何组件。

### 4.6 入场动画设计（FR-016）

**定位**：未登录用户的**第一印象页**，兼作登录态预检窗口——动画播放的 1.8 秒同时用于判断"该进主页还是该进登录页"，**时间不浪费**。

**页面构成**（`Welcome.vue`，全屏、无侧栏无顶栏）：

| 元素 | 说明 |
|---|---|
| 背景 | 品牌紫深色渐变（复用 4.5.1 品牌色系），中央聚焦，无多余装饰 |
| 品牌图标 | 简笔 SVG（上升折线 + 靶心意象：求职进展与命中目标），缩放入场 |
| 主标题 | 「个人求职助手」，逐字依次浮现 |
| 副标题 | "AI 驱动的求职全流程工作台" |
| 进度指示 | 细进度条从左至右走完 1.8 秒，同时暗示"可点击跳过" |

**时间轴**（**总时长 1.8s，含末段 0.4s 淡出**）：

| 区间 | 动作 |
|---|---|
| 0 ~ 0.4s | 背景渐显；品牌图标 scale 0.8 → 1 + 淡入 |
| 0.4 ~ 1.1s | 主标题逐字浮现（每字间隔约 60ms，`animation-delay` 交错） |
| 1.0 ~ 1.4s | 副标题淡入；进度条同步推进 |
| 1.4 ~ 1.8s | 整体淡出，路由跳转 |

**跳转判定**（与动画并行执行，不阻塞播放）：

```
挂载 → 读本地 Token
  ├─ 无 Token            → 目标 = /login
  ├─ 有 Token（本地未过期）→ 目标 = /，同时后台调 GET /auth/me 校验
  │                          └─ 校验失败（80001/80002）→ 清除 Token，目标改为 /login
  └─ 动画结束（或被跳过）→ 按目标跳转
```

**实现约定**：

- **纯 CSS `@keyframes` + `animation-delay`**，不引入第三方动画库（演示环境稳定优先，且体积可控）；
- **可跳过**：点击任意处 / 按任意键 → 立即结束动画并跳转；
- **不重复播放**：用**模块级内存标记**记录本次会话已播放，SPA 内部路由跳转不再回放；**重新打开或刷新页面时重新播放**（入场仪式感所在，且 1.8 秒可跳过）。**为何不用 `sessionStorage`**：它在同一标签页刷新后仍然保留，会与本节「刷新页面重新播放」的口径直接冲突；内存标记随页面重载自然重置，两条要求同时成立；
- **无障碍降级**：`prefers-reduced-motion: reduce` 时跳过动画直接跳转；
- **异常兜底**：动画播放期间接口校验失败不打断动画，只改变跳转目标。

### 4.7 新手指引设计（FR-019，P2）

**定位**：新账号的**上手兜底**——不指望用户自己去摸导航，注册完进首页即用 5 步高亮把"核心功能在哪、先干什么"讲清楚；同时**不打断**（每步可跳过、高亮外区域照常可点）。

**实现选型**：`driver.js`（体积约 5KB、零依赖、原生遮罩 + 高亮 + 弹层，演示环境稳定）。不引入引导视频/帮助中心类重方案，也不自研遮罩（自研要处理定位、滚动、层级三类边界，得不偿失）。

**步骤编排**（步骤配置集中在 `GuideTour.vue` 的一个数组里，增删步骤只改配置）：

| 步 | 高亮目标 | 说明要点 |
|---|---|---|
| 1/5 | 侧栏「投递管理」 | 投递全记这里：表单 / 一句话 / 对话三种录入方式 |
| 2/5 | 侧栏「JD 匹配分析」 | 粘贴 JD 出匹配报告：评分 + 差距 + 准备建议 |
| 3/5 | 侧栏「AI 模拟面试」 | 选一条投递记录发起面试，语音作答 + 逐题点评 |
| 4/5 | 侧栏「八股陪练 / 错题本」 | 笔试备战主战场：答错自动进错题本，按 1/3/7/15 天复习 |
| 5/5 | 顶栏右上角用户菜单 | **AI 功能总开关**：AI 配置页填供应商 Key、选模型 |

**触发与标记流程**：

```
注册成功 → 自动登录 → 进入首页（/）
  └─ GET /settings → guide_done === true ?
       ├─ 是 → 不启动（正常使用）
       └─ 否 → 延迟 ~300ms（等首页元素渲染完）启动引导
                ├─ 走完最后一步点「完成」 → PUT /settings { guide_done: true }
                ├─ 任意一步点「跳过」     → PUT /settings { guide_done: true }
                └─ 中途刷新 / 关闭页面    → 不写标记，下次进首页重新开始
```

**个人中心重看**：个人中心放「重看新手指引」按钮 → 触发同一套引导，**不写标记**、不影响 `guide_done`；老账号也可随时查看。

**实现约定**：

- **元素缺失自动跳过**：`onHighlightStarted` 回调里检查目标元素是否存在（侧栏折叠、窗口过窄、节点未渲染），不存在则立即 `moveNext()`，不卡住流程；
- **不锁页面**：不使用 `disableActiveInteraction`，引导期间系统其余功能照常可用；
- **不做服务端强制**：`guide_done` 只是前端判断依据，接口不因未读引导拦截任何请求，重复播放无副作用；
- **不与入场动画叠加**：触发路径唯一（注册成功首次进首页），此时入场动画已播放完毕。

**依赖登记**：`driver.js` 需加入前端依赖清单（项目结构文档 **§5 依赖清单**，由前端侧登记；已于 v1.17 登记）。

### 4.8 校招情报界面设计（FR-021 / FR-022，P1）

**定位**：校招情报页（`/campus`）是**候选池**、投递管理页是**进度追踪**，需求上是「先有候选、再谈进度」的两段式，**功能不重复**。但两者在界面上容易被读成重复，本节把分离约定固化下来，步骤 23 实现时照此执行（纯界面层约定，不影响任何接口与数据）。

**与投递管理的关系**（五条分离约定）：

| # | 约定 | 理由 |
|---|---|---|
| 1 | **位置**：招聘信息的家在 `/campus`，**不进投递管理页**；投递页只在「新建投递」表单接受「从岗位预填」这一个入口 | 一条信息一个家；两页都放就是两套重复列表 |
| 2 | **视觉语言分离**：投递管理用**看板 + 状态色**（列 = 状态、拖拽流转），校招情报用**列表 / 日历 + 时间 · 匹配度** | 同一套配色与排布会让人以为是同一批数据 |
| 3 | **岗位的信息状态不复用投递状态色**：`--s-*` 状态色为投递链路专属（见 4.5.1），岗位的 `ACTIVE` / `CHANGED` / `EXPIRED` 用**角标（已变更）+ 灰化（过期）**表达 | 两处字段都叫 `status` 但含义不同（两套枚举见数据库设计 §5），同名不同义最易混 |
| 4 | **已投递的岗位沉底或弱化** | 使命已完成，占着显眼位置是重复感的最大来源 |
| 5 | **概览页只放入口不展开**：3 条匹配度最高 + 「查看全部」跳 `/campus` | 概览页是入口，不是第二个校招情报页 |

**空态口径**：判定条件是**「是否真的什么都看不到」**而非「是否零投递」——`application_count === 0` **且**校招情报（宣讲会 / 双选会 / 岗位）也为空时，才显示空态引导卡；任一侧有内容就正常渲染区块。零投递但有岗位时，用户**有东西可投**，此刻应直接把岗位 / 宣讲会显示出来（它是本页唯一有内容的部分），而不是让用户跳出去找。引导卡文案按场景区分：全空说「还没有任何信息」，仅无投递说「看看这些机会」。

**模块色**：`--m-campus: #93AE55`（黄绿）——与陪练的青绿 `#5BAE84` 区隔，填补现有模块色相（15°/40°/150°/180°/215°/270°/340°）中黄绿一带的空缺；色值以 4.5.1 与 `tokens.css` 为准。

## 5. 核心机制设计

### 5.1 SSE 流式协议

**端点清单**（全部 POST + JSON 请求体，完整定义见接口文档）：`/stream/jd-analysis`（JD 分析）、`/stream/interview-chat`（面试作答+点评+下一题）、`/stream/interview-summary`（面试总结）、`/stream/practice-review`（陪练点评）、`/stream/experience-extract`（面经结构化）、`/stream/agent-chat`（Agent 对话）。

**事件格式**（text/event-stream）：

```
event: start
data: {"message": "正在分析…"}                  // 连接建立后立即推送，见下方感知延迟优化

event: delta
data: {"text": "增量文本片段"}

event: done
data: {"record_id": 123, "extra": {...}}
```

- `start`：**感知延迟优化**——后端进入 generator 后立即推送状态文案（"正在分析你的 JD…"等），界面在 300ms 内出反馈，覆盖 LLM 首字前的静默等待；LLM 首字 <2s 是真实延迟目标（NFR-001），start 事件保证用户从点击到界面反馈 <300ms（NFR-004 口径）；
- `delta`：LLM 增量 token（已按报告结构分段时带 `section` 字段标识当前段落）；
- `error`：中途失败，data 含错误码与 message，前端保留已渲染内容并显示重试；
- `done`：流结束，携带落库记录 id，前端据此刷新列表/跳转。

**后端实现要点**：

- 路由返回 `StreamingResponse(generator, media_type="text/event-stream")`；
- generator 内循环 `llm_client.stream_chat()`，逐块 yield；
- 连接断开（客户端刷新/关闭）→ generator 捕获 `GeneratorExit`/客户端断开异常，终止 LLM 调用，已生成内容按"半成品"落库（标注 interrupted）；
- 每个 SSE 请求内部持有独立 DB session，不与请求全局 session 混用。

### 5.2 Agent 设计（手写，不用 LangChain）

**整体循环**：

```
用户输入
  → ① 意图路由（规则+LLM 混合）：先规则快筛（关键词），不命中再 LLM 分类
  → ② 命中"需工具"意图：LLM Function Calling 输出 {tool_name, arguments}
      未命中：LLM 直接流式闲聊/问答回复（注入画像）
  → ③ 工具执行分两类：
       a. 查询类（查投递/搜面经/查提醒）：直接执行，流式回显结果卡片
       b. 写操作类（新增投递/更新状态/入错题本）：返回"确认卡片"给前端，
          用户点击确认后调用普通 REST 接口执行——LLM 绝不直接写库
  → ④ 执行结果以结构化卡片 + 流式文字总结回显
```

**意图枚举**：`APPLICATION`（求职操作）/ `PRACTICE`（笔试学习）/ `EXPERIENCE`（面经问答）/ `CHAT`（闲聊）。

**工具注册表**（Python dict：工具名 → 工具元数据 + 执行函数）：

| 工具名 | 类型 | 说明 |
|---|---|---|
| create_application | 写（确认卡片） | 提取公司/岗位/城市/日期，出确认卡片 |
| list_applications | 查询 | 按状态/公司过滤 |
| update_application_status | 写（确认卡片） | 状态流转 |
| generate_questions | 查询 | 出 N 道指定方向题目（可入库） |
| quiz_wrong_questions | 查询 | 抽错题（跳转抽问） |
| search_experience | 查询 | 关键词搜面经 |
| get_today_summary | 查询 | 今日概览摘要 |

**Function Calling 实现**：openai 兼容 SDK 原生支持 `tools` 参数（JSON Schema 描述工具），**不手写 JSON 解析**——SDK 返回结构化 `tool_calls`，失败时降级为追问"请再说清楚一点"。

**确认卡片场景的等待优化**：Function Calling 同样走 `stream=True`（tool_calls 增量回调），收到完整 tool_call 立即推 `tool_call` 事件；LLM 前置文字（如"好的，帮你记一笔"）以 `delta` 先上屏——用户先看到文字反馈、再看到确认卡片，全程无干等。

**画像注入**：组装 system prompt 时拼入画像摘要（结构化文本 ≤ 500 token），仅在 `APPLICATION`/`EXPERIENCE` 意图注入，`PRACTICE` 不注入（控制 token，NFR 低延迟措施第 6 条）。

**对话历史**：落库（agent_message 表），每次请求携带最近 10 轮，超长截断。

### 5.3 Prompt 工程

**统一约束（所有场景 system prompt 头部）**：

1. 角色设定一句（面试官/点评官/求职助手）；
2. 输出格式要求（如 JD 报告五段结构、每题点评三段结构）——用序号标题分隔，便于前端分段渲染；
3. 长度约束（如"参考答案 ≤ 200 字"）——控制 token 与首字延迟；
4. 禁止输出 markdown 表格（打字机渲染体验差），用列表。

**场景 prompt 模板表**（模板存 `backend/app/prompts.py`，统一管理便于调优）：

| 场景 | 要点 |
|---|---|
| JD 分析 | 画像全文 + JD 原文；强制五段结构；分项评分 0~100 |
| 模拟面试 | 公司/岗位/方向 + 已问题目摘要；一题一答节奏；点评 = 评分+亮点+不足+参考要点 |
| 面试总结 | 全部问答记录；输出总评+分题得分表（列表式）+改进清单 |
| 陪练点评（主观题 / 客观题） | 题目 + 参考答案 + 用户答案；输出评分 + 参考答案对照 + 差距点 |
| 陪练点评（**场景题**） | 题目 + **参考框架** + 四维 `rubric`（解题框架 / 量化估算 / 取舍权衡 / 兜底降级）+ 用户答案；**按四维分项给分并逐维点评**，输出四个固定 section 供前端分栏渲染；措辞用"参考框架"而非"标准答案"（场景题无唯一解） |
| 面经结构化 | 原文；LLM 流式输出 JSON 数组[{question, answer_points}]，后端流式收集增量——前端不逐字展示 JSON，显示提取进度状态，done 后回显条目供确认 |
| Agent 系统 | 画像摘要 + 工具说明；Function Calling 模式 |
| 错题判定 | 题目+标准答案+用户答案（场景题另加四维 `rubric`，判定依据同为标尺）；输出 {"correct": true/false, "explain": "..."}；`CHOICE` 题不走 LLM，规则比对 |
| 提醒文案 | 结构化提醒数据；输出一句话文案（失败用模板兜底） |

**题型分派**：陪练作答的处理路径按 `question.qtype` 分派——`CHOICE` 走**规则判定**（不调 LLM，零 token、即时返回）；`SUBJECTIVE` 走普通点评模板（评分 + 参考答案 + 差距点）；`SCENARIO` 走四维点评模板（**必须携带该题的 `rubric` 作为评分标尺**，输出四个维度的分项点评）。题库的两级分类（`stack` → `direction`）只影响**抽题筛选**，不影响点评路径；抽题时可同时按栈与题型筛选（如"只看 Java 后端的场景题"）。**错题复习判定同样按题型分型**（`CHOICE` 规则比对、`SUBJECTIVE` 与 `SCENARIO` 走 LLM 判定，场景题的判定依据为「标准答案 + 四维 `rubric`」）。

- 全部走 **OpenAI 兼容协议**：选供应商 = 定 base_url 与 Key；选模型 = 定 model——两级配置，SDK 与调用代码零改动；
- 注册表内建在代码中（`llm_provider.py`），新增供应商/模型只需加配置，无需改业务代码；
- **base_url 可覆盖**：注册表值为默认，`llm_provider_config.base_url` 有值则优先生效（应对供应商端点变更）；
- 免费供应商限速时触发统一兜底（重试 + 错误提示），与付费供应商行为一致。

**多供应商配置存储（每账号一份，可并存）**：

```
llm_provider_config（每账号 × 每供应商一行）
  user_id + provider 唯一
  ├─ api_key      加密存储（Fernet），接口只回 "是否已配置"
  ├─ base_url     可空（空=用注册表默认）
  ├─ model        该供应商下选定的模型（各家独立记忆）
  └─ is_active    当前生效标记（每账号至多一行为 true）
```

- **激活语义**：`is_active=true` 的那行决定后续所有 LLM 调用（base_url + api_key + model）；
- **切换**：把新供应商行置 `is_active=true`、原行置 false（同一事务内完成，保证至多一行生效）；
- **删除**：删除某行不影响其他行；删除当前生效行时 AI 功能进入"未配置"状态（10012）；
- **配置缓存**：进程内按 user_id 缓存生效配置，配置变更时失效（避免每次调用查库）。

**模型列表动态更新（保证可选模型"最新可用版本"）**：

- OpenAI 兼容协议提供 `GET /models` 端点；`llm_provider.list_models(provider, base_url, api_key)` 实时拉取该供应商当前可用模型；
- 拉取结果缓存 24h（存 `llm_provider_config.models_cache`，JSON 含 fetched_at，**天然按 provider + base_url 维度**——同一账号同一供应商仅一行）；AI 配置页"刷新模型列表"强制重拉；拉取失败回退内置表并在 UI 标注"内置列表（上次拉取失败）"；
- 内置表随项目版本维护；运行时以动态拉取为准。

**模型退役兜底**：供应商退役模型 ID 时通常自动路由替代模型（如 deepseek-v4-pro → deepseek-flash）；调用返回"模型不存在"→ 提示用户去 AI 配置页重选模型（错误码 10013 含此原因）。

探测类（不产生对话内容）与对话类分属两个模块，**探测类在步骤 6 已落地**（`llm_provider.py`），对话类在步骤 10（`llm_client.py`）：

```
llm_provider 职责（clients/llm_provider.py，步骤 6 落地）：
├─ test_connection(provider, base_url, api_key, model) → 连通性测试（发一条最小消息，返回实际生效的模型名）
├─ list_models(provider, base_url, api_key) → GET /models 拉取模型列表（失败抛探测错误，回退内置表由服务层决定）
├─ 12 项供应商注册表 + 内置模型表（离线回退用）+ resolve_base_url（账号配置优先于内置默认端点）
└─ 超时 10s、不重试（探测类请求，失败即刻反馈）

llm_client 职责（clients/llm_client.py，步骤 10 落地）：
├─ resolve_config(db, user_id) → 统一配置：读当前账号的 llm_provider_config 生效行并解密 Key
│                                （运行时读取，切换即时生效），返回 LLMConfig（供应商/端点/密钥/模型）
├─ stream_chat(config, messages, tools=None) → 生成器，逐块 yield token（LLM 侧 stream=True）；
│                                **同步迭代**——与全项目同步调用风格一致，StreamingResponse 直接消费
├─ chat_json(config, messages) → 非流式，返回解析后的 JSON（面经结构化 / 投喂抽取用）；
│                                容忍 ```json 围栏与前后解释文字，解析失败抛 10011
├─ 超时：连接 5s、首 token 8s（read 超时兼作「流中途静默超时」）；超时抛 LLMError
├─ 重试：失败重试 1 次（仅连接错误 / 超时 / 服务端 5xx；429 与鉴权错不重试）；
│         流式只重试「建流」阶段——已开始输出后再重试会导致内容重复
├─ 异常映射：配置缺失与 Key 无效 → 10012、模型不存在 → 10013、输出格式 → 10011、
│             其余（网络 / 超时 / 限流 / 5xx）→ 10010
└─ mock 注入点：get_llm_client() 依赖注入（测试以 app.dependency_overrides 替换替身，见测试计划）
```

**Key 读取链**：当前账号的 `llm_provider_config` 生效行（AI 配置页填写）→ 环境变量（.env，本地单机兜底）→ 都无则调用前抛配置错误（10012），前端引导去 AI 配置页。**生效行存在但不完整时（缺端点 / 缺 Key / 未选模型）不走 .env 兜底**，按缺失项直接提示——否则会把环境变量的 Key 配到账号所选的端点上，Key 与端点错配比"未配置"更难排查。

**加密方案**：`api_key` 以 Fernet 对称加密后入库，主密钥 `APP_SECRET_KEY`（与 JWT 同一密钥源，.env）派生；解密仅在调用供应商前内存中发生，**永不回显给前端**（只返回 `key_set: true/false`）。

### 5.5 定时引擎设计

- APScheduler `BackgroundScheduler`，启动时随 FastAPI lifespan 注册，**每日 07:00 触发**一次 `reminder_engine.run_daily()`（开发期提供手动触发接口便于演示，见接口文档）；
- **执行单元为账号**：任务开始先查 `user` 表取全部账号，**逐账号**执行判定与提醒生成（提醒记录归属该账号）；单账号失败不中断其余账号（异常捕获 + 日志）；
- 判定全为纯规则 SQL（无 LLM），**每条 SQL 均带 `user_id` 条件**：

| 任务 | 实现 | 范围 |
|---|---|---|
| 投递跟进 | `WHERE user_id=? AND status='APPLIED' AND date(now) - date(applied_at) > 3` | 逐账号 |
| 错题到期 | `WHERE user_id=? AND next_review_at <= now AND review_stage < 5` | 逐账号 |
| 待面试 | 按 `next_event_at` 字段区间查询（投递记录上的笔试/面试时间字段），带 `user_id` | 逐账号 |
| 校招信息采集 | 逐源抓取（三家就业网站系统适配器）+ 处理层去重 / 变更检测 / 归档后落库（见 5.9）；**单源异常只标记该源状态**，不影响其余源 | **全站一次**（公共数据，不重复抓取）；抓完对每个账号跑一遍订阅匹配 |

- 提醒文案：数据齐后调 LLM 一次生成概览文案（**用该账号自己的 AI 配置**；未配置或失败时用固定模板）；
- 执行互斥：`max_instances=1, coalesce=True`，防重入；
- 性能：账号数量级为个位数至十位数，逐账号串行执行即可，无需并发。

### 5.6 语音链路设计（P2）

**ASR 链路（长时长语音作答）**：

```
[前端] 点击「开始作答」→ MediaRecorder 持续录音（audio/webm）
  → 前端 VAD 静音检测：静音达阈值即切出一句（3~15s 片段）
      阈值随语速自适应：快 1.6s / 正常 2.65s / 慢 3.6s
    → POST /api/v1/asr/transcribe（multipart 上传单句音频）
      → asr_client.transcribe(audio_bytes, user_id)
        → 读当前账号配置的 ASR 供应商（config 表）：
             ├ funasr（默认）：进程内调用 paraformer-zh-streaming，不出网
             └ xunfei（备选）：实时语音转写，Key 取账号配置（加密存储）
      → 返回 { text }（仅文字，不落库不提交）
[前端] 逐句累积回填输入框（同时记录每句起止毫秒）→ 用户编辑
  → 提交作答时一并上传 segments（seq / start_ms / end_ms / 原始转写文本）
    → speech_metrics 计算指标 → 指标与作答文本一并落库、生成点评
```

**TTS 链路（语音播报）**：

```
[前端] AI 回复流式渲染结束（或用户点播报按钮）
  → POST /api/v1/tts/synthesize { text, voice? }（voice 缺省取账号配置）
    → tts_client.synthesize() → edge-tts 合成 mp3
         （按 sha1(text+voice) 缓存命中则直接返回）
  → 返回音频流（audio/mpeg）→ 前端 <audio> 播放，可随时停止
```

- `asr_client` 抽象基类 + `FunAsrClient`（默认，进程内）+ `XunfeiAsrClient`（备选）；`tts_client` 抽象基类 + `EdgeTtsClient`（备选豆包预留）；**ASR 供应商 / TTS 音色按账号存储**（设置页维护；讯飞 Key 加密规则与 AI Key 一致）；
- **模型加载策略**：FunASR 进程内**单例 + 懒加载**（首次调用时加载，不拖慢 uvicorn 启动）；模型文件由 ModelScope（AutoModel）首次联网下载到**本机用户缓存目录**（默认 `%USERPROFILE%\.cache\modelscope`，约数百 MB，**不在仓库内、不入库**），此后离线可用；若改到项目内目录，须另加 `.gitignore` 规则（现有规则只覆盖 `backend/uploads/` 与 `backend/cache/`）；
- **长时长支持**：单句上限约 15s（由 VAD 切分保证），一场面试**不限轮次、不限总时长**；前端只上传已切出的句子，不缓冲整场音频；
- **分句时间轴**：VAD 在前端执行，**句间停顿仅前端可得**——前端须在**提交作答时**随作答上传 `segments`（每句 `seq` / `start_ms` / `end_ms` / 原始转写文本），这是表达力指标的**唯一数据来源**；逐句转写接口 `POST /asr/transcribe` 本身不变；
- 转写失败：错误码 60001，前端 toast「转写失败，可重试或直接打字」，**不阻塞面试流程**；
- 播报失败：错误码 60002，**静默降级为不播报**（不打断对话）；TTS 缓存目录 `backend/cache/tts/`。

### 5.7 表达力分析设计（FR-014）

**分层位置**：指标计算下沉为**纯函数模块** `app/utils/speech_metrics.py`——输入分句数组，输出指标字典；**零外部依赖、不触发 LLM、可独立单元测试**。服务层在提交作答时调用，结果以 JSON 存入 `interview_qa.voice_metrics`（模拟面试）与 `drill_attempt.voice_metrics`（练习模式），两处字段结构完全一致、由同一函数产出。

**输入与产出**：

| 输入 | 产出（`voice_metrics`） |
|---|---|
| `segments: [{seq, start_ms, end_ms, text}]` | 基础量（总时长 / 有效语音时长 / 沉默时长 / 字数）＋ 五项指标（语速 / 填充词密度 / 停顿点 / 有效时长占比 / 流畅度趋势）＋ `quality` 标记 ＋ `version` 算法版本 |

指标口径与参考区间见 SRS §3.11，字段结构见数据库设计文档。

**为什么指标与点评分列**：

- **指标是客观事实**——纯算法计算，毫秒级、零 token 成本，作答提交后**即时**返回，用户先看到数字；
- **点评是主观解读**——LLM 生成，把指标与作答文本一并作为上下文，产出教练式解读（**须引用原话**），流式返回；
- 两者分列展示、互不覆盖：内容维度评"答得对不对"，表达维度评"说得顺不顺"。

**停顿点与知识点的联动**：停顿点的 `context`（停顿前一句的末尾若干字）由 LLM 判断是否构成知识点；若是，与模拟面试点评中"不足"同口径提示入错题本候选（用户确认后入本）。

**为什么带 `version`**：算法口径调整后新旧数据不可直接比较（跨次进步曲线对此尤其敏感），`version` 用于标识口径版本；**跨版本数据在对比视图中不并列展示**——宁可少展示一次对比，也不给出失真的进步曲线。

### 5.8 乐观更新机制

适用场景：Agent 一句话录入投递、状态流转确认。

```
用户对 Agent 说"记一笔投递"
  → LLM 提取字段 → 前端立即渲染确认卡片（此时尚未入库，卡片标"待确认"）
  → 用户点确认 → 调 POST /applications → 成功：卡片转"已入库"+ 看板刷新
                → 失败：卡片转红色错误态 + 重试按钮
```

原则：**乐观展示、确认才写、失败可重试**；任何写操作必须有后端确认，前端不得仅本地模拟成功。

### 5.9 校招情报链路设计（FR-021 / FR-022，P1）

**定位**：把多所高校就业网站的宣讲会 / 双选会 / 岗位聚合到一处。**采集层**取数据、**处理层**（纯函数）清洗判定、**消费层**（接口与页面）呈现，三层之间只通过数据结构通信——目标站点改版只换采集适配器，去重、打分、归档逻辑零改动。

```
采集层 Collector ─────────────▶ 处理层 Processor（纯函数、无 IO）──▶ 消费层 Consumer
├ adapters/njust_91job.py（JSON API）  ├ 归一化（全角/空白/日期）      ├ GET /campus-events、/job-postings
├ adapters/bysjy.py（HTML + menu_id）  ├ 去重指纹 dedup_key（跨源合并）├ GET /calendar（四类事件聚合）
├ adapters/jysd.py（HTML + universityid）├ 变更检测 content_hash（改期） ├ 匹配打分排序（零 token）
└ 投喂通道（LLM 抽取 → 预览确认）      └ 过期归档（EXPIRED / 物理删除） └ 订阅规则 → 写入 reminder
      ▲ 网络 / 异常 / 限频                └ 匹配打分（城市/方向/专业）      ▲ HTTP 接口
```

**采集层**：

| 项 | 设计 |
|---|---|
| 适配器协议 | `fetch(source: CrawlSource) -> list[RawItem]`；`RawItem` 是统一中间结构（标题 / 公司 / 时间 / 地点 / 专业 / 链接），**不含业务状态与指纹**——采集层只负责"把页面变成结构化条目" |
| 解析器 | **一家系统厂商一个模块**：91job 走免登录 JSON API、云就业与才立方走 HTML（`menu_id` / `universityid` 取源配置），站点差异全部收敛在参数里 |
| 源配置 | `crawl_source` 表一行 = 一所学校的一个站点；**新增学校 = 加一行配置 + 填参数，不写代码** |
| 调度 | 并入每日任务全站执行一次；另提供 `POST /crawl-sources/run` 手动触发（可指定 `source_id` 单源跑，便于调试与演示） |
| 单源隔离 | 逐源 `try/except`：失败只写该源的 `last_status` / `last_error` / `last_crawl_at`，**不影响其余源，也不影响提醒等其他每日任务** |
| 合规约束 | UA 标识 / robots 检查 / 同域请求间隔 ≥2s / 429 暂停 / 持续 403 停止不重试（NFR-016），**统一实现在合规模块中**，不散落到各解析器 |

**处理层（`app/clients/crawler/processor.py`，纯函数、零 IO、可离线单测）**：

| 函数 | 职责 |
|---|---|
| 归一化 | 全角→半角、去首尾空白、公司名去括号后缀、日期统一 `datetime`——**仅用于指纹与匹配计算，原文展示值不归一** |
| 去重指纹 | 宣讲会/双选会 = `sha1(归一(公司)+归一(标题)+日期)`；岗位 = `sha1(归一(公司)+归一(标题)+归一(城市))`。同一条信息跨源出现时指纹相同 → **只留一条**、`source_site` 记多个来源 |
| 变更检测 | 条目算 `content_hash` 与库中同 `dedup_key` 记录比对：无此指纹 → 新建；哈希相同 → 只更新 `last_seen_at`；**哈希不同 → 覆盖字段值 + `changed_at=now` + `status=CHANGED` + 触发订阅推送**（改期即提醒） |
| 过期归档 | 活动日期已过 / 岗位过截止日期或 30 天未再抓到 → `EXPIRED`；`EXPIRED` 距今超 90 天物理删除。**源 `last_status != OK` 时不执行归档**——避免源故障导致全量误清 |
| 匹配打分 | 城市 +30 / 方向 +40 / 专业 +30（满分 100）；**字段缺失的维度不扣分也不隐藏**，总分即命中项之和（不做百分比折算），仅影响排序 |

**投喂通道**：粘贴文本或链接 → `llm_client.chat_json` 抽取字段 → **返回预览、此时不入库** → 用户确认后落库（与 5.8 乐观更新同口径：AI 抽取可能错字段，确认是最后一道关）。链接抓取走同一套合规约束，**并拒绝内网地址**（见第 6 章 SSRF）；抽取失败或链接需登录 → 70003 + 降级手动填表。

**订阅匹配与推送**：采集落库后，遍历全部账号 × 其启用中的订阅规则（账号数个位数，串行即可）逐条比对 → 命中写 `reminder`（`reminder_type=INFO_MATCH`、`ref_type` 区分来源表、`ref_id` 为信息 id、**用模板文案不调 LLM**）。**匹配范围限「公共信息 + 该账号自己的投喂记录」**——沿用 3.6 的跨账号隔离口径，越权防护为必测项。重复提醒由现有 `UNIQUE(user_id, reminder_type, ref_id, remind_date)` 天然挡住。

**消费层**：校招情报页（三类信息 Tab + 筛选 + 时间/匹配度排序 + 卡片操作）、订阅管理、源管理（设置页，系统级）与 **FR-022 日历**——`GET /calendar?start=&end=` 一次返回**四类事件**（宣讲会 / 双选会取 `campus_event`，笔试 / 面试取当前账号的 `application.next_event_at`），替代前端并发拉两个列表；空区间返回空数组不报错。

**模块归属**：`app/clients/crawler/`（`adapters/` 三个解析器 + `processor.py` + `compliance.py`）+ `app/services/campus_service.py`（调度编排、落库、订阅匹配）+ `app/routers/`（`campus.py` / `crawl_sources.py` / `subscriptions.py`）——详见项目结构文档。

## 6. 安全设计

| 威胁 | 设计对策 |
|---|---|
| 密钥泄露 | API Key **加密存储**（Fernet，主密钥在 .env 且已 gitignore）；接口**永不回显明文**（只返回 `key_set` 布尔）；日志脱敏（不打印 Key/请求头/请求体中的 Key 字段） |
| 密码泄露 | bcrypt 哈希存储（含盐、不可逆）；明文密码不落日志、不入库、不返回；登录失败 5 次锁定 5 分钟 |
| 未授权访问 | 全局鉴权依赖 `get_current_user`，白名单仅 `/health`、`/auth/register`、`/auth/login`；**SSE 端点同样鉴权** |
| 水平越权（跨账号） | 服务层查询强制携带 `user_id`（来源为登录态，不接受前端传入）；跨账号访问返回 404 + 10002，与"不存在"不可区分（见 3.6） |
| Token 泄露/滥用 | Token 有效期 ≤30 天（默认 1 天）；修改密码后旧 Token 立即作废（Token 载荷 `pwd_ver` 比对）；Token 仅存前端 localStorage，不入 Cookie |
| SQL 注入 | 全程 SQLAlchemy ORM 参数化；禁止 raw SQL 拼接（NFR-009） |
| XSS | 前端不 v-html 渲染 LLM 输出/用户输入；后端 DTO 长度校验（NFR-010） |
| SSRF | ①**自动抓取**：目标限 `crawl_source` 已登记域名（仅 http/https），不跟随跳转到未登记域名（NFR-016）；②**投喂链接抓取**：**拒绝内网地址**——环回 / 私网段（10./172.16-31./192.168./169.254.）/ `localhost` 等一律拒绝，跳转后的最终地址同样校验，防止被当作内网探测工具（见 5.9）；③**自定义供应商 base_url 仅由本机用户配置，不对外暴露** |
| 路径穿越 | ①批量导入文件：校验扩展名+大小 ≤ 2MB+临时目录读取，文件名不参与路径拼接；②**头像上传**：服务端重命名为 `{user_id}_{uuid8}.{ext}`，不使用用户提供的文件名（NFR-015） |
| CSRF | 鉴权凭据为 `Authorization` 头而非 Cookie（无状态 JWT），浏览器不会自动携带，**天然免疫 CSRF**，不引入 CSRF token（设计声明） |

## 7. 异常处理设计

| 场景 | 处理 |
|---|---|
| LLM 超时/网络错 | llm_client 重试 1 次 → 失败抛 LLMError → SSE 发 error 事件（流中）/ 502（普通请求）→ 前端提示+重试按钮 |
| LLM 返回格式不符 | 解析失败 → 降级为纯文本流式展示（JD 报告）；JSON 场景（面经/错题判定）解析失败 → 重试 1 次后提示"AI 输出异常，请重试"，数据不落库 |
| 用户中途关页面（SSE 断连） | 后端捕获断开，终止 LLM 调用，已生成部分落库（标记 interrupted），不重复计费 |
| 数据库连接失效（MySQL 空闲断连） | 引擎启用 `pool_pre_ping`（取连接前探活）+ `pool_recycle=3600`（早于 MySQL 默认 `wait_timeout`）；失效连接由连接池自动重建，业务无感 |
| **源解析失败**（就业网结构改版） | 该源标记 `FAILED` + 记录失败原因；**保留上次数据、不归档、不影响其余源与其他每日任务**，前端只显示源状态异常（手动单源抓取时返回 70002） |
| **站点拒绝抓取**（403 / 429） | 429 → 当日暂停该源；**持续 403 → 停止该源且不再重试**（不绕过技术防护，NFR-016）；源状态标记为「被拒绝」，待人工确认后恢复 |
| **投喂解析失败**（AI 抽取失败 / 链接需登录） | 400 + 70003，message 区分两类原因；**不入库**，前端降级为手动填表 |
| **Token 过期/无效** | 普通请求：401 + 80001/80002 → 前端拦截器清 Token 并跳登录页；**SSE 请求**：连接建立阶段返回 401，流中途失效以 `error` 事件下发后关闭连接，前端提示并跳登录页 |
| **改密后旧 Token 被踢** | 校验 Token 载荷 `pwd_ver` 与库中当前密码版本是否相等 → 不等则 401 + 80002，前端提示"密码已修改，请重新登录" |
| **账号锁定期间登录** | 403 + 80005，message 给出剩余锁定分钟数，前端在登录表单下展示 |
| **头像文件缺失** | `user.avatar` 有值但文件不存在 → 返回 404，前端回落到默认头像（不报错、不阻塞页面） |
| **本地语音模型缺失/首次下载失败** | 首次调用时拉取模型失败 → 60001 + 提示「首次使用需联网下载语音模型，请检查网络后重试」；已下载过则离线不受影响 |
| **TTS 合成失败**（断网 / 接口变更） | 60002 → 前端**静默跳过播报**（不弹错、不打断对话），用户可手动再点播报重试 |

## 8. 可测试性设计

- **LLM mock 注入点**：出网调用收口在 clients 层两个模块——**对话类收口 `llm_client`（注入点 `get_llm_client`）、探测类（拉模型列表 / 连通性测试）收口 `llm_provider`**，业务层不得直接 new openai 客户端；测试以 `app.dependency_overrides[get_llm_client]` 注入对话替身（返回预设 token 流 / JSON），探测类以 monkeypatch 探测函数模拟拉取失败，全部 AI 链路离线可测（详见测试计划）；
- **语音 mock**：`asr_client` / `tts_client` 抽象接口，测试注入 `FakeAsr`（返回预设文本）与 `FakeTts`（返回固定音频字节），**测试不加载本地模型、不调用 edge-tts**（离线可跑）；
- **表达力指标**：`app/utils/speech_metrics.py` 为纯函数模块（输入分句数组 → 输出指标字典），不依赖数据库与网络，直接构造分句样例断言五项指标与边界（空数组 / 单句 / 全静音 / 作答不足 10 秒），无需 mock 任何外部组件；
- **定时任务**：`reminder_engine` 的判定函数为纯函数（输入时间戳/记录集 → 输出提醒集），不依赖调度器即可单测；
- **采集适配器快照**：适配器从注入的 HTTP 客户端取页面，测试替换为「读本地快照」的替身，快照按厂商存于 `backend/tests/fixtures/crawler/`（正常页 + **改版页**各一份）→ 断言字段映射正确、改版时抛出解析异常而非静默产出脏数据，**测试不出网**；
- **处理层纯函数**：`processor.py`（归一化 / 去重指纹 / 变更检测 / 过期归档 / 匹配打分）无 IO，直接构造条目断言——同条跨源 → 只留一条、改期 → `CHANGED` 且触发推送、**源状态非 OK → 不执行归档**、字段缺失 → 不扣分不隐藏；
- **合规断言**：合规模块统一注入，测试替身记录请求头与时间戳 → 断言 UA 为 `JobHunterBot/1.0`、**同域请求间隔 ≥2s**、robots 拒绝时跳过；投喂链接的**内网地址必测**（环回 / 私网段 / 跳转后落到内网各一条，见第 6 章 SSRF）；
- **鉴权注入点**：`get_current_user` 为 FastAPI 依赖，测试可通过 `app.dependency_overrides` 注入指定账号（免去每个用例都真实登录），也可直接携带真实登录 Token 做端到端校验；
- **多账号隔离测试**：注册 A/B 两账号，用各自 Token 交叉访问对方资源 id，断言返回 404/10002（越权防护为必测项，见 3.6）；**订阅匹配额外断言：A 的订阅不得命中 B 的投喂记录**（见 5.9）；
- **测试数据库**：pytest 使用独立的 **`job_hunter_test` 库**（与开发库 `job_hunter` 物理隔离，库需先手工创建、见数据库设计 §7.1），不碰开发库；用例间通过建表/清表保证互不污染。
