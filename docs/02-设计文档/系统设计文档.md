## 1. 引言

### 1.1 编写目的

本文档承接需求规格说明书（SRS），给出系统的技术架构与核心机制设计。开发人员按本文档 + 接口文档 + 数据库设计文档实现代码，不得偏离。

### 1.2 设计原则

| 原则 | 落地方式 |
|---|---|
| 低延迟优先 | 所有 LLM 输出 SSE 流式；prompt 精简；定时任务不阻塞请求（NFR-001~004） |
| LLM 失败不致命 | LLM 封装层统一重试/降级；纯数据功能与 LLM 功能完全解耦（NFR-005/006） |
| 可测试 | LLM 调用全部收敛到单一封装层，测试时注入 mock（NFR-012） |
| 最小依赖 | Agent 手写；数据库 SQLite；除 LLM/STT 外无外部服务 |
| 文档一致 | 本文档引用的表名/接口路径/枚举与数据库设计文档、接口文档严格一致 |

## 3. 后端设计

### 3.1 分层架构

```
routers/（API 层）：路由、参数校验、鉴权（无）、异常捕获 → 只做协议转换
services/（服务层）：业务逻辑、事务边界、LLM 调用编排 → 不做协议细节
models/（数据层）：ORM 模型、枚举、DDL 映射
schemas/（传输层）：Pydantic 请求/响应模型（DTO）
```

**规则**：routers 禁止直接访问 ORM；services 禁止返回 ORM 对象给 router（必须转 DTO）；所有 LLM 调用必须经 `llm_client`，任何地方不得直接 new 一个 openai 客户端。

### 3.2 统一响应体

```json
{ "code": 0, "message": "ok", "data": {} }
```

- `code=0` 成功；非 0 为错误码（完整错误码表见接口文档）；
- 列表类 `data` 统一为 `{ "total": n, "items": [...] }`（分页规范见接口文档）；
- SSE 流式端点不走此格式（事件协议见 5.1）。

### 3.3 全局异常处理

| 异常 | 响应 |
|---|---|
| 参数校验失败（Pydantic/RequestValidationError） | 400 + 错误码 10001，message 列出首个字段错误 |
| 资源不存在 | 404 + 错误码 10002 |
| LLM 调用失败（llm_client 抛出 LLMError） | 502 + 错误码 10010，message 提示"AI 服务暂不可用，请重试或检查设置" |
| 未捕获异常 | 500 + 错误码 10000，记录日志（logging），响应不含堆栈 |

### 3.4 事务边界

- 写事务最小化：单条 SQL 的简单写入由 ORM 自动提交；跨表写入（如"面经主记录 + 结构化条目"）在服务层显式 `with Session.begin()`；
- LLM 调用**不在事务内**：先完成 LLM 获取结果，再开事务落库，避免长事务占用锁。

| store | 职责 |
|---|---|
| `useAppStore` | 设置项、全局提示（el-message 封装） |
| `useAgentStore` | 悬浮球开关、对话历史、工具确认卡片队列 |

页面内短生命周期状态（看板数据、面试会话）用组件局部 state，不滥用 Pinia。

### 4.3 前端工程约定

- 请求统一走 `src/api/` 封装（axios 实例，统一拦截 code≠0 弹错）；
- 组件按页面分目录：`src/views/<page>/`；
- LLM 流式文本一律渲染为纯文本（`{{ }}`），**不用 v-html 渲染 LLM 输出**（NFR-010）；
- Element Plus 全量引入（项目规模下按需引入收益低，控制构建复杂度）；
- **Element Plus 主题定制**：覆盖其 CSS 变量，把默认蓝 `#409EFF` 换成品牌紫，并统一圆角与字体。只改视觉变量，不改组件行为与 API，升级 Element Plus 不受影响；
- **设计 token 单一出处**：`src/styles/tokens.css` 用 CSS 自定义属性定义全部色彩、间距、圆角，在 `main.js` 中于 Element Plus 样式之后引入使其生效。页面与组件一律引用变量，不写死色值。

#### 4.5.2 字体与排版

- 字体族用**系统字体栈**，不引入 webfont：`-apple-system, BlinkMacSystemFont, "Segoe UI", "Microsoft YaHei", "PingFang SC", sans-serif`。中文环境下系统字体（苹方 / 微软雅黑）质量已足够，而一个中文字体包动辄数百 KB，会让首屏白等——收益不抵成本；
- 数字一律 `font-variant-numeric: tabular-nums`，使表格与指标纵向对齐；
- 字号阶梯：

| 用途 | 字号 / 字重 |
|---|---|
| 顶栏页面标题 | 15.5px / 700 |
| 卡片标题 | 13px / 700 |
| 正文 | 13px / 400 |
| 次要信息 | 12px / 400 |
| 弱化信息 | 11.5px / 400 |
| 指标数字 | 13–15px / 700 |

#### 4.5.3 间距与圆角

- 间距基础单位 4px；内容区 `padding: 20px 22px`；卡片内 `padding: 16px 18px`；卡片间距 14px；
- **圆角按层级区分，不统一**：

| 元素 | 圆角 | 理由 |
|---|---|---|
| 卡片 | 8px | 大块面，稍大圆角更柔和 |
| 按钮、输入框 | 6px | 可点击元素的触感 |
| 菜单项 | 5px | 可点击 |
| 需强调的标记 | 4px | 小面积色块 |
| 数据条 | 2px | **不可点击**，故接近直角——圆角是"这里可以点"的信号 |
| 状态色点 | 50% | 圆点本身 |

#### 4.5.4 组件形态原则

| 场景 | 形态 | 理由 |
|---|---|---|
| 列表中的状态（默认） | 色点 + 文字 | 一屏常同时出现五种以上状态；若全做成彩色胶囊，界面会布满色块、每个都在喊"看我" |
| 需警示/强调的状态 | 带底色标记 | 强调必须稀缺才成立，只给「明天截止」这类真正需要注意的用 |
| 表示量级 / 占比 | 直角长度条 | 长度本身表达大小；套上圆角矩形反而模糊了"量"的语义 |
| 操作按钮 | 三级：实心（主操作）/ 描边（次操作）/ 纯图标（工具性） | 按重要性分级，避免所有按钮长成同一个样 |
| 菜单选中态 | 左侧竖色条 + 浅底 | 色条直接回答"我在哪儿"，比整块圆角矩形定位更准 |
| 列表项 | 下边框分隔 | 不必把每一项都做成卡片；卡片只用于内容确实独立成块处 |

**明确禁止**：

- 全站共用一个圆角值；
- 所有卡片压同一层柔和灰阴影（阴影只用于真正需要"浮起"的元素，如悬浮层、下拉层）；
- 每个区块标题上方加全大写小标签；
- 用渐变作为装饰。

#### 4.5.5 暗色模式

**本期不做**。SRS 未要求，且会使样式量与回归成本翻倍。但全部色值已通过 CSS 变量收敛在 `src/styles/tokens.css`，将来新增暗色只需补一套变量值，无需改动任何组件。

## 5. 核心机制设计

### 5.1 SSE 流式协议

**端点清单**（全部 POST + JSON 请求体，完整定义见接口文档）：`/stream/jd-analysis`（JD 分析）、`/stream/interview-chat`（面试作答+点评+下一题）、`/stream/interview-summary`（面试总结）、`/stream/practice-review`（陪练点评）、`/stream/experience-extract`（面经结构化）、`/stream/agent-chat`（Agent 对话）。

**事件格式**（text/event-stream）：

```
event: start
data: {"message": "正在分析…"}                  // 连接建立后立即推送，见下方感知延迟优化

event: delta
data: {"text": "增量文本片段"}

event: done
data: {"record_id": 123, "extra": {...}}
```

- `start`：**感知延迟优化**——后端进入 generator 后立即推送状态文案（"正在分析你的 JD…"等），界面在 300ms 内出反馈，覆盖 LLM 首字前的静默等待；LLM 首字 <2s 是真实延迟目标（NFR-001），start 事件保证用户从点击到界面反馈 <300ms（NFR-004 口径）；
- `delta`：LLM 增量 token（已按报告结构分段时带 `section` 字段标识当前段落）；
- `error`：中途失败，data 含错误码与 message，前端保留已渲染内容并显示重试；
- `done`：流结束，携带落库记录 id，前端据此刷新列表/跳转。

**后端实现要点**：

- 路由返回 `StreamingResponse(generator, media_type="text/event-stream")`；
- generator 内循环 `llm_client.stream_chat()`，逐块 yield；
- 连接断开（客户端刷新/关闭）→ generator 捕获 `GeneratorExit`/客户端断开异常，终止 LLM 调用，已生成内容按"半成品"落库（标注 interrupted）；
- 每个 SSE 请求内部持有独立 DB session，不与请求全局 session 混用。

### 5.2 Agent 设计（手写，不用 LangChain）

**整体循环**：

```
用户输入
  → ① 意图路由（规则+LLM 混合）：先规则快筛（关键词），不命中再 LLM 分类
  → ② 命中"需工具"意图：LLM Function Calling 输出 {tool_name, arguments}
      未命中：LLM 直接流式闲聊/问答回复（注入画像）
  → ③ 工具执行分两类：
       a. 查询类（查投递/搜面经/查提醒）：直接执行，流式回显结果卡片
       b. 写操作类（新增投递/更新状态/入错题本）：返回"确认卡片"给前端，
          用户点击确认后调用普通 REST 接口执行——LLM 绝不直接写库
  → ④ 执行结果以结构化卡片 + 流式文字总结回显
```

**意图枚举**：`APPLICATION`（求职操作）/ `PRACTICE`（笔试学习）/ `EXPERIENCE`（面经问答）/ `CHAT`（闲聊）。

**工具注册表**（Python dict：工具名 → 工具元数据 + 执行函数）：

| 工具名 | 类型 | 说明 |
|---|---|---|
| create_application | 写（确认卡片） | 提取公司/岗位/城市/日期，出确认卡片 |
| list_applications | 查询 | 按状态/公司过滤 |
| update_application_status | 写（确认卡片） | 状态流转 |
| generate_questions | 查询 | 出 N 道指定方向题目（可入库） |
| quiz_wrong_questions | 查询 | 抽错题（跳转抽问） |
| search_experience | 查询 | 关键词搜面经 |
| get_today_summary | 查询 | 今日概览摘要 |

**Function Calling 实现**：openai 兼容 SDK 原生支持 `tools` 参数（JSON Schema 描述工具），**不手写 JSON 解析**——SDK 返回结构化 `tool_calls`，失败时降级为追问"请再说清楚一点"。

**确认卡片场景的等待优化**：Function Calling 同样走 `stream=True`（tool_calls 增量回调），收到完整 tool_call 立即推 `tool_call` 事件；LLM 前置文字（如"好的，帮你记一笔"）以 `delta` 先上屏——用户先看到文字反馈、再看到确认卡片，全程无干等。

**画像注入**：组装 system prompt 时拼入画像摘要（结构化文本 ≤ 500 token），仅在 `APPLICATION`/`EXPERIENCE` 意图注入，`PRACTICE` 不注入（控制 token，NFR 低延迟措施第 6 条）。

**对话历史**：落库（agent_message 表），每次请求携带最近 10 轮，超长截断。

### 5.3 Prompt 工程

**统一约束（所有场景 system prompt 头部）**：

1. 角色设定一句（面试官/点评官/求职助手）；
2. 输出格式要求（如 JD 报告五段结构、每题点评三段结构）——用序号标题分隔，便于前端分段渲染；
3. 长度约束（如"参考答案 ≤ 200 字"）——控制 token 与首字延迟；
4. 禁止输出 markdown 表格（打字机渲染体验差），用列表。

**场景 prompt 模板表**（模板存 `backend/app/prompts.py`，统一管理便于调优）：

| 场景 | 要点 |
|---|---|
| JD 分析 | 画像全文 + JD 原文；强制五段结构；分项评分 0~100 |
| 模拟面试 | 公司/岗位/方向 + 已问题目摘要；一题一答节奏；点评 = 评分+亮点+不足+参考要点 |
| 面试总结 | 全部问答记录；输出总评+分题得分表（列表式）+改进清单 |
| 八股点评 | 题目+标准答案（题库有则附）+用户答案；评分+参考答案+差距点 |
| 面经结构化 | 原文；LLM 流式输出 JSON 数组[{question, answer_points}]，后端流式收集增量——前端不逐字展示 JSON，显示提取进度状态，done 后回显条目供确认 |
| Agent 系统 | 画像摘要 + 工具说明；Function Calling 模式 |
| 错题判定 | 题目+标准答案+用户答案；输出 {"correct": true/false, "explain": "..."} |
| 提醒文案 | 结构化提醒数据；输出一句话文案（失败用模板兜底） |

### 5.4 LLM 调用封装与多供应商适配

**供应商 → 模型两级注册表（provider + model registry）**：

| 供应商 key | base_url | 内置模型（**加粗**为默认） |
|---|---|---|
| deepseek | `https://api.deepseek.com` | **deepseek-flash**（V4.1 Flash）、deepseek-v4-pro（退役路由中） |
| zhipu | `https://open.bigmodel.cn/api/paas/v4` | glm-4.7-flash（免费）、glm-4-flash（免费） |
| kimi | `https://api.moonshot.cn/v1` | kimi-k2.6、kimi-k2.7-code、kimi-k3 |
| siliconflow | `https://api.siliconflow.cn/v1` | Qwen3-8B 等（9B 以下免费） |
| custom | 用户自定义 | 用户自定义 |

- 全部走 **OpenAI 兼容协议**：选供应商 = 定 base_url 与 Key；选模型 = 定 model——两级配置，SDK 与调用代码零改动；
- 注册表内建在代码中（`llm_provider.py`），新增供应商/模型只需加配置，无需改业务代码；
- 免费供应商限速时触发统一兜底（重试 + 错误提示），与付费供应商行为一致。

**模型列表动态更新（保证可选模型"最新可用版本"）**：

- OpenAI 兼容协议提供 `GET /models` 端点；`llm_client.list_models(provider)` 实时拉取该供应商当前可用模型；
- 拉取结果缓存 24h（config 表 `llm_models_cache`，JSON 含 fetched_at）；设置页"刷新模型列表"强制重拉；拉取失败回退内置表并在 UI 标注"内置列表（上次拉取失败）"；
- 内置表随项目版本维护；运行时以动态拉取为准。

**模型退役兜底**：供应商退役模型 ID 时通常自动路由替代模型（如 deepseek-v4-pro → deepseek-flash）；调用返回"模型不存在"→ 提示用户去设置页重选模型（错误码 10013 含此原因）。

```
llm_client 职责：
├─ stream_chat(messages, tools=None)   → 异步生成器，逐块 yield token（LLM 侧 stream=True）
├─ chat_json(messages)                 → 非流式，返回解析后的 JSON（面经结构化/错题判定用）
├─ test_connection(provider, key)      → 连通性测试（发一条最小消息，返回成功/失败原因）
├─ list_models(provider)               → GET /models 拉取模型列表（24h 缓存，失败回退内置表）
├─ 统一配置：两级注册表 + config 表配置（base_url/api_key/model 均运行时读取，切换即时生效）
├─ 超时：连接 5s、首 token 8s；超时抛 LLMError
├─ 重试：失败重试 1 次（仅网络类错误；429/鉴权错不重试）
└─ mock 注入点：provider 依赖注入，测试时替换为 FakeLLM（见测试计划）
```

**Key 读取链**：config 表（设置页填写）→ 环境变量（.env）→ 都无则调用前抛配置错误（10012），前端引导去设置页。

### 5.5 定时引擎设计

- APScheduler `BackgroundScheduler`，启动时随 FastAPI lifespan 注册，**每日 07:00 触发**一次 `reminder_engine.run_daily()`（开发期提供手动触发接口便于演示，见接口文档）；
- 判定全为纯规则 SQL（无 LLM）：

| 任务 | 实现 |
|---|---|
| 投递跟进 | `SELECT ... WHERE status='APPLIED' AND date(now) - date(applied_at) > 3` |
| 错题到期 | `WHERE next_review_at <= now AND review_stage < 5` |
| 待面试 | 按 `next_event_at` 字段区间查询（投递记录上的笔试/面试时间字段） |
| 就业网抓取 | 每日 1 次 HTTP 抓取 + 简单 HTML 解析；异常捕获后记日志跳过 |

- 提醒文案：数据齐后调 LLM 一次生成概览文案（可配置关闭，关闭或失败时用固定模板）；
- 执行互斥：`max_instances=1, coalesce=True`，防重入。

### 5.6 语音链路设计（P2）

```
[前端] 按住说话（按住录音，松开发送）
  MediaRecorder 录制 webm（audio/ogg，3~5s 短句）
    → POST /api/v1/asr/transcribe（multipart 上传）
      → asr_client.transcribe(audio_bytes)
        → 讯飞 WebSocket 短句听写（Audio16k 规格，Key 在 .env）
      → 返回 { text }（仅文字回填，不落库不提交）
[前端] 回填输入框 → 用户编辑 → 提交（走原有文字流程）
```

- `asr_client` 抽象基类 + `XunfeiAsrClient` 实现（备选阿里实现预留），设置页可切换供应商配置；
- 转写失败：返回错误码 60001，前端 toast"转写失败，可重试或直接打字"，**不阻塞面试流程**；
- TTS：前端 `speechSynthesis` 直接朗读最后一段 AI 文本（设置开关，默认关），无后端参与。

### 5.7 乐观更新机制

适用场景：Agent 一句话录入投递、状态流转确认。

```
用户对 Agent 说"记一笔投递"
  → LLM 提取字段 → 前端立即渲染确认卡片（此时尚未入库，卡片标"待确认"）
  → 用户点确认 → 调 POST /applications → 成功：卡片转"已入库"+ 看板刷新
                → 失败：卡片转红色错误态 + 重试按钮
```

原则：**乐观展示、确认才写、失败可重试**；任何写操作必须有后端确认，前端不得仅本地模拟成功。

## 6. 安全设计

| 威胁 | 设计对策 |
|---|---|
| Key 泄露 | .env 已 gitignore；设置页 Key 输入框用密码型+不显示明文回读；日志脱敏（不打印 Key/请求头） |
| SQL 注入 | 全程 SQLAlchemy ORM 参数化；禁止 raw SQL 拼接（NFR-009） |
| XSS | 前端不 v-html 渲染 LLM 输出/用户输入；后端 DTO 长度校验（NFR-010） |
| SSRF | 就业网抓取 URL 白名单校验（仅允许 http/https + 主机白名单，设置页可配但默认锁定学校域名） |
| 路径穿越 | 批量导入文件：校验扩展名+大小 ≤ 2MB+临时目录读取，文件名不参与路径拼接 |
| CSRF | 单用户部署形态，接口无 Cookie 会话（无状态 REST），不引入 CSRF token（设计声明） |

## 7. 异常处理设计

| 场景 | 处理 |
|---|---|
| LLM 超时/网络错 | llm_client 重试 1 次 → 失败抛 LLMError → SSE 发 error 事件（流中）/ 502（普通请求）→ 前端提示+重试按钮 |
| LLM 返回格式不符 | 解析失败 → 降级为纯文本流式展示（JD 报告）；JSON 场景（面经/错题判定）解析失败 → 重试 1 次后提示"AI 输出异常，请重试"，数据不落库 |
| 用户中途关页面（SSE 断连） | 后端捕获断开，终止 LLM 调用，已生成部分落库（标记 interrupted），不重复计费 |
| 数据库锁（SQLite 并发写） | WAL 模式 + 写事务最小化；定时任务与请求并发写时靠 WAL 读并发写串行，无需额外锁 |
| 就业网结构改版 | 解析失败 → 保留上次数据 + 记录最后抓取时间与失败原因，不抛错到前端 |

## 8. 可测试性设计

- **LLM mock 注入点**：`llm_client.provider` 是唯一出网口，测试 fixture 替换为 `FakeLLMProvider`（返回预设 token 流/JSON），全部 AI 链路离线可测（详见测试计划）；
- **讯飞 mock**：`asr_client` 抽象接口，测试注入 FakeAsr；
- **定时任务**：`reminder_engine` 的判定函数为纯函数（输入时间戳/记录集 → 输出提醒集），不依赖调度器即可单测；
- **测试数据库**：pytest 使用独立临时 SQLite 文件（tmp_path），不碰开发库。
